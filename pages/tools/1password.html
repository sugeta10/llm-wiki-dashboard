1Password — パスキー・CLI・ゼロ知識暗号化で個人とエージェントの資格情報を 1 か所に置く

TL;DR: 2026 年 10 月に相次いだ不正アクセス事件を機に、パスワードの使い回しと 3 社のパスワードマネージャーの併用をやめて 1Password へ全面移行した hayatosc（@sh_at_tus・東京理科大学の学部 4 年）が、パスキーのデバイス間共有・op:// 参照で秘密をローカルに置かない 1Password CLI・2 つの鍵によるゼロ知識暗号化・エージェントにパスワードを渡さない 1Password for Agents の 4 点を「全人類導入すべき」理由として挙げた導入記。本ページは製品本体のハブで、機能と実践は別ページが持つ。

hayatosc は記事の冒頭で「世はまさに大不正アクセス時代である」と書き、次の事例を並べる。GMO へのサイバー攻撃で顧客と自社の情報が公開され警視庁が捜査（日テレ NEWS）、ソースネクストのパスワードが「暗号化していたが、鍵にアクセスできるシステムに侵入された」ために平文で流出（ITmedia）、メドレーの産婦人科向けシステムへの不正アクセスで最大 787 医療機関の患者情報が漏えいした可能性（ITmedia）、デジタル庁の問い合わせフォームの情報が Studio のクラウド環境への不正アクセスで漏えい（ScanNetSecurity）、タイムズカーの個人情報最大 660 万件流出で免許証画像も対象（日本経済新聞）。hayatosc は「どの個人情報が漏えいしていないのか探す方が簡単」と述べ、自分にも迷惑メールが届いたとする。一方で自身はパスワードを使い回し、パスキーの登録はまちまちで、パスワードマネージャーは Google・Vivaldi・Apple の 3 重管理だったと振り返り、意を決して 1Password に丸ごと移行したところ体験の良さに「QoL が爆上がりした」ので共有したい、と書く。

パスキーをデバイス間で共有できる

hayatosc が「めちゃくちゃデカい」と最初に挙げるのがこれである。パスキーの最大の問題はデバイス間で共有できないことで、Google アカウントをパスキーで登録すると手元のスマホ・持ち運ぶ Windows PC・自宅の Windows PC で 3 回以上の登録が要り、サイトが増えると何がどこに登録済みか分からなくなっていた。1Password に入れるとパスキーは 1 個登録すればどこからでもログインでき、「パスキーはセキュリティに強いが不便なもの」という自分の印象がツール 1 つでひっくり返った、と hayatosc は書く。パスキーにはフィッシング耐性があるとして、「パスワードは死んだ」と言い切る。

1Password CLI：秘密をローカルに置かず op:// 参照だけ置く

hayatosc が「マジで神ツール」と呼ぶのが 1Password CLI（保管庫の項目をターミナルから読み書きする 1Password 公式のコマンドラインツール）である。開発者は OpenAI や Stripe の API キー、SSH 鍵のような、1 度流出すれば他人に使われて損害を生む秘密を日々扱い、.env のようなファイルで管理するが、他人にどう渡すかで難儀する。1Password CLI は API キーを 1Password 上に置いて必要なときに読み出すだけにし、ローカルに置くのは op://vault/item/field という参照文字列だけでよい、と hayatosc は説明する。これはコーディングエージェントに任せるときにも効き、エージェントが API キーを読むことなく実行できるので、エージェント経由の漏えいリスクを大きく避けられる、と続ける。

記事は参照がどの時点でどのプロセスに展開されるかを書いていない。エージェントが起動したサブプロセスの環境変数に値が展開される構成では、エージェントが実行するコマンド次第で値が出力に現れうるので、再現するならエージェントのプロセスから値が見える経路があるかを先に確かめる必要がある（wiki 側の注意・推論）。

ゼロ知識暗号化：1Password 側が攻撃されても中身は読めない

hayatosc は 1Password のセキュリティの中心を「ゼロ知識暗号化」方式と説明する。保存されたパスワードは「マスターパスワード」と「シークレットキー」という 2 つの鍵で暗号化され、この 2 つは 1Password 側に一切保存されず、復号はローカルでしかできない。だから万が一 1Password が不正アクセスされ保管庫が流出しても、中身が解読されてパスワードが漏れることはない、と書く。hayatosc はこれを 1Password が「他の追随を許さない安全性」を持つ理由とし、対比として LastPass の 2022 年の流出事件（GIGAZINE）を挙げ、1Password は他のパスワードマネージャーが起こしてきた流出事件を起こしていない、と述べる（いずれも hayatosc の評価）。

1Password for Agents：エージェントに平文のパスワードを渡さない

hayatosc が「最高に激アツ」と評するのが 2026 年 10 月に発表された 1Password for Agents で、ITmedia の「AI にパスワード渡さずアクセス権限付与可能に」という記事を引く。hayatosc の整理では、最近のトレンドは自分の代わりになんでもやるパーソナル AI エージェントで、今年 3 月頃の OpenClaw、直近の SpaceXSI の Grok Bot（grok-bot）・OpenAI の dots（openai-dots）・Meta の Muse などが出てきた。これらが既存のものと違うのは、それぞれ専用のコンピューターを与えられ、ブラウザを起動してサイトにアクセスしたり別のソフトを起動したりと、そのコンピューターでできることが全部できる点だという。ブラウザ操作につきまとうのが「ログインどうするのか」問題で、人間がログイン部分だけ手で操作する面倒なやり方か、チャットにパスワードを打ち込む危険なやり方しかなかった。1Password for Agents はエージェントに平文のパスワードを渡さずに認証を通すので、「もう人間がウェブサイトを操作する時代は終わった。全人類は AI にブラウザ操作を一任すべき」と hayatosc は書く。仕組み（エージェントが固有のデジタル鍵で身元を示し、利用者が自分の端末で承認し、1Password がフォームへ直接入力する）と対応エージェント一覧は 1password-for-agents に収録している。

学生向けの条件

hayatosc は、学生なら GitHub Student Developer Pack の特典で 1Password に 2 年間無料で入れると書き、1Password の学生向けページを案内している。1Password 公式の学生向けページ（1password.com/jp/developers/students）を取得したが、抽出したテキストに期間の記載は含まれておらず、2 年という年数は未確認である。記事は「1Password に全部賭けろ」で締める。

ゼロ知識暗号化とパスキー集約への反論（@emadurandal_cgj）

hayatosc の告知投稿を引用して、Web3D ライブラリ RhodoniteTS の作者 @emadurandal_cgj が「1Password お勧めなのは同意」としたうえで 2 点を指摘した（2026-10-31・1,511 ブックマーク）。第一に、LastPass もゼロ知識暗号化に対応したサービスで、同社のデータ漏えいで被害が出たのは流出した保管庫に攻撃者が総当たり攻撃をかけたためであり、1Password でも同社から保管庫が流出し利用者のマスターパスワードが短いなどの条件が重なれば同様のリスクがある。「ゼロ知識暗号化＝サービスとして絶対安全ではない。運営側のセキュリティ体制も含めて安全性が計られる」と @emadurandal_cgj は書く。第二に、1Password へのパスキー保存は正規の運用でプラットフォームを問わずまとめられて便利だが、今度は 1Password クライアントを入れた全端末を守る必要が生じる。「リスクが消えたのではなく、リスクの場所が変わった」のであり、端末がマルウェアに感染し、そのとき保管庫がアンロックされていればデータ漏えいの危険はある、と続ける。

@emadurandal_cgj 自身は、パスキーを含むすべての認証手段を 1Password に保存するのはリスクがあると考え、Google Authenticator などの二要素認証とパスキーは 1Password で運用していない。パスキーは YubiKey（USB や NFC で接続するハードウェアセキュリティキー）に保存し、キーを挿さないと認証が通らないようにしたうえで、YubiKey 自体にも PIN を設定して紛失・盗難時にも安全なようにしている。安全性と利便性はトレードオフで hayatosc の運用を否定する意図はない、と断っている。

1Password 公式のサポートページ「About your Secret Key」は、アカウントパスワードとシークレットキーを組み合わせて暗号鍵を作り、アカウントパスワードは「端末上のデータ」を、シークレットキー（128 ビットで 1Password は保持しない）は「端末の外のデータ」を守る、サーバーへの総当たり攻撃はシークレットキー無しには復号できない、と説明している。この説明に照らすと、第一の指摘がそのまま成り立つのはサーバー側の保管庫に加えてシークレットキー（端末やエマージェンシーキットに保存される）も攻撃者の手に渡った場合で、サーバー側の流出だけなら LastPass の事例と前提が異なると考えられる（wiki 側の読み）。一方で第二の指摘は、公式ページの「端末上のデータを守るのはアカウントパスワード」という説明と整合し、端末が侵害された状況ではシークレットキーの設計は効かない。hayatosc が「1Password 側が攻撃されても中身は読めない」と書いた安全性は、端末側の安全を前提にしたものと読むのが正確と考えられる。

位置づけ（wiki 側の読み）

この wiki には 1Password を扱うページが既に 3 つあり、それぞれ製品の一面を持つ。1password-for-agents はサインインを代行する機能の公式発表、1password-cli-password-audit は CLI 経由で Claude Code に手持ちのパスワード 1,116 件を点検させた実践（チャエン・GOROman）、grok-bot-ai-team-workspace は Grok Bot 7 体の「認証情報の共有の土台」に 1Password を置いた個人構成である。本ページは製品本体のハブとして、hayatosc の 4 点をこれらの入口にする位置にあると考えられる。

hayatosc の CLI の使い方（エージェントがキーを読まずに実行する）は、チャエンの構成（Claude Code が CLI で保管庫を読む）と同じ CLI を使いながら、エージェントに何を見せるかの向きが逆である。前者は idp-shared-cli-mcp や claude-projects-threads の API credentials と同じ「秘密は AI に渡さず、使う瞬間だけ別の層が代行する」形で、1Password for Agents もこの形をサインインに適用したものと読める。記事の冒頭の事件一覧は、personal-data-leak-checklist が「漏えいニュースの後に確認する個人の設定」として挙げた状況そのもので、本ページはその先にある「パスワードとパスキーの置き場所を 1 つにする」実装にあたる。

問い

  • パスキーとパスワードを 1Password に集約すると 1Password のアカウント自体が単一障害点になる。マスターパスワードとシークレットキーの保管と復旧をどう設計するか（記事は触れていない）
  • 自分の Claude Code / Codex の .env を op:// 参照に置き換えるとき、値が展開される経路（サブプロセスの環境変数・ログ・エージェントのツール出力）をどこまで塞げるか
  • 学生向けの無料期間と条件は公式ページで取り直す。抽出テキストに期間の記載が無かったのは動的に出る内容か、記載自体が無いのか
  • パスキーと二要素認証を 1Password に入れるか YubiKey に分けるかは、@emadurandal_cgj の言う「リスクの場所」をどこに置くかの選択になる。自分の端末のうち保管庫をアンロックしたまま使う時間が最も長いものはどれで、そこがマルウェアに感染したときに守りたい認証手段は何か
