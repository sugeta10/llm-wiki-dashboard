「AI っぽくない UI」のための 15 リンク（部品と配色 → エージェント向け設計資産 → 作図と画像処理）

TL;DR: seeco（@seeconvm）が「Fable 5.2 は誰にも AI 製と分からない UI を作れる」として並べた、無料・オープンソースの 15 リンク。shadcn/ui・Tailwind CSS・Magic UI・Lucide・Leonardo の UI 部品と配色、ui-ux-pro-max・frontend-design・theme-factory・DESIGN.md・Astryx・stitch-skills・Figma Context MCP のエージェント向け設計資産、Excalidraw・tldraw・rembg の作図と画像処理。15 のうち 2 項目は同じ anthropics/skills リポジトリ内のスキルで、リポジトリとしては 14 本。

投稿者の seeco はプロフィールに「ai researcher / post about AI / crypto / open for collabs」とある個人アカウントで、デザイナーやツール作者としての肩書は書かれていない。投稿は 487 件ブックマークされた（2026-11-19 時点）。「紫のグラデーションも汎用カードもなし」という枕は、AI 製 UI の凡庸さを指す言い方として impeccable や unslop が検出対象に挙げる兆候と同じ語彙で、一覧の狙いもそこにある。末尾の「ブックマークして、この一覧を Fable 5.2 に貼ってランディングページを作り直せ」と、引用先の同じ投稿者の X 記事（Fable 5.2 のモーションデザイン講座）への誘導は宣伝的な枠で、14 本のどのリポジトリの description にも Fable 5.2 への言及はない。同じ「リポ N 選」形式の creative-pipeline-repos（Florence の映像制作 10 本）と作り方が同じで、見どころも個々のリポの新しさではなく、何を揃えれば「AI っぽくない」に届くかという並べ方にある。

投稿者の一言と GitHub 記載の照合

  • エージェント向けに作られたのは 7 項目（6 リポジトリ）。ui-ux-pro-max（AI スキル）・frontend-design と theme-factory（Agent Skills）・DESIGN.md（エージェント向け仕様）・Astryx（agent ready）・stitch-skills（Stitch MCP 前提の Agent Skills）・Figma Context MCP（MCP サーバー）は description 自体がエージェントからの利用を前提にしている。残る 8 本（shadcn/ui・Tailwind CSS・Magic UI・Lucide・Leonardo・Excalidraw・tldraw・rembg）は人が使う汎用のライブラリとアプリで、一覧の半分強はエージェント以前から定番の道具である。
  • 2 項目は同じリポジトリ。7 本目と 8 本目はどちらも anthropics/skills の中のディレクトリで、スターの 197,472 はリポジトリ全体の数であり、2 本のスキルの人気ではない。anthropics/skills はリポジトリのライセンス欄が未設定で、各スキルの利用条件は中を見る必要がある。
  • 数字の食い違い。投稿者は ui-ux-pro-max を「80 の UI スタイル」と書くが、ui-ux-pro-max が README から転記した数は 79 スタイル（2026-08 時点）。差 1 はバージョン差か丸めかは未確認。
  • Figma Context MCP は個人製。所有者 GLips は個人アカウントで、claude-code-mcp-stack が構成に挙げる Figma の MCP サーバー（同ページは公式 MCP サーバー 8 本として整理）とは別物と考えられる。description も「Cursor などの AI コーディングエージェント向け」と第三者製の立場で書かれている。
  • 更新の鮮度に差がある。Leonardo の最終 push は 2026-07-08 で、他の 13 本（2026-11-06 から 19 の間）より 4 か月空いている。tldraw の description は自分で「エージェント推奨 No.1」と名乗る宣伝文で、リポジトリ側の自己申告である。

既存ページとの関係（wiki 側の推論）

  • 15 項目のうち wiki に独立ページがあるのは ui-ux-pro-max と design-md の 2 本。frontend-design スキルは ui-skills のカタログ行と claude-premium-website-build のワークフローに登場し、同カタログの shadcn スキル（shadcn-ui 作）は 1 本目の shadcn/ui 本体を扱うスキルである。shadcn/ui 本体のページは無く、取得した README は冒頭の説明（「自分のコンポーネントライブラリを作るために使う」・MIT）だけなので、本ページの行に留めた
  • AI 製 UI の凡庸さ対策として wiki にある impeccable（frontend-design スキルから派生した決定論検出器）・unslop・taste-skill はこの一覧に入っていない。一覧は「凡庸さを検出して直す」側より、「良い部品と仕様を先に渡す」側に寄っている
  • DESIGN.md（仕様を書いて渡す）・Astryx（出来合いのデザインシステムを渡す）・stitch-skills（プロンプトから画面を起こす）は、エージェントにデザインを与える 3 つの経路として並べられている。design-md が frontend-design との役割分担（禁止ルールか参照仕様か）を問いにしているのと同じ線が、Astryx と stitch-skills にも引ける
  • 同じ「リポ N 選」の投稿形式では creative-pipeline-repos が映像制作の工程別、agent-skills-by-role が職種別、本ページが UI の素材から接続までの層別にあたる

問い

  • 独立ページがない 12 本のうち、エージェント用途で README を読む価値が高いのは Astryx（Meta のエージェント対応デザインシステム）と stitch-skills（Stitch MCP サーバー前提）。DESIGN.md が「仕様を書く」なら Astryx は「システムを渡す」別解か、重ねて使うものか
  • 「紫グラデーションなし・汎用カードなし」をこの 15 本のどれが保証するか。部品ライブラリ（shadcn/ui・Magic UI）の既定値はそのまま使うと「AI っぽい」になりうる。一覧を貼って作った画面を impeccable の 62 ルールで検出させると何本引っかかるか
