Claude Code 公式 MCP サーバー8選と工程別スタック

TL;DR: Boris Cherny（Claude Code 開発者）の「Claude に自分の出力を検証する手段を渡せ」を、工程ごとに公式 MCP サーバーで実装する構成論。@kimuai08 が Context7・Playwright・Figma・Linear・Sentry・Cloudflare・Stripe・GitHub の8本を選び、初心者は Context7→ブラウザ→Linear/GitHub の3段で十分と述べる。

flowchart LR
  Figma["Figma MCP\n設計データ"] --> C7["Context7\n現行の正しい書き方"] --> CC["Claude Code\n実装"] --> PW["Playwright MCP\nブラウザ検証"] --> GH["GitHub MCP\nPR・レビュー対応"] --> CF["Cloudflare MCP\nデプロイとログ"]

MCP を1本ずつ「便利ツール」として入れても効果が薄い、と@kimuai08は述べる。価値が出るのは、情報を取る→計画する→作る→自分で検証する→外部に反映する→結果を見る、というループを Claude Code から一歩も出ずに閉じたときで、Boris の「検証する手段を渡せ」はブラウザ1個の話ではなく「工程ごとに、その工程の正解を確認できる手段を渡せ」という意味だと解釈している。本ページは、その解釈に沿って8本の公式サーバーと使い方の型を整理したもの。MCP の仕様改定（ステートレス化・長時間処理・UI 返却・組織認証）は claude-mcp を正本とし、ここでは扱わない。

Boris Cherny の3原則（@kimuai08 の整理）

@kimuai08 は Boris の発信を並べると主張はずっと同じだと述べ、3原則にまとめる。

  1. Claude に、自分の出力を検証する手段を渡す。Boris はこれを「最も重要な Tip」と呼ぶ。ブラウザ禁止で Web サイトを作らせてもまともなものは上がってこないが、ブラウザを渡せば作って・見て・直してを納得いくまで繰り返す、という説明を@kimuai08が紹介している
  2. 1日1回以上やる作業は、仕組みにする。毎回チャットで同じ手順を説明せず Skill やコマンドにする。呼ぶまでコストがほぼゼロなので作っておいて損がない
  3. 外部ツールを、Claude Code の作業面に持ち込む。Slack・課題管理・DB・社内 API を直接触れるようにし、ツール間の移動そのものを消す。ここで MCP が登場する

@kimuai08 は Boris の働き方として、自分では手でコードを書かず、ターミナルで5つ前後・Web で5〜10 の Claude セッションを同時に走らせてタブに番号を振り通知で入力待ちを管理していること、CLAUDE.md は100行程度しかないこと、「プロンプトを書くな。ループを書け」が最もよく引用される言葉であることを挙げる（Boris の一次発信の整理は claude-code と loop-engineering を参照）。

8本の公式サーバー

選定基準は、提供元が自分で管理している公式であること・初心者でも効果を体感しやすいこと・3原則のどれかを直接実装できること、の3つ（@kimuai08）。

# サーバー 消える往復 実践プロンプトの要点（@kimuai08 が「必ず入れろ」とする行） 公式
1 Context7 古い書き方のコードを自分で直す 現バージョンの推奨・廃止済み・差分・修正ファイルを整理してから実装。推測で実装しない。1回の問い合わせに複数の概念を混ぜない https://github.com/upstash/context7
2 Playwright MCP 作った画面を自分でブラウザで開く 新規登録・ログイン・入力エラー・スマホ幅・ログアウトを実操作で検証。失敗時はコードからの推測でなくブラウザで再現してから修正し、再実行で成功を確認してから完了報告 https://github.com/microsoft/playwright-mcp
3 Figma MCP スクリーンショットから余白・色を目視で当てる まず構造・再利用コンポーネント・色とタイポ・余白・レスポンシブ変化だけを抽出し実装に入らない。既存コンポーネント優先、新規は「なぜ既存で足りないか」を先に説明 https://developers.figma.com/docs/figma-mcp-server/
4 Linear MCP Issue をコピペし進捗を手で書く 不足情報の洗い出し→コード調査→計画提示→承認後に実装とテスト→Issue にコメント。ステータス変更は人間が確認してから https://linear.app/docs/mcp
5 Sentry MCP スタックトレースをコピペする 直近24時間で影響ユーザー最多の未解決エラーを取得し、発生条件→関連コード→再現テスト→最小修正→全テスト→根本原因まとめ。再現できないなら推測で直さず、必要な追加情報を列挙して止まる https://docs.sentry.io/product/sentry-mcp/
6 Cloudflare MCP デプロイ先の状態を別画面で見る エラー・レスポンス時間・キャッシュヒット率・セキュリティイベント・Workers 例外を調べ、コード変更が要るもの／設定だけで直るものに分類。承認まで設定変更しない。導入初期は読み取りのみ https://developers.cloudflare.com/agents/model-context-protocol/cloudflare/servers-for-cloudflare/
7 Stripe MCP Stripe 側の商品・Webhook 設定を別タブで確認 Product/Price・Checkout Session・Webhook イベント・解約・支払い失敗・二重登録防止・テスト方法を確認して月額課金の計画を作る。テストモードだけを使い本番データに触れない https://docs.stripe.com/mcp
8 GitHub MCP レビューコメントを読んで戻る 未解決コメントを「必ず修正」「設計判断が必要で人間が決める」「修正不要（理由つき）」に分類し、必ず修正だけ実装してテストを通す https://github.com/github/github-mcp-server

補足として@kimuai08は次を述べる。Playwright MCP が画面を読む手段はスクリーンショットではなくアクセシビリティツリーなので、見た目が似た要素を取り違えにくい。Boris 本人が Web 作業で毎回使うと言っているのは Playwright MCP ではなく Claude Code のブラウザ拡張の方で、ログイン状態を共有できるため安定する、という言い方を Boris はしている。使い分けは、自分のログイン済みブラウザで実画面を見ながら確認したいなら拡張、テストとして何度も同じ手順を回したいなら Playwright MCP。GitHub MCP の価値は git コマンドを打てることではなく、Issue 詳細・PR のレビューコメント・CI 結果・別リポジトリ・組織内コード検索といったリモート側にしかない情報を横断できることにある。Stripe は MCP に加えてエージェント向け Skill も用意しており、MCP で操作し Skill で作法を守らせる組み合わせが強い。

工程に沿って並べる2つのスタック

@kimuai08 が提示する並べ方は2つ。

  • Web 制作スタック: Figma で設計を取る → Context7 で今の正しい書き方を確認 → Claude Code で実装 → Playwright でブラウザ検証 → GitHub で PR とレビュー対応 → Cloudflare でデプロイとログ確認
  • SaaS 開発スタック: Linear で要件を取る → Context7 で技術仕様を確認 → Claude Code で実装 → Stripe で決済を設定して検証 → Playwright でユーザー操作をテスト → Sentry で本番エラーを監視

初心者が入れるのは3つだけ

8個全部入れると後述の落とし穴に落ちるので、次の3段で十分だと@kimuai08は述べる。

  1. Context7。目的は間違ったコードを減らすこと。読み取り中心でリスクが低く、効果を最も早く体感できる
  2. Playwright またはブラウザ拡張。目的は Claude 自身に成果物を検証させること。作る→開く→崩れを見つける→直す→また開く、に人間が挟まらなくなる
  3. Linear または GitHub。目的は仕事の入口と出口を繋ぐこと。ここまで来ると Claude Code は「指示待ちのコーダー」から「仕事を自分で進めるメンバー」に変わる

今日やることは1つだけで、Claude Code と別の画面を行ったり来たりしている場所を1つ探し、それを消す MCP だけを入れて効果を体感してから次を足す、というのが記事の結論。

4つの落とし穴

  1. MCP を増やすほど賢くなるわけではない。候補ツールが増えると迷う・文脈を食う・似たツールを取り違える・頼んでない操作をする・権限管理が複雑になる。100個より今の作業に必要な3〜5個をプロジェクトごとに切り替える。@kimuai08 自身も10個以上繋いで「急にバカになった」と感じ、減らしたら直ったと述べる
  2. 読み取りと書き込みを最初から一緒にしない。読み取りは許可・作成と更新は確認を挟む・削除と本番操作は拒否。本番デプロイ・DNS 変更・顧客データ変更・決済の本番操作・Issue 削除・PR マージ・DB 削除は最初から全面許可しない。MCP は便利さと危険さが完全に比例する。この線引きを外部ポリシー層で持つ設計は ai-agent-governance が扱う
  3. 公式とコミュニティ製を混同しない。検索サイトには同名サーバーが複数並び、公式一覧に載っていても提供元の公式実装とは限らない。提供元組織が管理しているか・最終更新・セキュリティポリシー・認証方式・要求権限・削除や本番変更ができる設計か、を見る
  4. 外部から来た文章をそのまま実行させない。Issue や PR コメントには他人が書いた文章が入り、手順の中に余計な指示が混ざっていれば Claude が読んでしまう。外部入力を扱う MCP では、何をやろうとしているかを一度提示させる

まだ固まっていない領域

@kimuai08 は「盛らずに書く」として次を挙げる。長時間ジョブを MCP 経由で投げる仕組みは仕様としては正式に入ったが各サーバーが対応しているかは別で、使う前に対応状況を確認する。会話の中に UI を返す仕組みもこれから広がる段階。料金・提供条件・認証方式・権限範囲は動くので公式リンクを使う前に見に行く。「MCP を入れると性能が何倍」という数字は証明されていないので出さず、代わりに測るべきは1日のうちコピペ・画面移動・目視確認に何分使っているか、だと述べる。

問い

  • このvaultの運用で「Claude Code と別画面を往復している場所」はどこか。X API（xurl）と NotebookLM は既に CLI 化しているが、公開サイトの表示確認は Playwright MCP で閉じられるか
  • 「読み取りは許可・書き込みは確認・削除は拒否」を Claude Code の permissions と hooks でどこまで決定論的に強制できるか（claude-code-instruction-methods の「ガードレールは hook＋permissions」と対応）
  • Boris が Playwright MCP でなくブラウザ拡張を選ぶ理由（ログイン状態の共有）は、自動テストと探索的確認の使い分け基準として自分の作業にも当てはまるか
