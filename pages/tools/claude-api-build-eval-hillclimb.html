/claude-api build-eval と /claude-api hillclimb（Claude Code の eval 用2コマンド）

TL;DR: Claude Code 同梱の claude-api スキルに追加された、試験（eval）を人の確認つきで組む build-eval と、変更を1回1つずつ試して「改善役に見せない test 側でも点が上がった修正だけ」を残す hillclimb の2コマンド。点数だけ上がる過剰適合を手順で防ぐのが核心。

問題集め・採点役の検証・問題の分割・修正の採否判定は、これまで人が自分で組み立てていた作業だった。まさお（note「まさお@未経験からプロまでAI活用」）は、Anthropic 公式ブログを読み自分でも動かしたうえで、変わったのは「誰が手を動かすか」で、2コマンドでは Claude が手を動かし要所で人に承認を求める形になったと解説する。公式の位置づけは新しいモデルや製品ではなく、claude-code に同梱された claude-api スキル（Anthropic API の使い方や Claude との仕事のコツを Claude に渡すスキル）へのコマンド追加である。claude update で最新版が入り、アプリのリポジトリで Claude Code を開いてコマンドを打つだけで使える、と同氏は書く。

flowchart LR
  A["build-eval: 問題を集める"] --> B["人が入力を確認"]
  B --> C["採点役を提案・人が試し採点を確認"]
  C --> D["ベースライン計測"]
  D --> E["hillclimb: train/test に無作為分割"]
  E --> F["変更を1つ試す"]
  F --> G{"test でも伸びた？"}
  G -- yes --> H["残す"]
  G -- no --> I["捨てる"]
  H --> F
  I --> F

build-eval：質問に答えるだけで試験とベースラインができる

まさおが実際に動かした範囲では、/claude-api と打つと補完候補に build-eval と hillclimb が出る。最初に「問題を本番ログから取るか」などの選択式の質問が来て、次に採点をプログラム判定にするか LLM 採点にするかを選び、そのまま直す前の点数（ベースライン）の計測へ進んだという。

同氏が紹介する公式の説明では、Claude は決まった所で手を止めて人の確認を待つ。人が確かめるのは入力と採点の2か所で、集めた入力は簡単なページに全部並べて見せ、採点役は試しに数件を採点して「違う点にしたいものは無いか」を尋ねる。ベースラインの計測はその後に来る。

  • 問題の集め先の優先順（公式）: 本番の記録 → バグ報告・サポートチケット → 人が手で書く数件 → コードベースから合成した問題（こちらが出した数件の実例を手本に作れる）
  • 採点役の選び方（公式）: 出力に合う一番安い方法を Claude が提案する。答えの形が限られていればプログラムで確かめ、何通りもあるなら LLM に採点させる
  • 公式は採点の失敗を eval の設定ミスの中で特によくあるものに挙げており、まさおは採点済みの記録を自分で何件か読む手間は省かないほうがよいと勧める

信頼できる試験の条件

公式ブログは頼りになる eval の条件を4つ挙げている（条件の一覧表は画像でソース本文に転記されておらず未収集）。本文から読めるのは次の点である。

  • 満点に余地を残す: 変更で性能が動いたかを判定できるようにするため。まさおは、余地を残しつつ強いモデルほど点が上がるように作るのは難しいと自身の経験を書く
  • 良い問題の目安（公式）: その分野の専門家2人が同じ判定になり、採点役が確かめることがすべて問題文に書かれている問題
  • 問題の選び方（公式）: 今のモデルが落とす問題だけを集めると、そのモデルの失敗の癖を測る試験になりかねない。人が難しいと判断した問題を選び、なぜ難しいかを言えるか確かめる。本番の記録も、ユーザーがうまくいきそうなことを試しがちなため易しい側に寄ることがある

過剰適合：試験の点だけ上がって本番が変わらない

よく設計した eval でも本番のタスク分布とは完全には一致せず、そのずれに合わせて直すと「本番より試験で良い成績を出すアプリ」になる。公式の例では、試験の問題は OCR があると有利なのに本番では OCR がほとんど役に立たず、改善を回すと OCR ツールが追加されて試験の点だけ上がる。プロンプトやツールなどモデル周りのコード（ハーネス）には、試験の癖が漏れる経路がたくさんあると公式は述べる。まさおも、動画台本を書かせるスキルに評価項目を増やし続けた結果、一見ルールを守っているのに全体で読むと機械っぽい台本になった経験を挙げている。

公式が挙げる防ぎ方は3つ。

  1. 問題を2つの束に分ける: 改善役が読める束を train、最後まで見せない束を test と呼ぶ
  2. 失敗の中身をプロンプトに写さない: 改善役が失敗の記録を読むのは構わないが、貼り付けて直すのは禁じ手
  3. 答えをモデルの手が届かない場所にしまう: モデルは答えそのものを探し当てて点を稼ぐことがある

見るべき合図は「train の点が上がったのに test が横ばいなら過剰適合を疑う」である。

hillclimb：隠した問題で伸びない直しは捨てる

/claude-api hillclimb はこの分け方を手順にしたコマンドだ。始める前に Claude は「性能を上げたいのか、性能を保ったまま費用を下げたいのか」を尋ね、問題を無作為に train と test に分ける。書き換えてよい場所は人が選び、候補はシステムプロンプト・スキルや指示ファイル・ツールの説明・モデルや effort の設定・ハーネスのコードである。

  • 1周で試す変更は1つだけ。まさおは、そのため点が動いたときに原因がその変更だと分かるのだろうと推測している。提案の中身も言い回しの調整でなく、原因になっている節の書き直しや足りないルールの追加だという
  • 全体の点が一番高い版がそのまま選ばれるわけではない。隠しておいた問題で伸びなかった直しは、数字が良く見えても捨てる。まさおの手元でも、両方上がる場合と train しか伸びない場合の両方が起きた
  • 点が2〜3周伸びないときは、直すのをやめて残った train の失敗を1件ずつ読み原因ごとに分類し、本当の失敗だけを次のラウンドに回す
  • 終了時は test が一番良かった版のコードが残り、結果はベースラインと比べて信頼区間つきで報告される。伸びがブレの範囲に収まるなら取り込まないよう勧める

最初に回す場所の選び方

公式が挙げる hillclimb の当て所の基準は、安く試せること・点の変化を変えた所に結びつけられること・目標を絞ることの3つ。まさおは、プロンプトやスキルのような文章は変えるのも戻すのも簡単なので最初の対象に向き、自前で仕組みを組む前に公式の2コマンドに乗るのが一番楽な入口だと勧める。build-eval には本番の記録などの実例を渡すと問題の作り方を方向づけられる。

余地を考えずに「性能を上げて」と頼むのはよくある失敗で、build-eval はベースラインがすでに約95%以上だと警告を出し、品質でなく費用か速さを狙うよう知らせる、と公式は説明する。

まさおは、Opus 5.5 なら誰でも高品質なものが出せて差がつきにくくなったが、評価をちゃんと作れているかどうかではまだ差がつくと見ている。
