# Stripe Minions

Stripe 社内のコーディングエージェント・パイプライン。人手で1行も書かないマシン生成のプルリクエストを**週1,300本超マージ**していると、Stripe エンジニアの Steve Kaliski がポッドキャスト How I AI で説明した。オープンソースのエージェントフレームワーク Goose のフォークであり、中核の主張は「**信頼性はモデルのサイズではなく制約の質から来る**」。

パイプラインは決定論的ステップと LLM ステップの交互配置になっている（Kaliski の説明の要約）:

1. **人間トリガー** — Slack で bot に@するか絵文字リアクションを付けるだけの軽い起動
2. **決定論的オーケストレーター** — モデルが起きる前に、リンクのスキャン・Jira チケットの取得・Sourcegraph と MCP による関連コードの特定まで、ルール化できる文脈収集をすべてコードが済ませる。LLM に自分で文脈を探させる部分が最も制御不能だから、そこをモデルの手から取り上げる
3. **LLM エージェント** — 材料の揃った状態でコードを書く
4. **ハードコードされたゲート** — リンターが必ず走り、エージェントはスキップできない
5. **LLM エージェント** — lint エラーを修正する
6. **ハードコードされたステップ** — git commit
7. **人間レビュー** — 週1,300本の PR は今も人間がレビューする

設計原則は一貫している: **決定論的ロジックで解けるものは、決して確率的モデルに渡さない**。その線をどこに引くかがループの信頼性を決める、と Kaliski は述べる。サンドボックスは EC2 上の Devbox を「ペットではなく家畜」方式で使い捨てにし、千体超のエージェントが衝突せずに同時稼働する。

人間は消えたのではなく席を移した——書く側からレビューする側へ。レビュー帯域が実質の上限になる構図は [[concepts/loop-engineering]] の指摘とも一致する。

## 問い

- 自分の wiki ingest パイプラインの決定論/AI境界（find_unprocessed.py や validate_wiki.py は決定論、カテゴリ判定・本文合成は AI）は、Minions の線引き基準「ルール化できるものは全部コードへ」に照らして最適か
- 週1,300本をレビューする人間側の仕組みはどうなっているか（サンプリングか分担か）。一次ソースである How I AI の該当回で確認したい
