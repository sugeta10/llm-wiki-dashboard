show-me（HumanLayer製Agent Skill）

TL;DR: エージェントの応答を散文の壁でなく、コンポーネント木・コールスタック・型シグネチャなど9種類の軽量な視覚表現で返させるAgent Skill。

flowchart LR
  P["設計の議論"] -->|/show-me| S["型・シグネチャ・コールスタックで形を合意"]
  S --> I["エージェントが実装"]
  I --> D["大きな差分"]
  D -->|/show-me| R["掘る箇所を絞ってレビュー"]

エージェントは指標の上では賢くなったのに、読める度合いではむしろ悪くなった——HumanLayer創業者のDex Horthyはそう書く。彼は「かつてClaudeが愛されていた声・人格・魂はRLの地下牢で洗い流された」と表現し、Solも多少ましだが専門用語の壁で目が滑る応答を日に何度も返してくる、と述べる。同じ不満は他の実践者にも広がっており、Dillon Mulroyは「直前の発言を言い直せ。専門用語をやめて筋の通った言葉で話せ。人間が人間に話すように、もっと簡潔に」とだけ書いた /bro スキルを作った。

show-meの提案は、言い直させることではなくモードを変えることにある。発想の下敷きはCoda Haleのインフラ論（intuition vs. attention）だとDex Horthyは述べる。情報を分析するのは難しく消耗するが、視覚野は何百万年もかけて豊かな視覚情報を無努力で処理するよう訓練されている、だから道具の側をそれに合わせろ、という主張である。彼は「斧が役に立つには人間の手に合っていなければならないように、ソフトウェアが役に立つには人間の心に合っていなければならない」という一文を引く。

彼がいちばん効くと言うのは、プログラム設計のフェーズである。最近は飛ばされがちだが本質的な工程だとして、エージェントがコードを書き始める前にコードの形（型・シグネチャ・コールスタック）を議論すべきだと主張する。同じ技法は事後にも使える。大きな差分を視覚表現に落とし、レビューでどこを掘るかを決める用途である。

収録されている9つの形式

形式 何に効くか
component trees フロントエンド。効いているstate hookとモジュール境界だけ残し、他は落とす
call stacks オーケストレーション・制御フロー・バックエンド形の問題。Dillon Mulroy発の形。TanishqはASTから直接算出するツールを書いた
diagrams チャットがインラインmermaidに対応していれば効く。HumanLayerは状態遷移図とシーケンス図を最も好む
file layouts 浅いファイル木に1行ずつ責務を書く。「これはどこにあるか」とリファクタの範囲決め
pseudocode アルゴリズム寄りの話題では擬似コードのほうが簡潔になる
types and signatures まだ存在しないコードの形。アーキテクチャ文書に書くには内部的すぎるが、エージェントは間違えうる部分
diff syntax 大半が変更なしのとき。コンポーネント・コール木・ファイル配置・状態/制御フローの変更を差分記法で示す
html mockups プロトタイピング。HumanLayerではFigmaの多くをHTMLが置き換えた
html diagrams 説明図。humanlayer上ではアシスタント応答にHTMLを直接埋められる。ブラウザで開くだけでもよい

Dex Horthyは、これらがHTMLより軽く速く、開発作業の形をした問題のほとんどには十分だと位置づける。mermaidの図は「ときどきslopになる」とも認めた上で、それでも言葉を読むよりましなことが多い、と書く。HTML explainerについては、Matt Pocockの /teach スキルが生成するものを良い先行例として挙げている（matt-pocock-skills）。

使い方

スキルを入れたあと /show-me を呼ぶか、show-meスキルを使うようエージェントに頼む。ルート・サービス・機能・プルリクエスト・今の話題のいずれかを指させばよい、と作者は説明する。単に「this is too much content. show me.」と投げる、あるいは「/show-me as an html explainer」と形式を指定する使い方も挙げられている。HumanLayer製品には同梱済みで、そちらの版はインラインHTMLと図を一級市民として扱う。他のコーディングエージェント向けには単体スキルとして配布されている。

問い

  • このvaultでも作業報告を散文でなく視覚表現で返させる価値はあるか。CLAUDE.mdのUC-2はHTML生成を明示指示時のみに制限しているが、show-meの主張は「HTMLより軽い表現なら日常的にやれ」である
  • 9形式のうち、file layouts と types and signatures は docs/DEVELOPING.md のコード地図と役割が重なる。ドキュメントに固定するのとその場で生成させるのはどちらが腐りにくいか
  • 図が slop になる境界はどこか。著者自身がmermaidの図を「ときどきslop」と認めている以上、生成させる前に形式を指定する判断が要る
