REA Prompts（REAP）— コーディングエージェントでソフトウェアを調べるプロンプト集

TL;DR: REA（Reverse Engineer Anything）というコーディングエージェント向け解析ツールに貼って使うプロンプト集。自分が所有・解析を許可されたソフトウェアを対象に、「1 プロンプト 1 機能」「主張ごとに証拠（ファイル・関数・アドレス）」「事実／推論／未知の分離」「静的解析から」「成果物で終える」という共通の骨格でエージェントに挙動を調べさせる。

REA 自体は rea.tools が配布するツールセットで、リポジトリの説明によればコーディングエージェントに接続し、ソフトウェアがどう動くかをエージェントに調べさせる。プロンプト集の作者 JoasASantos は、置き換え用の山括弧を埋め、1 回の依頼を 1 機能に絞ることを勧め、「狭い問いほど証拠に裏づけられた答えが返る」と書いている。REAP という名前は @zazencodes の命名で、リポジトリは codila の紹介スレッド（Matthew Berman を引用）を出典に挙げる。@C0d3Cr4zy は「REA Prompts」とだけ添えてこのリポジトリを紹介し、3,371 件保存された。

リポジトリは冒頭に責任ある利用の注意書きを置き、自分が所有するか明示的にテストを許可されたソフトウェアだけを対象にせよ、保護機構・脆弱性関連のプロンプトはセキュリティ研究・相互運用性・CTF・バグバウンティ・自社ソフトの防御テストのためのものだ、他者の所有物の保護を回避したり発見した脆弱性を悪用したりすれば法や利用規約に触れうる、と明記している。各プロンプトがエージェントに「確認された事実と仮説を分け、証拠を引け」と求めることを「譲れない点」としている。

収録範囲（目次の転記）

リポジトリの目次は 0〜16 の番号つきで、Install & verify / Getting started / Feature tracing / Native binary exploration / Software & feature cloning / Games / Game portability to WASM / Firmware & embedded / Android / Kernel analysis / Vulnerability research / Electron & JavaScript / Anti-cheat & protection research / DMA & hardware-assisted cheat research (defensive) / Software cracking research / Version comparison & crash work / Long-running investigations、加えて Wildcard prompt・Prompt-writing tips・Next steps の節からなる。保護機構・DMA・クラッキングの各節には、冒頭に「自分が所有する機器・自社ソフト・ベンダーのバグバウンティ・CTF・学術研究に範囲を限れ」という但し書きが付く。

各節は 1〜5 本のプロンプトからなる。たとえば Software & feature cloning はクリーンルーム方式（コードや素材でなく観察した振る舞いだけを抽出する）で CLONE_SPEC.md を書かせ、独自アセットで作り直すことを前提に置く。Long-running investigations は INVESTIGATION.md に所見・証拠・棄却した仮説・次の一手を残して再開する構成になっている。

プロンプトの共通骨格

リポジトリが「ここから始めよ」とするワイルドカードプロンプトは、対象アプリの 1 機能について「まず実際に使えるツールを確認する」「静的解析から始めて責任を持つ関数まで追う」「結論ごとに証拠を示し、事実と仮説を分け、限界を記録する」「最後に振る舞いの仕様を生成し、検証テストを提案する」の 4 段で書かれている。他のプロンプトもこの骨格の具体化で、節ごとに早合点を禁じる一文が添えられる。たとえば Android 向けは「文字列にドメインがあるだけでアクセスしていると結論するな」、クローン検証向けは「数例が通っただけで等価と見なすな」といった具合である。

書き方の 6 原則

リポジトリ末尾の「Prompt-writing tips」は、これらのプロンプトがなぜ効くかを 6 点にまとめている。

  1. 1 プロンプト 1 機能。「アプリ全体を説明して」のような広い問いは浅い地図しか返さず、狭い問いほど呼び出し連鎖やアドレスまで返る。
  2. 証拠を要求する。ファイル・関数・アドレスの引用を必須にすると、エージェントの作話を止められる。
  3. 事実／推論／未知を分ける。3 分類の形式が仮説を正直に保つ。
  4. 静的解析を先に。実際に実行観察が要るまで「アプリを実行するな」と言う。
  5. 成果物で終える。SPEC.md・リーダースクリプト・移植計画・最小の再実装など、具体的な成果物がエージェントに自分の主張を検証させる。
  6. 範囲を声に出す。「自分が所有するラボ機」「オフラインのシングルプレイヤー」「文書化せよ、回避するな」といった枠組みが、結果を研究・報告に使える形に保つ。

このvaultから見た接続

主張ごとに証拠（ファイル・関数・アドレス）を引かせ、確認された事実・推論・未知を分離させる骨格は、finding-unknowns の「事実と仮説を分ける」運用や、agent-trust-inverse-pyramid の「散文の指示でエージェントの判断を縛る」層と同じ発想と読める（wiki 側の解釈）。コードベースを俯瞰する目的では understand-anything が近いが、そちらは構造・依存の可視化、REA はバイナリやファームウェアまで含む動的・静的解析の対象が広い点が違う。

問い

  • この「証拠を引け・事実と仮説を分けろ・成果物で終えろ」という骨格は、REA を使わない通常のコード調査プロンプト（自分のリポジトリの挙動調査）にも流用できるか
  • finding-unknowns の「ブラインドスポットパス」と、REA の「まず使えるツールを確認してから静的解析」はどちらも調査の入口設計だが、何が違うか
