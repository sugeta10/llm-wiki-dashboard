Elephant-Goldfish Model（EGM・設計を「象」に書かせ「金魚」に審査させる Google 製プラグイン）

TL;DR: コードを書く前に、文脈を全部持つ AI セッション（象）と設計ドキュメントを作り、会話履歴を一切持たない新規セッション（金魚）に「説明し直せるか・穴はないか・このまま実装できるか」を審査させる開発手法と、それをスキル 7 本・レビュアーペルソナ 9 本として Antigravity・Claude Code・Codex に入れる Google のオープンソースプラグイン（Apache 2.0・2026-10-21 公開）。

  B["egm-brainstorm<br/>象と議論（コード禁止）"] --> CB[concepts_brief.md]
  CB --> D["egm-draft<br/>設計ドキュメント起草"]
  D --> DD[design_draft.md]
  DD --> R["egm-review<br/>金魚 5 段審査"]
  R --> RS["egm-resolve<br/>指摘の処理"]
  RS -->|再審査| R
  RS -->|人間が承認| I["実装（通常のコーディング）"]
  I --> DR["egm-drift-report<br/>文書と実コードの乖離検査"]

提唱者の Dave Rensin（Google のエンジニア。EGM の原典エッセイの著者）は、AI でコードを書く速度が上がると「速く書いている」のではなく「自分の間違いを量産している」状態に陥りうると述べる。生成される悪いコードの割合が良いコードを上回れば、プロジェクトは読めず保守できないスロップの重みで崩れる、というのが Rensin の問題設定である。Rensin はこの経験から 3 つの気づきを挙げる。進捗と意図を書いた文書があればセッションが落ちても 30 秒で復帰できること、AI は喜ばせたがるので厳しいガードレールなしに走らせると崖から飛び降りること、そして「sizeof(docs) << sizeof(code)」、つまり AI にシステムを理解させるには何万行のコードより平易な英語の設計文書を渡すほうが安く速く確実だということである。

Rensin は人間がコードを書かなくなると設計上の微細な判断がコードに残らなくなるため、判断をコードより前の設計文書へ「左に寄せる」必要があると主張し、これを「Design is the new code（設計が新しいコードである）」と言い切る。象と金魚の比喩はこの文書を検査するための仕掛けで、Rensin の原則は「象に食わせ、金魚で試す」の一文に要約される。

役割 持っている文脈 責任
象（Elephant） プロジェクト・要件・これまでの決定 問題を探索し、仕様を起草する
金魚（Goldfish） 文書と、文書が参照するソースだけ。会話履歴は無い 言外の前提・不明瞭な要件・実装リスクを見つける
あなた 本当に重要な目標と制約 トレードオフを決め、設計を承認し、何を作るか決める

（役割表は README の記載を転記）

README は「機能に設計判断が要るときに使い、小さく明確なバグ修正なら通常のワークフローでよい」と用途を限定している。金魚の審査は新規コンテキストのサブエージェントを前提とし、ハーネスがそれを作れなければ EGM は審査を止める。README は「レビューはテストと人間の判断を代替しない」とも明記する。

原典の手順（Rensin のエッセイ・2026 年 4 月執筆）

Rensin は原典で、機能 1 つごとに 4 フェーズ 9 ステップを回すと書く。フェーズ 1「象を育てる」は、関連文書とソースを読ませて理解を要約させ（ステップ 1）、「コードを作るな。設計の議論をする。私の前提を疑え」と命じて 20〜30 分、ときに 2〜3 日議論し（ステップ 2）、モデルが「素晴らしい考えです」と言い始めたら「同意は役に立たない。私の思考に挑むのが最高の使い道だ」と批評モードへ戻し（ステップ 3）、最初の設計案は人間でなく AI に散文とブロック図で出させる（ステップ 4）。AI に先に提案させる理由を Rensin は「人間が案を出して反応を求めると、ほぼ確実に盲点を見逃す」と説明する。

フェーズ 2「象に教える」は設計文書を 1 セクションずつ書かせる。順序は問題（3〜5 文）、技術計画（専門用語を減らした散文とブロック図）、却下した代替案（将来の幻覚と議論への防波堤になる）、詳細実装（作成・変更する全ファイルと理由の列挙）で、Rensin は一括生成を禁じ、全ファイル列挙を「これが AI を線路に乗せ続ける」と最重要視する。

フェーズ 3「金魚プロトコル」が審査で、新規セッションを 3 回立てる。理解テスト（文書と参照ファイルだけで何を達成するか説明できるか。できなければ文脈不足なので足して繰り返す）、批評レビュー（見落とし・誤った前提・エッジケースを全部挙げさせる。Rensin の体感では提案の約 3 割が高価値）、実装準備（初回で実装し切るのに必要な情報が全部あるか問い、質問が出たら文書に答えを書く）の順で、最後に人間のレビューを受ける。フェーズ 4 で初めてコードを書き、「文書どおり正確に実装せよ」と渡す。コードが出たら「このコードは質が低いと強く疑っている。ずたずたに切り刻んで悪い点を全部挙げろ」と自分の実際のプロンプトで批評させ、10 行コメントなしの箇所を指摘させる、と Rensin は書く。

既存の巨大コードベースへは、葉のディレクトリから README.md を AI に生成させ人間が 5〜10 分で直し、1 段ずつ上へ巻き上げる「ピーナッツと干し草」方式で約 1 週間あれば象を育てられると Rensin は主張する。全ファイルがいずれかの設計文書から参照されたら README は消してよい、ともある。

Rensin の同僚向けの見立ても原典にある。README 階層と設計文書があれば新任者は NotebookLM に入れて最初の機能の設計文書を書くことで参画でき、プロダクトマネージャーなどコードを少し書ける非エンジニアから届く設計文書は「たいてい 7〜8 割正しく、1〜2 往復で基準に達する」と Rensin は述べる。

プラグインの構成（README と harnesses.md）

リポジトリは 2026-09-13 に作られ、Rensin はエッセイ冒頭の追記で「2026-10-21、Google が社内でこの手法に使っているプラグインのオープンソース化を許可した」と書いている。README は「数千人の Google エンジニアが EGM を使っている」と述べる（Google 側の自己申告）。ライセンスは Apache 2.0 で、フッターに「Google の公式サポート製品ではない」とある。

スキル 用途（README の記載）
egm-brainstorm アイデアを試し、コンセプトブリーフを書く
egm-draft ブリーフや既存メモを設計文書にする
egm-resolve レビュー指摘を処理し、変更に合意する
egm-bootstrap 既存コードベースの文書を作る・更新する
egm-review 新規エージェントで設計を 5 段階レビューする
egm-review-loop 設定したレビュアー群を特定の審査に回す
egm-drift-report チェックインされた文書と現在のソースを比較する

egm-review の 5 段階は、スキル定義の説明文によれば初回ズームアウト、理解、設計批評、中間ズームアウト、実装準備の順で、レビュアーペルソナは agents/ に 9 本（bootstrap_orchestrator・codebase_details・comprehension・design_critic・implementation_readiness・structural・style・synthesizer・zoom_out）置かれている。各ペルソナは読み取り専用ツールと文脈隔離で動き、ハーネスにサブエージェント機能が無ければ「同一文脈のレビューは金魚レビューではない」と告げて止まる、とスキル定義にある。

egm-review の実行制約も特徴的で、提案や下書きをチャットに出さずファイルに書いてパスを伝えること、「シームレス」「堅牢」のような根拠のない宣伝形容詞と装飾副詞の禁止、既定で同意せず弱点から述べること、「素晴らしい」「完璧」などの肯定形容詞と謝罪の禁止、対話ゲートは 1 ターンに 1 問だけ、と列挙されている。原典の「同意は役に立たない」をプロンプト規約へ落とし込んだものと読める。

対応ハーネスは Antigravity（CLI・App・IDE 拡張）、Claude Code、Claude Cowork、Codex、ChatGPT、omp で、harnesses.md は Antigravity・Claude Code・Codex がインストール・レビュアー隔離・一気通貫の自動試験を通過し、Cowork と ChatGPT Work は導入経路はあるがクラウド側の検証に未了があると書く。Antigravity IDE の単体版は新規文脈サブエージェントのツールを公開していないため非対応。スキルだけをコピーする導入は agents/ と文書標準を読めず壊れるので、プラグイン全体を入れよ、とも注意している。

Brady Long のまとめと一次ソースとの差分

今回のソースは @thisguyknowsai（Brady Long。自己紹介で「AI が好きなだけで専門家ではない」と書く個人アカウント）の X 長文で、EGM の流れを「コードは計画が生き残るまで書かない。AI に自分の宿題を採点させない。機能の途中で文脈が崩壊しない」と要約し、ブレインストーム・起草・金魚による説明し直し・複数の敵対レビュー・go/no-go 判定の 5 手順を挙げている。README と突き合わせると次の 2 点がずれる。

  • Long は「いまは Antigravity の中でしか動かない」と書くが、README と harnesses.md は Claude Code と Codex のインストールコマンドを載せ、両者が自動試験を通過したとしている。投稿時点の README が古かったか、Long の読み違いと考えられる（推論）
  • Long の「セキュリティは既定のレビュアーに無いので自分で足せ」は agents/ の 9 本にセキュリティ担当が無いことと整合する

Long の「金魚はあなたの設計会話を見ていないので、その盲点を継承しない」という一文は、原典の「象の文脈に頼って文書が良く見えているだけではないか」を検査するという動機を正しく言い換えている。

他ページとの位置づけ（wiki 側の推論）

compound-engineering も brainstorm→plan→review の順で計画に重心を置くが、EGM の差分はレビュアーを「文脈ゼロ」に固定する点にある。llm-council が匿名化で権威バイアスを消すのに対し、EGM は会話履歴そのものを消して同意バイアスの発生源を断つ。superpowers の brainstorming→writing-plans と同じ「実装前に文書」の系譜で、原典の理解テスト（文書だけで説明し直せるか）は cognitive-debt の「説明できないものは出さない」を AI 側に適用したものと読める。Rensin が「迎合の渦」と呼ぶ現象は 2023-sharma-sycophancy が測定した迎合で、EGM はそれをプロンプト規約と文脈隔離の二重で抑えている。

問い

  • このvaultの wiki-ingest や weekly 生成に「金魚」を置けるか。生成したページを文脈ゼロのサブエージェントに読ませ「ソースを見ずに何を主張しているか説明できるか」を通すと、帰属の曖昧さや造語がどれだけ落ちるか
  • 原典の 3 回の金魚（理解・批評・実装準備）がプラグインでは 5 段階 9 ペルソナに増えている。増えた分（ズームアウト 2 回・structural・style）は指摘の質を上げるのか、それとも ai-review-bottleneck の言う「読んで直す工程」を膨らませるだけか
  • Rensin の「全ファイル列挙」は spec-driven-development の仕様の粒度としてどこまで要るか。Fable 世代の長いタスクで、列挙の硬さが逆に設計変更を妨げないか
