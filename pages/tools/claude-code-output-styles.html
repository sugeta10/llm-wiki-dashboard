Claude Code の出力スタイル：pstack の /bro を常時適用する（uehaj）

TL;DR: pstack の /bro スキル（直前の返答を専門用語なしで言い直させる）を毎回打つ代わりに、~/.claude/output-styles/bro.md という Markdown 1枚で出力スタイルにすると最初から平たい返答になる。uehaj は「短く」だけだと判断に要る数字や依頼が削られ、コードやパスまで言い換えられるので、「中身は落とさない」「コードはそのまま」の2項を足し、keep-coding-instructions: true で普段のコーディング指示を残した。

出力スタイルは Claude Code の返事の書き方を決める指示をファイルに書いて選べるようにする仕組みで、組み込みには Concise（簡潔）や Explanatory（説明多め）などがある。claude-code-instruction-methods の整理では、7つの指示手段のうち開始時にシステムプロンプトへ注入され圧縮されず権威が高い手段にあたり、既定ではソフトウェアエンジニア支援の役割ごと置き換えてしまうので keep-coding-instructions: true で回避する、と公式が注意している。uehaj（@uehaj・「意味で探す grep、sys1grep」の作者と名乗る AI エンジニア）の X 記事は、この仕組みを「言い直しを何度も頼んでいる」状態への答えとして使った実例である。

/bro というスキル

pstack に含まれる /bro スキルの中身は、uehaj の転記によれば次の1文だけである。

直前のメッセージを言い直して。専門用語をやめて、筋の通った話し方で。もっと簡単に短く、人が人に話すように。

uehaj は pstack の中でこれを一番多用していると書き、Claude Code の出力が見違えて分かりやすくなるので通常の出力スタイルにしたくなった、と動機を述べる。組み込みの Concise は縮めるだけで /bro ほど平明にはならない、というのが uehaj の比較である。

出力スタイルにする手順

~/.claude/output-styles/ にスタイル名の Markdown を1つ置くだけで自作スタイルになる。記事のファイルはこの内容である（転記）。

---
name: bro
description: 返答をはじめから平たく書く。/bro で言い直させる手間を省く
keep-coding-instructions: true
---

すべての返答を、はじめから次のように書く。

- 人が人に話すように書く。専門用語や略語は、普通の言葉に置き換える。
  置き換えられないものは、初めて出たところで一言で説明する。
- 短く書く。1 文に 1 つのことだけを言う。結論を先に言う。
- 筋を通す。前の文とのつながりが分かるように書く。
- 中身は落とさない。判断に必要な事実や数字、相手に頼むことを省かない。
- コード、コマンド、ファイルのパス、識別子は、そのままの形で書く。

作成後は /output-style の一覧に bro が出て、/output-style bro で切り替わる。

/bro の文面に足した2項と、残した設定

/bro の文をそのまま写すと困ることが2つあった、と uehaj は書く。

  1. 中身が落ちる。「短く」と言うと、判断に必要な数字やこちらへの依頼まで削られることがある。そこで「中身は落とさない」を足した。短くするのは言い方であって情報ではない、というのが uehaj の線引きである
  2. コードまで平たくされる。ファイルのパスやコマンドを言い換えられるとそのまま使えない。そこで「コードやパスはそのまま」を足した。平たくするのは説明の文だけである

加えて keep-coding-instructions: true を付けている。これがないとコードを書くときの普段の決まりが外れるので、書き方だけを変えて仕事の仕方は変えないためだと uehaj は説明する。これは claude-code-instruction-methods が転記した公式の注意（出力スタイルは既定のシステムプロンプトを置き換える）を、実運用で踏んだ側からの確認にあたる。

記事のまとめは3点で、「言い直して」と何度も頼んでいるなら出力スタイルにする合図であること、出力スタイルは Markdown 1枚で作れること、「短く」だけだと中身が削られるので「中身は落とさない」「コードはそのまま」を一緒に書くこと、である。

既存ページとの関係（wiki 側の推論）

  • 毎回のスラッシュコマンドを常時適用の設定に昇格させる判断は、claude-code-instruction-methods の「どの手段に置くか」の表で言えば、Skills（起動時にだけ効く）から Output styles（開始時に注入され圧縮されない）への移し替えにあたる。uehaj の2項の追加は、権威の高い層に置くほど副作用（情報の欠落・コードの言い換え）が全返答に及ぶことの裏返しと読める
  • lean-prompt-rules-adaptation は output style では止まらなかった「進め方」の癖があったと報告する。本記事が変えているのは進め方でなく文体なので、出力スタイルが効く範囲の内側にあると考えられる
  • このvault の CLAUDE.md「文章スタイル」（括弧は文末・用語には一言添える）や kuden-writing の心得は文の構造を定める規範で、/bro の「専門用語をやめて人が人に話すように」は語彙の層を定める規範である。両者は対象が違うので併用できると考えられる

問い

  • keep-coding-instructions: true で残る「普段の決まり」の範囲は公式ドキュメントで確認していない。自作スタイルの文面と衝突したときどちらが勝つか
  • この output style を入れたまま長いセッションを回すと、/bro を都度打つ運用と比べて「中身は落とさない」がどこまで守られるか。uehaj の記事は導入直後の印象で、長期の実測はない
  • このvault で返答の平明さを上げたいなら、output style でなく append-system-prompt に同じ5項を足す方が claude-code-instruction-methods の「スタイル変更を避ける」線引きに合うか
