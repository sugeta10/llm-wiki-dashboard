OpenAI Codex

OpenAI が提供するコード生成・エージェント実行プラットフォーム。claude-code の競合にあたる。

Codex App Server

Codex CLI および API を使ったアプリケーション販売の可否について OpenAI に3往復確認した事例（@akira_papa_IT, 2026-05）：

  • 商用利用は可能: Codex API を使ったアプリの有料販売は利用規約上許可されている
  • ただし条件あり: OpenAI のブランド表記・利用規約への同意・API利用料の負担
  • Codex App Server 経由でエンドユーザーにアプリを提供するモデルが現実的

Claude Code との比較

Claude Code OpenAI Codex
形態 CLI / API CLI / API
強み エージェント自律性・スキル拡張 コード補完精度・GitHub統合

X投稿の自己改善ループへの活用

@super_bonochin による実験（2026年5月）。Codex を毎回のX投稿ワークフローに組み込む試み：

  1. 投稿者が雑に喋った内容をCodexが本人らしい文体で作文する
  2. 投稿者が修正・ポスト
  3. ポストごとに Codex へ「自分の提案の何がダメで、どうすべきだったか」を分析させる

スライド画像生成のCodexスキル実例は image2-brand-slides を参照。

継続使用によりCodexが発信者のスタイル・批評を学習していく設計。self-refining-skills と同様のself-refinement ループをコンテンツ生成に適用した事例。

Codex最適化プロンプト（繰り返し作業の4分類）

OpenAI社員のCodex開発者がポストした、繰り返し作業を洗い出して自動化分類するプロンプト（@tetumemo紹介, 2026-05-25）。AIが「探偵」として動き、以下の4分類に整理する：

  • Skill — 再利用可能な手順としてパッケージ化できる作業
  • Subagent — 独立したサブエージェントに委譲できる作業
  • Automation — 完全自動化可能な作業
  • Skip — AIに任せる必要のない作業

Codex × Hermes Agent連携

@tetumemo による実験（2026-05-25）。コストパフォーマンスの高い自動化パイプライン：

  1. Codex → Hermes Agent呼び出し
  2. x_search（X検索）→ 要約
  3. Codex × GPT-Image-2 で画像化
  4. 画像を Hermes Agent に投げて音声付き動画化

hermes-agent との連携で、テキスト→画像→動画の全工程を自動化できる事例。

Codexによるスレッド自己管理（2026-05）

@guinnesschen（OpenAI Codexチーム）による機能発表。これまで人間が手で管理していたCodexのスレッド（会話）を、Codex自身がメタ操作できるようになった：

  • スレッド作成・検索・整理 — Codexが自分の過去スレッドを検索し、トピック別に整理する
  • 重要スレッドのピン留め — 後で参照する会話を固定
  • worktree起動による並列タスク — 複数タスクを git worktree 上で並行して回す

エージェントが「実行」だけでなく自身の作業環境（スレッド・ブランチ）の管理まで担うようになった点が新しい。claude-code-work-folder が人間側で棚を用意する発想なのに対し、こちらはエージェントが棚自体を運用する方向。worktree並列は claude-code-subagents のサブエージェント並列と同じ「複数作業の同時進行」を、IDE/CLI側のブランチ分離で実現している。

Codex Sites（2026-06）

@OpenAI 公式発表（2026-06-02）。Codex に Sites 機能が追加された：

  • Codex が「仕事・アイデア・計画」を、チームが探索・利用・URL共有できるインタラクティブなWebサイト/アプリに変換する
  • まず Business / Enterprise プランへロールアウトし、その後より広く展開予定

エージェントが「コードを書く」段階から「成果物を共有可能なアプリとして出力する」段階へ広がった動き。アプリ販売の可否を整理した上記「Codex App Server」の議論と地続きで、Codexを成果物配信プラットフォーム化する方向性を示す。

Build iOS Apps プラグイン（2026-06）

@OpenAIDevs 公式発表（2026-06-04）。iOSアプリ開発ループを Codex 内で完結させるプラグイン：

  • アプリ内ブラウザで iOS アプリを閲覧・テストできる
  • SwiftUI プレビューを開く
  • Codex から離れずに編集をホットリロードする

「コードを書く」だけでなく、ビルド→プレビュー→テストの反復をエージェント環境内に取り込む動き。前述「Codex Sites」（成果物のWeb化）と並び、Codexを単なる生成器から開発ループ全体のランタイムへ拡張する方向の一例。

Codex /goal の進捗可視化（2026-06）

@gosrum による運用改善。Codex の /goal コマンドで「現在何%進んだか」が見えない問題を、goalプロンプトに以下のTODO管理ルールを含めることで解決した:

  • 作業開始時に、goalを実現するためのTODOリストをチェックリスト形式で作成する
  • TODOは「未着手 / 進行中 / 完了 / 保留」が分かる形で管理する

心理的負担が大幅に減る実感があるという報告。harness-engineering のセッション初期化ルーティン（7ステップ起動）と同じ「エージェントに現在地を明示する」アプローチ。

プロダクト構成と導入（非エンジニア向け整理）

Codex は単一アプリではなく、同じコーディングエージェントが6つの入り口（サーフェス）で動く製品ファミリーとして提供される。最も摩擦が少ないのは Codex App。重要なのは、Codex が ChatGPT の有料プラン（Plus、月20ドル）に含まれており、追加費用ゼロで使える点。Free プランでも試せるが、本格的に業務で使うなら Plus 以上が現実ラインになる。

  • モバイル操作: 2026-05-14 に追加。PC で動かしている Codex をスマホから操作できる。
  • 権限モードは3段階: 「デフォルトの権限」「自動レビュー」「フルアクセス」。フルアクセスは Codex が自分の判断で何でも実行できてしまい事故が起きやすいため、最初はデフォルトから始めて慣れてから上げるのが安全な順序。
  • 画像生成（GPT Image 2）: Codex 内から $imagegen で OpenAI の画像生成モデル GPT Image 2 を呼べる。API 単体だと1枚約20円かかるところを ChatGPT 契約の範囲で使えるため、資料・サムネ・SNS 画像に流用できる。スライド画像生成スキルの実例は image2-brand-slides を参照。

モデル構成（2026-06 時点）

Codex のモデルセレクタで選べる構成。既定は GPT-5.5（2026-06-14 時点）、フラッグシップが GPT-5.4、高速版が GPT-5.4-mini、ChatGPT Pro 限定の研究プレビューが高速反復特化の GPT-5.3-codex-spark。旧 GPT-5.2 と GPT-5.3-codex は 2026-06-02 にサンセット済み。GPT-5.5 はトークン消費を抑えつつ出力が速く、「ファストモード」でさらに体感速度が上がる。じっくり考えさせるなら claude-code、速く回したいなら Codex、というのが使い分けの目安。

Migrate to Codex（2026-06-09）

OpenAI 公式の移行機能。claude-code の設定をほぼワンクリックで Codex 側へ移せる。後述の「2本目のエンジン」戦略を取りやすくする公式の後押しにあたる。

「2本目のエンジン」戦略（SPOF回避）

単一の AI エージェントに業務を全部預けることは、そのまま単一障害点（SPOF: single point of failure、一箇所が止まると全体が止まる構造）を抱えることを意味する——というのが株式会社デジライズ代表のチャエン（茶圓）の主張。結論は「Claude Code か Codex か」の二者択一ではなく、両方を平時から温めておく（warm に保つ）こと。すでに払っている ChatGPT 月20ドルに眠る Codex が、最もコスパのよい2本目のエンジンになる。

ポイントは、Codex を「コードを書く道具」に限定しないこと。資料作成・Excel・画像生成・オートメーション・Codex Sites・スマホ操作まで一通り使える状態にしておけば、Claude Code がレート制限や障害で詰まっても、その日の仕事をそのまま Codex で回せる。claude-usage-optimization（レートリミット回避・モデルスタッキング）や llm-model-selection-strategy（工程分解型のモデル選択）と地続きの、可用性をリスク管理として設計する発想。
