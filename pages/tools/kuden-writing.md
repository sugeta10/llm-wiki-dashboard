# 文章を書く時の心得スキル（shokai の kuden/writing）

> **TL;DR**: 「効く」「正本」のような語を言い換えるより、解釈のブレが起きない文の構造を直せ、という shokai の主張と、その実装にあたる kuden プラグインの writing スキル。5つの心得は語を1つも禁じず、述語の選び方・節の完結・括弧・強調記号・表記だけを定める。

AI が書く日本語を直す試みの多くは、避けるべき語の一覧として実装されている。「効く」は [[tools/japanese-tech-writing]] の「翻訳調の比喩と擬人化の禁止」節が研究者の話し言葉として禁じる例に入り、[[concepts/llm-japanese-style-hooks]] では500本超の NG ルールの検出上位に挙がる。shokai は X への投稿で、こうした語を「言葉尻」と呼び、「もっと気にする事あるだろ」と書いて自作スキルの SKILL.md へのリンクを添えた。投稿本文はこの1文だけで、どの規範やツールを念頭に置いたかは名指ししていない。語彙リスト型の規範への反論として読めるが、これは wiki 側の推論である。

shokai は GitHub プロフィールで Helpfeel Inc. 所属、wiki サービス Cosense の開発者と自己紹介している。GitHub アカウントの twitter_username が shokai で、投稿者と同一人物である。

## kuden プラグインの中の1スキル

writing スキルは、shokai が公開する Claude Code 用プラグイン kuden の9スキルのうちの1つである。README で shokai は kuden を、AI との作業で重ねてきた失敗と成功の memory から抽出した心得を集めたガイドライン群と説明し、AI が必要だと判断した時に読み込み、手動でも起動できると書く。9スキルの対象は README の記述では次のとおり。

| スキル | 対象 |
|---|---|
| common-rules-for-agent-instructions | AI が読んで従う文書に共通の、読み手の前提・何を書かないか・編集の仕方・レビュー指摘の採否の基準 |
| agent-skill | SKILL.md に何を書き、何を書かないかの判断基準 |
| persistent-instructions | CLAUDE.md や AGENTS.md に何を書き、何を書かないか・制約の文体・置き場所 |
| code-comment | ソースコード中のコメントに何を書き、何を書かないか・置く位置・日本語の文体 |
| writing | コメント・PR 概要欄・ドキュメント・wiki のどこでも変わらない、解釈のブレを起こさない文の書き方と、強調記号とカッコ書きの扱い |
| github | PR のタイトルと概要欄・壊れないリンク・親子 PR・レビュー指摘への対応・squash and merge のコミットメッセージ |
| software-test | 何を test し何を test しないか・アクセス権限の test・fixture の仮名・落ちた test の直し方 |
| orchestrator | subagent に任せる指揮役の心得。報告の確かめ方・進み具合・止まった subagent・利用上限 |
| user-decision | ユーザーの判断を得る時の説明と訊き方・auto mode の分類器に止められた時の許可の求め方 |

導入はマーケットプレイス登録とプラグインのインストールの2手順で、起動は `/kuden:writing` のようにプラグイン名を前置する。

```bash
/plugin marketplace add shokai/agent-skills
/plugin install kuden
```

SKILL.md の description では、ソースコードのコメント・PR 概要欄・ドキュメント・wiki を書く時、直す時、レビューする時に読み込む、と発火条件を書く。書く場所が変わっても基準は変わらない、というのがこのスキルの前提である。

## 心得1. 解釈のブレが発生しない文を書く

shokai が最初に置くのは、読み手によって意味が分かれない文の書き方で、5つの規則からなる。

- 良くない事は、良くない事だと分かる述語で書く。「pattern が遅くなっても落ちない」は良い事のようにも読めるので、失われる働きを述語にして「pattern が遅くなった事を検知できない」と書く
- 目的は完全な節で言い切る。「〜できるよう」「〜で使うため」と書き、「〜用に、」のような体言止めの断片にしない
- 目的の述語を曖昧な語にしない。「highlight が当たるよう、X を保持する」ではなく「highlight を判定できるよう、X を保持する」と書く。「当たる」では何が成立する事なのかを言い切れていない
- 理由の後に2つの事柄を「〜し、〜する」でつなぐと、理由がどちらにかかるか曖昧になる
- 文を他所から写す時は、貼り付け先の前後の文脈に合うか確かめ、書いた後に読み直す。元の文脈を前提にした省略は、貼り付け先では意味が通らない

4つは文の組み立ての規則で、最後の1つは写した文の扱いである。語の良し悪しではなく、述語が何を言い切っているか、節が完結しているか、修飾がどこに掛かるかを見る。

## 心得2. 強調記号で重要性を示さず、文を推敲する

太字などの強調記号で重要性を表現しない。重要なら、語彙・断言の強さ・文の位置で伝わるように文そのものを推敲する、と shokai は書く。鹿野桂一郎の規範が「演出の抑制」の中で太字強調を制限するのと同じ対象を、こちらは全面的に使わない側に倒している。

## 心得3. カッコ書きで補足説明しない

丸括弧で補足を挿入すると文の構造が曖昧になり読みにくくなる、として、補足の種類ごとに置き場所を変える。

- 親の項目の詳細や判断基準なら、子リストで展開する
- 背景や理由なら、文を分けて続ける
- 括弧の中身を先に述べてから本題に入るなど、文の順序を変える
- 文意を裏返しただけの括弧注記は削る。「実際に書かれた表記を保持する(正規化後ではない)」の括弧の中は、前半が言えた時点で自明である

[[concepts/ai-japanese-writing-stack]] が書く前の削りで「削除しても判断に影響しない括弧の補足は取り除く」と置くのと対象が重なる。shokai は削るだけでなく、残す補足の行き先を3通り示している。

## 心得4. 和文と英字の間に空白を入れない

和文と英字やコードの識別子との間に空白を入れない。`Modal を <dialog> に` ではなく `Modalを<dialog>に` と書く。`react-bootstrap Modal` のような英単語同士の空白は残し、Markdown の inline code の前後の空白はこの規則の対象外とする。

## 心得5. URL で終わる行の末尾に句点を付けない

`起点は <URL>` のように URL で終わる行の末尾に句点を付けない。URL の直後の句点は、リンクの一部として解釈される可能性があるための規則と考えられるが、SKILL.md は理由を書いていない。

## 語彙リスト型の規範との関係

5つの心得のうち、心得1から3は文の構造の規則で、心得4と5は表記の規則である。避けるべき語の一覧はどこにもない。鹿野の規範が10カテゴリのうち2つを語彙の禁止に充て、@yugen_matuni の Hook が語を正規表現で照合し、[[concepts/writing-norms-adoption]] が「AIっぽさの6つの型」を語の列挙で示すのに対し、このスキルは述語・節・修飾の掛かり方という、正規表現では検出しにくい層だけを扱う。

ただし両者は排他ではないと考えられる。@yugen_matuni は語を検出しても修正単位は文にし、語の置き換えだけを禁じている。鹿野の規範も「演出の抑制」「読み手の負荷の管理」で構造側の規則を持つ。shokai の投稿は、語の一覧から入る規範が構造の規則を後回しにする点に向けられた、優先順位の主張と読める。

## 問い

- 心得1の「失われる働きを述語にする」は正規表現では検出できない。[[concepts/llm-japanese-style-hooks]] の文書全体集計のような機械検査に載せられるか、それとも reviewer エージェントか人が読むしかないか
- このvault の CLAUDE.md「文章スタイル」は括弧を文末に置く規則で、shokai は括弧を使わず構造を変える規則である。wiki ページの読み手の負荷を下げるのはどちらか、同じ段落で書き比べられるか
- このvault では「正本」を定義済みの術語として使っている。shokai の言う言葉尻としての「正本」と、定義済み術語としての使用は区別できるか
