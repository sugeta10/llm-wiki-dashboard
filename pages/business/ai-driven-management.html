AI駆動経営の概念設計（人が判断し、AIが実行する基盤）

TL;DR: 経営を「目標・プロジェクト・資源」の3軸で管理し、目標→プロジェクト→WBS→AI実行→成果物の検証→事業成果の評価を一つの循環にする、@yoshio_nocode の「AI駆動経営 概念設計 v0.2」。人は判断と例外対応に集中し、日々開く窓口はチャットとプロジェクト・タスク管理の2つに集約する。タスクの完了と事業上の成果は別の事象として記録する。

@yoshio_nocode は多くの AI 支援をしてきた経験から「個人的に一番良いと思う」スキームとしてこの4枚のスライド（概念設計 v0.2）を整理したと述べる。本文はスライド画像を wiki 側で読み取って転記したもので、ポスト本文は3文のみである。設計の出発点は「人が判断し、AI が実行する」で、オーケストレーターが管理情報・専門 AI・会社のデータをつなぐ。人（複数）は判断・合意・承認など人ならではの意思決定と例外対応に集中する。

全体像：6つの層

スライドは基盤を次の層で描く（製品名はスライドに並んだ例）。

層 役割 例
チャット 協議・依頼・承認 Slack・Chatwork・Teams
プロジェクト・タスク管理 目標・WBS・進捗・依存関係 Notion・Linear・Asana
会社のデータ 知識・判断履歴・成果物（議事録・顧客情報・ドキュメント） Google Drive・Dropbox
オーケストレーター 可視化・調整・判断支援（状況集約・依頼振り分け・進行監視・権限制御） OpenClaw・Hermes Agent・Codex・Claude Code
専門 AI エージェント 実行・検証（調査・文書作成・実装・テスト） Codex・Claude Code
業務ツール 会計・決済・資料作成など freee・Stripe・PowerPoint

人はチャットとプロジェクト・タスク管理の2層にだけ触れ、オーケストレーターがその下で会社のデータと専門 AI エージェントをつなぐ。オーケストレーターと専門 AI の両方に Codex と Claude Code が置かれているのは、同じ製品が指揮役と実行役のどちらにもなる構成を示している（openclaw・hermes-agent は指揮役の側にのみ置かれている）。

人が日々開く窓口は2つに集約する

スライドは「画面を減らしても、判断のための見える化は残す」と書く。

  • チャット（協議・合意・依頼）: 人同士で論点を詰める、AI に調査や実行を頼む、変更・例外・承認を判断する。扱うのは状況共有・依頼・承認・差戻し。
  • プロジェクト・タスク管理（共通の状態・根拠）: 目標と指標の予実を見る、WBS・工程・依存関係を見る、資源の余力と判断待ちを見る。扱うのは KPI・担当・期限・ボトルネック。

会話→決定→計画・WBS→実行・検証を、同じ対象と履歴でつなぐ。チャットで決めたことが計画に落ち、実行結果が同じ対象に戻ってくる構造である。

経営の中核は目標・プロジェクト・資源

営業や経理などの業務領域に共通する3つの管理軸を置き、それぞれで人が決めることと AI が担うことを分ける（スライドの表を転記）。

管理軸 例 人が決めること AI が担うこと
目標管理 売上・応答時間・継続率 何を・なぜ・いつまでに達成するか（目的・優先順位・評価指標を設定する） 差分・予測・施策案を整理し成果を追う（実績とのギャップ分析・リスク予測・施策の提案・効果測定）
プロジェクト管理 FAQ 整備・営業資料更新・開発案件 何を作り、どの条件で完了とするか（スコープ・成果物・完了条件・関係者を決める） 計画・WBS 化・実行・検証・改善まで進める（計画立案・タスク分解・進捗管理・リスク対応・成果検証・改善提案）
資源管理 人員・予算・AI 利用枠・データ権限 何を、どこへ、どれだけ投入するか（人・予算・ツール・データの配分方針を決める） 配分・確保・消費・解放と不足の予測を行う（最適配分・需給予測・利用状況の可視化・不足時の代替案）

スライドは「プロジェクト管理は、実行と成果検証までを含む」と強調する。AI が WBS を作って終わりではなく、実行と検証まで AI 側の担当に入る。

目標から WBS へ落とし、成果から計画を見直す

問い合わせ体験の改善を例にした6ステップの循環。

  1. 目標: 問い合わせ体験を改善（応答時間短縮・自己解決率向上）
  2. プロジェクト: FAQ と対応手順を整備（分類方針・更新体制・公開ルール）
  3. WBS: 分類・更新・レビュー（担当・期限・依存関係）
  4. AI が実行: 対象データと手順を限定（収集・下書き・反映）
  5. 成果物を検証: 内容・根拠・完了条件（正確性・出典・承認）
  6. 事業成果を評価: 応答時間・品質・再発（CS・解決率・再問い合わせ）→ 実績・改善のフィードバックとして目標へ戻る

ここでの原則は「タスクの完了と、事業上の成果は分けて確認する」で、スライドは「『FAQ を作った』と『問い合わせが解決した』は、別の事象として記録する」と書く。この目標管理の軸をさらに掘り下げたのが goal-kpi-management-layer である。

実行層の前提：herdr × Linear

このポストは同じ @yoshio_nocode の以前のポストを引用しており、そこでは「AI 並列のタスク実行基盤は herdr × Linear が最適解」と述べ、4手順を挙げている。人と AI のタスクを Linear に集約し、herdr で 1 Issue＝1 AI セッションに固定し、Claude Code や Codex が起動時に自分で起票し、Creating by AI→In Review も自分で更新して Done にすると作業画面まで自動で閉じる、という流れである（引用元ポストの本文のみで、添付画像は未収録）。概念設計の「プロジェクト・タスク管理」層に linear を、専門 AI エージェントの実行を herdr で束ねる、という具体化と読める。

問い

  • 「タスク完了」と「事業成果」を別の事象として記録する運用を、Linear や Notion のどのフィールドで表すか。成果の観測指標を Issue に紐づける実装例はあるか
  • オーケストレーター層に置かれた OpenClaw・Hermes Agent・Codex・Claude Code は、権限制御（人の承認を経ずにどこまで実行するか）を実際にどう分けるのか。スライドは機能名だけで実装は書いていない
  • 資源管理に「AI 利用枠」を入れている点は、token-management が言うトークン費用の経営イシュー化と同じ発想か
