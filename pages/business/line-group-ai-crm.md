# LINEグループに「記録係」の公式LINEを入れて顧客台帳を自動化する

> **TL;DR**: 社内連絡がLINEグループで回っている地方の現場系企業に、新しいツールを入れず「記録係」の公式LINEをグループへ招待し、発言をClaude APIで仕分けて顧客台帳と月報を自動で作る導入支援の実例（安松谷直登・@meguron12。本人は「1ヶ月で12件受注」と書く）。

SlackやNotionはAIと連携しやすいが、LINEグループのやり取りは後からAIに読ませにくいため、リフォーム・塗装・工務店のように現場に出る人が多い会社はAIの話になると「うちはLINEだから、まだ先」で止まりがちだ、と安松谷が書く。安松谷はここを「困っている会社は多いのに、まだほとんど手がつけられていない」市場と見ている。導入の芯は「新しく何かを書いてもらうのはやめて、LINEに書いたものを裏で写す」という方針で、構成はLINE公式アカウント・Googleスプレッドシート・Claude APIの3つ、ランニングコストは月1,200〜2,700円くらいだと安松谷は述べる。

## 出発点：同じ案件を3か所に手入力していた

最も多かった支援先（地方のリフォーム・塗装会社）では、問い合わせの入口がチラシ・紹介・自社サイト・LINEに分かれ、顧客管理シート・毎月の月報フォーム（30問の自己申告）・現場ごとの予算シートの3か所に同じ案件を手入力していた。安松谷は「Slackか顧客管理ツールで一本化」は書く場所を4か所目に増やすだけで、入力は続かなかっただろうと判断した。ツールを決める前に社内のLINEグループを読むと、事務担当がすでに「電話お問い合わせ／チラシ反響／反響日／お名前／住所／電話番号／ご要望／@担当 ◯日◯時 現調になりました」のようなほぼ決まった型で報告しており、足りないのは台帳へ写す手間だけだった。

## 仕組みと導入の5手順

流れは「いつもどおりLINEグループに書く → 記録係の公式LINEが1行ずつ記録 → 雑談を外す → AIが名前・流入経路・状況・金額を読み取る → 自信があるものは顧客台帳へ、迷ったものは『要確認』へ → 月末に月報」。仕組みを作る作業（プログラム・データ整理・テスト・マニュアル）は Claude Code、毎日動いて仕分けるのは Claude API と分けて考えるとよい、と安松谷は書く。

1. **記録用の公式LINEを作ってグループに招待する**: 既存の公式LINEは別の配信ツールにつながっていたので新規に作った。ハマりどころは、グループ参加の設定が最初はオフであることと、1グループに入れられる公式アカウントが1つだけであること（先に入っていた通知用アカウントを別グループへ移した）
2. **届いた発言を加工せず「生ログ」に残す**: GAS（Googleスプレッドシートで動くプログラム）で1行ずつ書き込むだけ。記録係を入れる前の過去ログは取れない
3. **Claude APIで必要な情報だけを仕分ける**: 「明日の集合9時で」のような雑談はAIに渡す前に外し、呼び出し回数と費用を下げる。名前・住所・電話・流入経路・工事の種類・現調日・状況・金額を読み取り、「32万」→320,000円、「30日14時半」→日時に正規化する。1通に2人分の話が混ざるようなAIが迷う発言は台帳に書かず「要確認」へ回す。安松谷は「間違ったまま台帳に入る方が後で大変」なのでここに最も気をつけたと言い、本番前に実際のやり取り23パターンで全件正しく仕分けられることを確かめた
4. **既存の約870行を整理する**: 完全重複5組をまとめ、判断がつかない105行は印をつけて先方に決めてもらった
5. **月報を自動で出す**: 会議で使う月報と同じ形で、毎月28日に速報・翌月1日に確定版。流入経路別の件数と受注率も出る。ほかに、現調日を過ぎたら自動で「現調済」にする機能と、金曜17時に止まっている案件をグループへ知らせる機能を入れた

キックオフから本番グループへの接続まではおよそ6週間だった。

## 見えたこと：データは担当と担当の「間」で抜けていた

既存の約870行を整理すると、ステータスが「現調」のまま止まった行が8割あった。現地調査には行っているが、その後の見積・受注・失注が台帳に残らず、受注や金額は月報フォームや予算シートの側に書かれていた。結果として、チラシ・紹介・自社サイトのどの経路から来た客が決まりやすいかを過去データから出せない状態だった。安松谷は、現場も事務も社長もそれぞれ報告・記帳・数字確認をしているのに「現調のあとどうなったか」だけが現場と事務の間で抜けていたと述べ、営業とマーケの間で経路別の受注率を誰も追っていないのと同じ構造だと見る。

そのため現場へのお願いは2つだけにした。受注・失注が決まったらLINEに一言（「◯◯様 受注しました 59,000」程度）書くことと、お客さん1人につき1通で送ること。運用面では、最初の月は月3〜4回人の目でデータを確認し、その後も2週間〜1か月に1回は仕分けルールを見直す。電話のようなLINEの外のやり取りは自動では入らないので、人が足す。

## 何から手をつけるか

安松谷が勧める順番は「今どこに・何を・誰が書いているかを並べる → 書く場所を1つに寄せる（新しく作るより、すでに書いている場所に寄せる）→ AIに渡すのはそのあと。AIが迷ったものを人に戻す道を先に作る」。自社で試すなら、新規問い合わせ・現調や商談の日程・受注と失注・金額のそれぞれについて「どこに・誰が書いているか」を紙に書き出し、2か所以上に書いている箇所を自動化の入口、どこにも書いていない箇所を今まで見えていなかった数字と見る。安松谷は「AIで速くなるのは作業で、売上を決めているのは今も商談」なので、商談の結果を取りこぼさず数字に残すところまでやって初めて仕組みとして意味がある、と締めている。

記事はAI導入支援を営む安松谷（ミセス株式会社 代表取締役）自身の事例紹介で、末尾に無料壁打ちと営業資料プレゼントへの誘導がある。受注件数・コスト・期間はいずれも本人の申告である。

## 問い

- 「迷ったものは台帳に書かず要確認へ」の閾値をどう決めているか。AIの自己申告の自信度か、ルール（1通に複数人など）か。後者なら [[concepts/decision-layer-model]] のように判定をルール側へ寄せられるか
- 「新しいツールを入れると書く場所が増えるだけ」という判断は、LINE以外（メール・電話中心の会社）にも同じ形で当てはまるか。電話の記録が抜ける問題はどう埋めるか
- [[tools/line-harness]] のようなLINE公式アカウント向けOSSのCRMと、この「グループに記録係を入れるだけ」の構成は、どちらが地方の小規模事業者に定着しやすいか
