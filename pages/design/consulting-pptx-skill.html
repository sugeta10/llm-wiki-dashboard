consulting-pptx-skill｜コンサル品質のPPTXをAIに作らせるClaude Codeスキル

TL;DR: 提案書・報告書づくりで毎週使っている仕組みを公開した Claude Code スキル。価値の中心はテンプレでも生成パイプラインでもなく、レビューで受けた指摘を1行ずつ溜めた約80項目のスライド規約ファイルを「作らせる前に毎回読ませ、出力後に機械チェックで違反を検出する」蓄積ループにある。

@Gozengogo_ が「まじなスライドをつくるためのパワポスキル」として告知したリポジトリ（gozen3ji/consulting-pptx-skill）。README によれば公開元は AI エージェント基盤「Jinba」を開発する Carnot AI で、同社が実際に毎週の提案書・報告書づくりで使っている仕組みの公開版だとしている。一式の中身は、27パーツの自由記述HTMLパーツ集、コンサル型スライド36型のカタログと JSON によるスライド定義（SlideSpec）、HTMLプレビューから編集可能な PPTX へ出す生成パイプライン、スライド作成規約、規約違反を検出する機械チェッカーの5つ。README の冒頭は規約を「約85項目」、本文の節では「約80項目」と書いており、項目数は概数として扱う。

本体は規約ファイル slide-rules.md

README はリポジトリで一番価値があるのはテンプレでもスクリプトでもなく references/slide-rules.md だと明言する。実務の資料レビューで受けた指摘を1行ずつ書き溜めたもので、「結論はタイトルに書く」「角丸禁止」「塗りのあるボックスに枠線を付けない」「1資料1用語」といった項目が並ぶ。使い方は、AIに資料を作らせる前に毎回このファイルを読ませ、出力後に scripts/check_deck.py で違反を機械検出するだけ。AIはセッションごとに記憶がリセットされるので口頭で注意しても定着せず、ルールをファイル化して毎回読ませるのが唯一の定着方法だと README は述べる。

良いスライドを作るのは型ではなく「流し込んだ後の調整」だという立場も明確で、表を2枚に割る・右カラムを帰結形に書き直す・タイトルの通し読みでストーリーを繋ぎ直す、といった調整で受けた指摘をまた規約ファイルに1行追記する。この蓄積ループが品質の源泉であり、36型テンプレとパイプラインは「たたき台を数十秒で出して、調整の反復回数を稼ぐ」ための道具にすぎないと位置づけている。自社で使うときは規約ファイルに自社の規約・指摘を追記して育てることを勧めており、指摘を教訓ファイルへ書き戻す点は self-refining-skills と同じ構造だと考えられる。

作り方は2経路、型カタログは1本

経路 実体 出せるもの 使うとき
自由記述（本線） templates/freeform_parts_16x9.html（27パーツ） HTMLデッキ → PDF 納品物。主張に合わせて1枚ずつ組む
SlideSpec パイプライン pipeline/slide-spec/super_template.json（36型） 編集可能な PPTX たたき台を秒で出す・PowerPointで渡す

どちらの型もタイトル欄は型名だけで、見本の主張文を置いていない。見本文があると文型がそのまま真似され、主張ではなくテンプレを写した資料になるからで、タイトルは必ずストーリーラインから起こして差し替える。プレースホルダーの書き方は両経路で統一されており（本文 Text 1、項目名 ラベル 1、数値 00、年 YYYY年、出典 出典：Source 1 など）、チェッカーはこれらが納品デッキに残っていたら FAIL、タイトルの文型が6割以上同じなら WARN を出す。「1スライド1主張を先に決める」という ai-slide-creation の方法論を、規約と機械検査で強制している形と読める。

パーツ集には、主張パネル＋図、打ち手の効果表、状態ヒートマップ、充足度評価表（ハーベイボール）、割合のドットマトリクス、進捗バブル行列、注記つき散布図、柱＋土台、対向シェブロン、シナリオ線＋成長率チップ、課題と打ち手の2カラム、章扉のセパレーター（アジェンダ再掲・現在地を強調）などが含まれる。

AIにレイアウトを描かせない

SlideSpec パイプラインの核心は「AIにレイアウトを描かせない」こと。36型それぞれのレイアウト（タイトル位置・余白・フォントサイズ・作図ルール）は実測値としてレンダラーに焼き込んであり、AIが書くのは中身（主張・数値・ラベル）だけになる。たとえば template: "waterfall" に kicker・タイトル・単位付きの系列（base/up/down/total）・含意・注記・出典を持つ JSON を書くと、収益ブリッジの1枚がそのまま出る。書き出される PPTX は画像貼り付けではなく、全図形が PowerPoint で編集できるネイティブなテキストボックス・表・シェイプになる。AIに GUI でなく構造化された記法を書かせて精度を上げる点は intermediate-notation-pattern の一例と考えられる。

セットアップと構成

Claude Code のスキルフォルダに clone し、pipeline/ で npm run setup を実行する（Node.js が必要で、playwright chromium も入る）。あとは「36型から型を選んで10枚構成の SlideSpec を書き、パイプラインで編集可能な PPTX まで出して。作成前に slide-rules.md を読み、出力後は check_deck.py で FAIL 0 にすること」のように頼む。手動で使う場合はスキーマ検証→HTMLプレビュー→構造QA→編集可能PPTX書き出し→規約チェック→HTMLのはみ出し・重なり検査の順にスクリプトを回す。Node.js が無い環境でも、見本帳 PPTX の手動コピペと規約ファイル・機械チェックはそのまま使える。

パス 内容
SKILL.md 実運用フロー＋36型カタログ（AIへの指示書。スキルの本体）
templates/freeform_parts_16x9.html 自由記述パーツ集（27パーツ・1パーツ=1スライド・16:9）
pipeline/ 生成スクリプト（validate / render / qa / export / shots）＋CSS
pipeline/slide-spec/super_template.json 36型すべての完成 SlideSpec 定義（コピーして使う正本）
pipeline/slide-spec/schema.json SlideSpec スキーマ
references/slide-rules.md スライド作成ルール正典（約80項目）
scripts/check_deck.py 規約の機械チェック（PPTX / HTML 両対応・python-pptx が必要）
scripts/check_layout.mjs HTMLデッキの実レンダリング検査（フッターとの重なり・右端/下端のはみ出し）
assets/SuperTemplate_36type.pptx 36型を1枚ずつ収めた見本帳 PPTX（PDF版あり）

カスタマイズで一番効くのは規約ファイルへの追記で、SlideSpec ルートの palette でブランドカラーを一括差し替えできる。同じ仕組みをブラウザのチャットだけで使える形（Jinba App Neo）でも提供していると README は述べており、スキルはその公開版という位置づけになる。

問い

  • 約80項目の規約を読み、自分の文書レビュー規約と重なる項目・欠けている項目を突き合わせる。スライド以外の文書（報告書・設計書）に移植できる項目はどれか
  • 「実測レイアウトをレンダラーに焼き込み、AIは中身だけ書く」方式は、.md でデザインを固定する slide-md と比べて出力のバラつきをどれだけ抑えられるか
  • 「タイトル文型が6割以上同じなら WARN」のような機械検査は、AI生成文書の定型臭を検出する一般的な手として他の成果物にも使えるか

関連

  • ai-slide-to-pptx — AI生成スライドを編集可能な PPTX に組み直すプロンプト手法。本スキルはパイプライン側でネイティブ編集可能な PPTX を最初から出す
  • slide-md — デザインシステムを .md で固定してスライドのバラつきを抑える体系。本スキルは規約を .md、レイアウトをレンダラー実測値で固定する
  • ai-slide-creation — 「1スライド1主張」「結論を先に決める」方法論。本スキルの規約（結論はタイトルに書く・見本文を置かない）と機械チェックはその強制装置
  • ai-presentation-workflow — 構成→視覚確認→編集可能化→人間確認の工程分業。本スキルは編集可能化とチェックを1本のパイプラインにまとめる
  • intermediate-notation-pattern — AIに GUI でなく構造化記法を書かせる設計手法。SlideSpec（JSON）はその一例
  • self-refining-skills — 指摘を教訓ファイルへ書き戻して育てるループ。規約ファイルへの1行追記と同じ構造
