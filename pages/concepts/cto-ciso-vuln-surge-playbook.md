# PHP 脆弱性対応の「後」に向けた CTO/CISO の 4 つの構え（米内貴志）

> **TL;DR**: GMO Flatt Security 取締役 Co-CTO の米内貴志（@lmt_swallow）が、2026-10-21 夜からの PHP 緊急対応の翌朝に CTO/CISO 向けに書き残した 4 点。AI による脆弱性発掘が加速するこれからは高負荷が続くので、新機能開発を落としてセキュリティに時間・金・トークンを配分し、予防的サービス停止の覚悟と顧客との期待値調整を済ませ、平時にはレガシーを Rebuild and Retire し、CTO と CISO のサイロを壊して総力戦に入れ、という主張。

投稿は [[concepts/php-critical-vuln-2026-10]] で扱った PHP の重大脆弱性 2 件への一晩の対応直後、2026-10-22 の朝（UTC 00:57）に書かれた。米内は「一晩中連絡が鳴り止まず個別メッセージに返せていない」と断り、個別対応の代わりに世の中の CTO/CISO に届けたいことを 4 点にまとめ、「まとまりない部分もあるが投稿しないよりマシ」と添えている。投稿者プロフィールの表示名は「YONEUCHI, Takashi | GMO Flatt Security」で、自己紹介に取締役 Co-CTO とある。保存数は 2026-10-23 時点で 3,968 件。

書き手の立場に注意が要る。米内は脆弱性リサーチ事業と「Takumi Guard」を含む自社製品を持つセキュリティ企業の経営者で、投稿内でも自社の対応方針（顧客への事前スタンス表明をリリースノートで出す予定）に触れている。以下の 4 点は、脆弱性リサーチに数年取り組んできた当事者の見立てであって、業界統計や公式見解ではない。

## 1. 高負荷が続く前提で、セキュリティに時間を割きチームが休める体制を

米内は「ここ 1 年、体感では GPT-5.6 Sol 以後が、最も『本当に？』という脆弱性が掘り出される 1 年になる」と述べる（[[models/gpt-5-6]]）。中心になるのは memory safe でない言語で書かれたものを中心とする複雑なメモリバグと、認可バグの類だという。少なくとも年末まではこのクラスの脆弱性がまだ出てくると考えるべきで、直近の PHP 脆弱性についても世界中の研究者が Variant Analysis（既知の脆弱性と同型のバグを周辺コードから探す手法）をしており、まだ出てくるだろうと見る。

ここから導く経営判断は「新規機能開発に割く時間を明確に落とす」こと。米内は、これは経営者である CTO には取りにくい判断だと自分を含めて認めたうえで、それでもリーダーが意図してセキュリティに時間・お金・トークンを配分するのは経営者にしか取れない択だと書く。

「対応は AI で」という発想については、技術的には正しいが組織的には正しくない、と切り分ける。理由はセキュリティ対応のタイミングを自分で御せないこと。深夜対応・急な計画変更・デグレへの不安・自社に影響があるか分からない脆弱性情報の過多が重なってストレス強度が上がり続け、昨夜のような対応が毎週あればチームは比較的簡単に壊れる、という見立てである。

## 2. 「必要なら予防的にサービス停止」の覚悟を決め、止められないなら仮想パッチと監視に資源を

今回のような脆弱性では「顧客保護のためにサービスを止めざるを得ない場面」が訪れ、今回も多くのビジネスが直面したと米内は書く。今回の経験を元に、本当に止めてはならないのか、止められるのか、止めうる期待値調整が顧客とできているかを徹底的に見直すことを勧める。顧客への事前連絡によるスタンス表明も有効だとし、GMO Flatt Security 自身もこれから実施してリリースノートに掲示すると明かす。理由として、自社サービス、特に Takumi Guard の侵害はソフトウェアサプライチェーンの最悪の侵害につながるからだと述べる。

止められないビジネスがあることは認めつつ、天秤の置き方が変わったという指摘が要点である。金融・医療の規制や顧客との SLA は存在するが、現代ではそれに反するリスクとセキュリティ侵害に遭うリスクを天秤にかける必要が出てきた。少し前までは「停止のデメリットは想像できるが侵害は考えにくい」時代だったが今はそうではない、と米内は書き、「何がなんでも止めてはならない」ビジネスは人命に関わるものを中心に相当限定的だと見る。どうしても止められない場合は WAF（Web Application Firewall）層などで緩和策を施して監視する流れになるとし、必要なコンポーネントと運用資源がなければ整えるよう促す。

## 3. 平時があればレガシーを Rebuild and Retire する

自社の緊急対応が落ち着いているなら、数年塩漬けのシステムや誰がメンテできるか分からない「オーパーツ的存在」から順に、作り直し（Rebuild）と旧システムの廃止（Retire）を試みるべきだと米内は言う。新規開発の代わりにここへ資源を充てるのは他の誰も決められない CTO/CISO の仕事であり、追々自分たちを助け、ついでに AI-native 開発へ移行できて改善しやすくなる、という見立てである。

どこから手を付けるかの基準として挙げるのは 2 つ。第一に memory unsafe な言語や型安全性があまり確保されていない言語の実装で、米内は PHP 好きと断りつつ「C/C++ で書かれた php-src はメモリバグ類に対する見通しに限界がある」と書く。第二に開発当時に DevOps プラクティスが整っていなかった時代のソフトウェアで、経験上「セキュリティ診断をすると取り返しのつかない量の脆弱性が出て、作り直した方が早い」となる傾向にあり、診断やペネトレーションテストを行う自社でもこうなるとどうしようもないと述べる。

ただし Rebuild には強いソフトウェア開発力と AI-native なスタイルへの移行が必須で、ここに CTO の力が要る。どこからレガシーを追い出しどうレジリエンスを確保するかには CISO 的な感性、既製品（特に SaaS）を買って済ませる判断には CIO 的センスが要るとして、「総力戦だと思ってください」と締める。レガシーの置き換えをコードレベルで担う道具としては [[tools/code-modernization-plugin]] が同じ時期に出ており、新旧の振る舞い一致を示そうとするその設計は、ここで言う Rebuild の検証工程に当たると考えられる（wiki 側の推論）。

## 4. CTO/CISO の総力戦

直近の局面には CTO/CISO の総力戦が必要で、ボードがセキュリティに向かって一致団結する必要があると米内は書く。両ロールの間にサイロがあるケースは結構あるが「そんなことを言っている場合ではない」として、投稿は「団結を！」で終わる。

## 位置づけ（wiki 側の読み）

[[concepts/php-critical-vuln-2026-10]] が個人の備え（使い回しパスワードの変更・2 要素認証・偽メール警戒）を扱ったのに対し、本投稿は同じ出来事を組織の経営判断の側から見ている。米内の第 1 点が前提にする「AI が脆弱性発掘を加速する」という構図は、供給側として [[tools/oss-scanner]]（Anthropic が最強モデルで重要 OSS をスキャンし結果を送る無料サービス）が同じ月に始まっていることと整合する。発掘が加速するなら、組織側の対応容量の方が律速になるという米内の見立ては、スキャン結果を受け取る側の負荷問題として読み替えられる（推論）。組織内でのセキュリティ設定・展開の実務は [[concepts/claude-code-security]] が扱う。

## 問い

- 自分が関わる組織で「予防的にサービスを止める」判断は誰が持ち、顧客との期待値調整は文書になっているか。止められない理由は規制か SLA か、単に検討していないだけか
- 「対応は AI で」が組織的に正しくないという米内の見立ては、[[tools/oss-scanner]] のように発見側が AI 化したとき、受け手側の対応容量をどう設計すれば崩れるのか
- Rebuild and Retire の優先順位（memory unsafe・型安全性の弱さ・pre-DevOps）を自分の手元のシステムに当てると、どれが最初に該当するか
