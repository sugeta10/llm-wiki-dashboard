# 仕様駆動開発（Spec-driven Development）

**仕様駆動開発**とは、AIエージェントにコードを書かせる際に、曖昧な指示のまま渡さず、事前に仕様・要件を整理してから渡すアプローチ。[[concepts/vibe-coding]] の反省から生まれた。

## Vibe Codingの限界

[[concepts/vibe-coding]] スタイルは最初の生産性は高いが、機能を数個追加した段階でコードベース全体が崩壊し始める傾向がある。

> 「Vibe Codingは『動くもの』は作れるが、『育つもの』は作れない」

この反省から、**上流で意図を固めてから下流（AIエージェント）に渡す**スタイルが主流になった。

## 仕様の3種類

| 種類 | 別名 | 内容 |
|------|------|------|
| 踏み台としての仕様 | Spec-first | 実装に入る前の準備で、マージと同時に捨てる。Planモードと同義に近い |
| 地図としての仕様 | Spec-anchored | 実装と並走して書き直す生きたドキュメント |
| 金型としての仕様 | Spec-as-source | 仕様を変えるとコードが変わる。型・テスト・スキーマで実現 |

**Planモード**はSpec-firstとして振る舞う。真に差別化するにはSpec-anchoredかSpec-as-sourceへ踏み込む必要がある。

## 要件・仕様・契約の区別

| 用語 | 意味 | 例 |
|------|------|-----|
| 要件 | 業務として何を達成したいか | 「在庫がある商品だけを検索できる」 |
| 仕様 | システムが何をするか | 「検索APIはstock_count > 0のフィルタを適用し最大20件を返す」 |
| 契約 | 呼び出し側と提供側の約束 | 「200を返すならbody.itemsが存在し各itemはid/name/priceを持つ」 |

3つを混同すると議論が壊れる。仕様駆動の「仕様」が実際にどれを指すかで書き方・精度・書き手が全く異なる。

## AIが書いたコードを信じにくい理由

人間が書いたコードのレビューでは、**書き手との共有知**（チームの癖・過去の議論・ドメイン常識）が直感的な判断を支える。AIが書いたコードにはその共有知がなく、1行ずつ明示的に「これは合っているか」を判定する必要がある。

> 人間のPRなら15分で終わるレビューが、AIのPRだと45分かかった（差は3倍）

対策として有効な4方向:
1. **ドメイン知識の構造化** — エンティティ・関係・状態遷移をAIが参照できる形で置く
2. **責務の分離** — Bounded Contextを明示することでAIへの命令の解像度を上げる
3. **プロセスの再設計** — 実装前に合意を取る（「とりあえず作らせて考える」は試作のみ）
4. **チーム展開** — 指示を個人の暗黙知からチームの共有資産（リポジトリ）へ移す

## コンテキストエンジニアリング

仕様の量を増やすだけでは逆効果になる場合がある。

- **Context Rot** — 長すぎるコンテキストは精度を下げる
- **Lost in the Middle** — 先頭・末尾に比べ中間の情報の認識精度が大幅に下がる

対策: 仕様書に書くべきは「人間にしか判断できない業務文脈」のみ。残りはテスト・型・CI等の決定論的ゲートに任せる。

## プロンプトの共有資産化

AIへの指示をリポジトリで管理する（`.claude/skills/`・`.cursor/rules/`・`AGENTS.md`等）。「3回繰り返したらリポジトリに引っ越す」というルールが実践的。

個人のチャット履歴に書いた指示は、その人が辞めた瞬間に消える。

## SDDワークフローの実践（JetBrains / DeepLearning.AI コース）

Karpathy自身が2026年に「Vibe Codingの時代は終わり、エージェンティックエンジニアリングへ移行している」と認めた。典型的なSDD実践フローは以下の3フェーズ：

### Phase 1: コンスティテューション（憲法）の作成
プロジェクト全体の合意文書。3つのコアドキュメントで構成：
- `mission.md` — なぜ作るか・主要目標
- `tech-stack.md` — 技術スタックと開発・デプロイ方針
- `roadmap.md` — フェーズ分けされた実装計画

**重要**: コンスティテューションの作成はエージェントに手伝わせてよいが、**最終確認は人間が行う**。ここで使った1時間が、実装フェーズで節約する数日になる。

### Phase 2: フィーチャーフェーズ（plan → implement → validate のループ）

各機能に対して専用ディレクトリを作成（例: `specs/YYYY-MM-DD-feature-name/`）：
- `plan.md` — 番号付きタスクグループのリスト
- `requirements.md` — スコープ・主要決定・コンテキスト
- `validation.md` — 成功の定義と確認方法

**実装の進め方**: タスクグループ単位で実装し、都度 `plan.md` と `validation.md` のステータスを更新する。一括実装は避ける。

> 誘惑：仕様を更新せず直接エージェントに「修正して」と伝えたくなる。しかし**仕様を真実の源として維持することがSDDの堅牢性の根拠**。

### Phase 3: リプランニング（方向性の再確認）

最初の機能実装後に**必ず立ち止まり**、以下を行う：
- コンスティテューションと実際の進捗の整合性確認
- ロードマップの優先順位の見直し
- CHANGELOGの作成・更新

> 「現在のAI時代において、人間の価値はコードを書くことではなく**思考とアーキテクチャ**にある」

## ツールサポート：Spec Kit（GitHub製）

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify init . --integration claude
```

30以上のエージェント統合に対応。JetBrainsのアプローチと違い、コンスティテューションをコード品質・テスト標準・UX一貫性等の高レベル基準に重点を置く。

## エンジニアの役割の変化

SDDによって開発者の役割は：
- **旧**: コードを直接書く
- **新**: アーキテクチャ決定・レビュー・方向性のステアリング

「いずれ英語が主要なプログラミング言語インターフェースになる」方向への移行が進んでいる。
