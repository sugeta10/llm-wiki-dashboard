# How I work with Agents（Thorsten Ball の15か条）

> **TL;DR**: エージェントとの仕事は、最新モデルだけを使い、How でなく What を渡し、SDLC 全体を見せ、反証不能な証拠を要求し、待たずに非同期で大きく任せ、影響範囲の大きいコードだけ人間が見る、という形に収斂するという実践者 Thorsten Ball の15か条。

> 📌 X bookmark: 13,787（2026-10-27 時点）

Thorsten Ball（@thorstenball。記事中で自チームのツールとして Amp に言及）が、友人に DM で繰り返し送っていた助言を X の記事「How I work with Agents」に1本化したもの。各条は根拠を並べる論証ではなく断言の形で書かれ、「半年前なら真だったかもしれない」「確信はない」と留保する箇所も本人がそのまま残している。Ball が「最大のゲームチェンジャー」と呼ぶのは「反証不能な証拠を求めろ」の1条である。以下は記事の順序どおりの転記で、4つの小見出しへの束ね方だけが wiki 側の整理にあたる。

## モデルとプロンプト（第1〜3条）

- **最新・最良のモデルを使え。** それ以外は時間の無駄になりうる、と Ball は述べる。モデルが10%の確率で間違うとき、どの10%かはわからないので結局何度も試すことになる。「50%安いが、ランダムに20%鈍いジェネラリストを本当に雇いたいか？」「まだ Opus 4.5 を使っている人がいるか？ いないだろう」
- **スロップの蓄積を心配するのをやめろ。** 「コードベースが保守不能な混乱になる」は半年前なら真だったかもしれないが、今はスロップが増えるとも、増えたとして保守不能になるとも確信がない、と Ball は留保つきで述べる
- **How でなく What をプロンプトせよ。** 何が欲しいかを書き、どうやるかは書かない方がしばしば結果が良い。例として「バイトコードコンパイラと VM を可能な限り速くしろ。2倍速くなるまで止めるな」「最終的にはこう動くべきだ」を挙げる

## エージェントに現実を見せる（第4〜7条）

- **SDLC 全体をエージェントに可読にせよ。** 幻覚を止めたのはツール呼び出し、つまりエージェントが現実に触れられるようになったことだ、と Ball は述べる。見えないものはでっち上げる。だから、作ったものを end to end で動かし、本番ログを読み、デプロイし、ロールアウトを見守り、リリースを切り、フラグを倒し、バグ報告をトリアージし、顧客にメールするところまでやらせる。「あなたに見えるものは何であれ、エージェントにも見えるべきだ」
- **SDLC のためのツールを渡せ。** Ball のチームにはバグ報告・ユーザーへのメール・「システムは健全か？」・フィーチャーフラグ付与のカスタムプラグインがある
- **エージェント向けの知識を eval せよ。** AGENTS.md・スキル・スクリプト・ドキュメントはコードベースに積み上がるが、エージェントは本当にそれを使っているのか。5体のブラインドエージェントを対照群と処置群で走らせて確かめる。「エージェントは実験を回すのが本当に、本当に得意だ」
- **ローカル開発は今や気持ちが悪い（yucky）。** 各エージェントが仕事に必要なものを何でも入れて動かせるべきで、リモートマシンでは簡単だがローカルでは end to end テストをさせるとリソース競合を避けにくい

## 反復・証拠・待ち方（第8〜11条）

- **エージェントと反復するな。反復するためのツールを作らせろ。** 「これを試して……いや、あれを試して」ではなく「20通りの変種と、それを組み合わせて試せる小さなページを作って」。解の空間だけでなく問題の空間にも使う。「遅い理由の仮説を4つ出して、4つ全部確かめて」
- **反証不能な証拠を求めろ。** Ball が「最大のゲームチェンジャー」と呼ぶ条。エージェントは end-to-end のウォークスルー・デモ動画・前後の数字といった証拠を作るのが本当に得意で、何が証拠かの信頼と勘は使いながら育てるしかない。AGENTS.md に「これは証拠ではない」を書いておけ、と勧める
- **エージェントを待つな。エージェントに待たせろ。** TTFT（最初のトークンまでの時間）を気にしているなら何かが間違っている。非同期に寄せ、より大きな仕事を、より野心的に渡し、往復でなくバッチで扱う
- **自動化・スケジュール・wake-up・heartbeat はキラー機能。** 使えなくなって初めて痛烈に恋しくなった、と Ball は述べる。「2時間後にログを見て」「これが本番に出たら教えて」「毎日9時に確認して」

## 記憶・文章・レビュー（第12〜15条）

- **コンテキストを手で管理するのをやめろ。** 「いま300kか380kか」と考える時間はすべて無駄で、コンパクションは驚くほどよく機能する。1スレッド＝1タスク。46メッセージのスレッドもあれば3,714メッセージのスレッドもある
- **スレッドは会社の記憶だ（Amp の場合）。** 「なぜこうしたのか？」に答えられる。チームが使うほど知識が増え、スレッドは git コミットと結びつく。重複作業を避けられる
- **人間向けの文章をエージェントに書かせるな。** 例外はデバッグ手順・インシデント報告・一部のドキュメント。相手側の人間がそれほど重要でない機械的なものに限る
- **影響範囲（blast radius）の大きいコードだけレビューせよ。** 中心的なファイルは5つ未満で、それだけ見る。データベースのマイグレーションは見る。クロージャか class か・よりきれいな型・変数名・重複でさえ、もう気にしない。動くか？ 図の矢印のレベルで理解しているか？ エージェントは end to end でテストしたか？ 1か月後に自分が変えられるか？ そこまで Yes なら、レビューするかもしれない

## 他ページとのつながり（wiki 側の推論）

- 「影響範囲の大きいコードだけレビュー」は、[[concepts/agent-trust-inverse-pyramid]]（@poteto）が人間レビューを最下層の最小に置く配分と同じ向きで、[[concepts/agent-era-code-review]] がリスク別に人間承認を 0/1/2 人へ絞る運用の個人版にあたる
- 「反証不能な証拠を求めろ」「これは証拠ではない」は、[[concepts/claude-code-long-task-harness]] の「証拠を返すレビュアー」や [[concepts/fable-5-prompting]] の「進捗を証拠で監査」と同じ要求を、プロンプト側でなく人間の受け取り方の規律として書いたもの
- 「エージェント向けの知識を eval せよ」の5体ブラインド対照実験は、[[tools/claude-code-plugin-eval]] と [[papers/2026-li-skillsbench]] のスキルあり/なし対試験と同じ構造を、公式コマンドでなく自前の実験設計として述べている
- 「待つな・非同期・バッチ・スケジュール」は、[[concepts/coding-agent-workflow-styles]] の委譲低速ループ側に全面的に賭ける立場で、[[concepts/agentic-engineering-workflow]]（@mvanhorn）の「人間は手でなくシグナル」と重なる。スケジュール/heartbeat の具体は [[concepts/goal-loop-routine]] と [[concepts/claude-code-loop-types]] が扱う
- 「SDLC 全体を可読に・見えないものは作り話になる」は、[[concepts/harness-seven-jobs]] の「自律より先にセンサー」と同じ診断
- 「スロップを心配するな」「変数名や重複はもう気にしない」は、[[concepts/cognitive-debt]] の「説明できないものは出さない」と正面から対立する。Ball は「図の矢印のレベルで理解しているか」を残すので、理解の粒度を矢印レベルまで粗くした上で負債を受け入れる立場と読める

## 問い

- 「これは証拠ではない」を AGENTS.md に書くなら、何が証拠で何が証拠でないか（自己申告の「動きました」・テスト名の列挙・スクリーンショットなし）をどう列挙するか。自分の CLAUDE.md の「検証可能な手段で検証してから報告する」と同じ型か
- 5体のブラインド対照実験を wiki-ingest スキルに当てる: LESSONS.md のあり/なしでカテゴリ判定や粒度判定が変わるか（[[tools/claude-code-plugin-eval]] の問いと同じ）
- 「人間向けの文章をエージェントに書かせるな」は、AI が書くこの wiki と正面から衝突する。wiki ページは「相手側の人間がそれほど重要でない機械的なもの」に入るのか、入らないなら何を人間が書くべきか
