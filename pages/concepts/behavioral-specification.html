振る舞い仕様（Behavioral Specification）

TL;DR: 外部から観測可能なシステムの振る舞いについて「正解・不正解」を判定するための成果物で、AIに実装させる前に人間が確定させるべき基準である。

良い仕様の条件は「実装の正誤を判断でき、かつその判断に追加の質問をなるべく要しないもの」。ここで実装をそのまま仕様にしてしまうと正解を狭くしすぎる（エラーメッセージの文字列レベルまで固定されてしまう）。そこで観測可能な振る舞いの範囲で「許される出力・流れ」を記述するのが核心となる。spec-driven-development の中核概念。

システムの2分類

振る舞い仕様の表現はシステムの種類によって異なる。

変換システム（Transformation System）

入力すると停止して出力を返すシステム。FizzBuzz関数・ソート・コンパイラ・Web API等。

振る舞い仕様の形式: 入力と「許される出力」の関係（表・場合分け・数式）

| 入力 | 出力 |
|-----|------|
| 3で5でも割り切れない | 入力の10進数文字列 |
| 3で割り切れ5で割り切れない | "Fizz" |
| ...（場合分けで圧縮）|

注意点: 1つの入力に複数の許容出力がある場合（サイコロ等）、同じ入力を複数行書く。「表に書かない入力 = 何を返しても仕様違反にしない」という意味になる。

リアクティブシステム（Reactive System）

何度も入力できて停止しないシステム。WebApp・GUI・自販機・ゲーム等。

振る舞い仕様の形式: 発生できるイベントの流れ（状態遷移図）

Idle → 貨幣投入 → Paid → 商品選択 → Dropping → 商品排出 → Idle
  • 正常系だけでなく異常系（売り切れ選択・現金回収）も必ず書く
  • 図にない遷移は「その仕様では発生できない流れ」として扱う

状態遷移図の注意点

状態遷移図は「状態そのもの」ではなく「イベントの流れを表現すること」が目的。実装側の内部状態は仕様の状態と一致しなくて構わない。

仕様バグの典型例（自販機）: - 選んだ商品を状態に記録していない → 水を選んでもコーヒーが出ても仕様違反にならない - 商品選択イベントが抜けている → 点灯後に何も押さないまま商品排出が可能になる - 売り切れ遷移がない → 在庫0でも販売し続ける実装が仕様違反にならない

内部イベント τ（タウ）

外から制御も観測もできないイベント。サーバー内部処理・通信エラー・時間経過等。

おみくじを引く → τ(大吉が選ばれる) → "大吉"を表示
                → τ(凶が選ばれる) → "凶"を表示

τを書かずに「大吉になるイベント」と書くと、ユーザーが結果を制御できる振る舞い仕様になってしまう。通信エラーは必ずτで正常系と異常系に分岐させる（AIはデフォルトで異常系を省略しがち）。

AIとの協働

  • AIに仕様を作成させる: 代表的なトレースを質問し、AIがPlantUMLで状態遷移図を埋める → 人間が確認・修正
  • AIに仕様バグを探させる: 完成した仕様を読ませて「意図しない流れ」「抜けた流れ」を質問する
  • AIにテストを作らせる: 仕様を渡して「振る舞い仕様からテストを作って」と指示（property-based testingと相性良）

問い

  • 自分のwikiやツール開発で、状態遷移図ベースの振る舞い仕様をAIに先に書かせるフローは実際に回るか？
  • τ（内部イベント）の明示は、AIが省きがちな異常系の網羅をどこまで改善できるか？
  • 変換システムの「表に書かない入力＝仕様違反にしない」という暗黙ルールは、AI生成テストとどう噛み合うか？
