エージェントに仕事を任せるときの批判的思考（Addy Osmani）

TL;DR: エージェントの出力が「よく書けていて大体正しい」ほど二度見を促す刺激は消えるので、批判的思考は日課として自分で組み込むしかない。Addy Osmani は委任の深さを「オフロード→委ね→認知的降伏」の3段で測り、仮説を先に書く・緑のチェックが何を証明したか問う・エージェントが決めたことを一覧させる・自分の名で出せる水準を守る、という問いと習慣で降伏を防ぐ。

📌 X bookmark: 27,352（2026-11-04 時点）

かつて批判的思考が働いたのは「問いと答えの間の空間」で、そこで認知と審美の処理が起きていた。Addy Osmani（Claude Code チーム）は、エージェント経由で仕事が回る今その空間は秒単位に縮み、日々の仕事の中で批判的思考を強いるものが何も無くなったと書く。難しさは予想と違う形で来る、と Osmani は言う。モデルが良くなるほど明白な誤りの割合は下がり、出力の多くは「よく書けていて大体正しい」ので、二度見を要求してこない。複数のエージェントを並列で走らせても、出力を見る目は一対しかない。しかもエージェント的な働き方は快適で、速く・心地よく・だいたい正しい答えが返るからこそ、警戒を緩めやすい。Osmani はエージェントの大ファンだと断ったうえで、減らせと言うのではなく「何でもエージェントに投げられる世界で批判的思考を保つ」ための実践を書いている。

オフロード・委ね・降伏の3段階

Osmani は人に説明するときこれをスペクトルとして描く。上端は認知的オフロードで、タスクを AI に委任しつつ結果の所有権は保つ。Osmani 自身も一日中これをやっており、読者にも勧める。中段は委ね（deferral）で、ツールの出力がそのまま自分の新しい入力になり、結果が仮説であることをやめる。下端が認知的降伏（cognitive surrender）で、AI の出力が静かに自分のものになり、確かめる必要を感じなくなる。この語は Wharton の Steven Shaw と Gideon Nave が作ったもので、Osmani が見てきたことにぴたりと合うという。信頼（あるいは怠惰）が増すにつれ人はスペクトルを下っていくが、各段が緩やかで合理的に見えるため、移行はほとんど観察されない。前の答えをよく読んだから次は流し読みし、その次は骨格だけ眺め、やがてある行について聞かれてもエージェントの助けを借りても説明できない。これが降伏であり、認知的負債（cognitive-debt）が積み上がる経路だと Osmani は書く。

負債が見つかるのは、システムのメンタルモデルを当てはめようとして、それが存在しないと気づくときである。Margaret-Anne Storey はこれがチームでは「共有されたシステム理論の理解の侵食」として現れると書き、Osmani はコード側の等価物を comprehension debt（理解の負債。Jeremy Twei の造語）として書いてきた（loop-engineering に既出）。その瞬間には完全に見えない。コードベースはきれいに見え、テストは通る。誰も理解していないと分かるのは変更が必要になったときで、戦略文書や仕様の目次だけ読んで承認した場合も同じだという。

ただし Osmani は不可能を求めてはいない。大規模なコードベースの完全なメンタルモデルを保つのは無理で、Claude Code チームは理解をオンデマンドで組み立て直すと公言している。ある部分を理解する必要が出たら、そのスライスを Claude に説明させる。この種の負債はエンジニアが思うより回復しやすく、必要に応じて局所的に再構築できるなら完全なモデルを保つ必要はない。自分が何を持っていないかを知っていればよい、というのが Osmani の線引きである。

賭け金が低いところでは全部委任してよい。Osmani は講座の収録場所を似た評価の3ホテルから選ぶとき、レビューを読む時間が無く AI に決めさせ、うまくいったので次も同じにすると書く。しかし資金の投資先・子どものキャリア助言・仕事で何を作るか・どの変更がどのユーザーに影響するか・出荷して安全か、には使わない。間違いが安いところで手渡し、他人が結果を引き受ける場所では推論を手元に残す。質問の答えをエージェントの助けを借りても説明できないなら、所有権を手放したということであり、それ自体は常に問題ではないが、どこにいるかは知っておくべきだという。

Osmani が自分に問う6つの問い

自分が何を考えているか分からないとき、Osmani は昔から基本の問いに戻ってきた。正しい問題に取り組んでいるとどう分かるか、正しいやり方で解いているとどう分かるか、結論を支える証拠はあるか、終わったとどう分かるか。書き出すと子どもじみて見えるが、普段無視するカテゴリで考えることを強いる。今は「エージェントにどうすべきか聞く」でこれを全部飛ばせるので、Osmani は新しい版の問いを置いている。

  • 聞く前に仮説を立てたか。 些細でないタスクをエージェントに走らせる前に、頭の中だけでも答えの見当を書く。悪い推測でよく、新情報で変えてよい。ただし一度よく書けた応答を読むと他の可能性を想像しにくくなる。見当が全く無ければ、Thariq Shihipar の言う blind spot pass（自分が知っていることを渡し、未知の未知を探させる。finding-unknowns）を頼む。
  • 考える助けを頼んでいるのか、考えること自体を外しているのか。 どちらでもよいが、どちらをしているか分かっていること。
  • これが間違いなら何が真でなければならないか。 そして確かめに行く。モデルの自己申告の確信度は、実際に実行できるテストよりはるかに価値が低いので、テストを与える。
  • 別の角度から反論を聞いたか。 開かれた問題で強い立場を取ったとき、複数のモデルに反対側を論じさせてから自分の意見を作る。時間はかかるが主題について格段に多く知ることになる。
  • 保守する人の前でこれに賭けられるか。 コードに限らず納品物すべてに当てはまり、Osmani はこれを説明責任（answerability）の基準線だと考える。
  • 何を練習しなくなったか。 日常的なデバッグの一部は手放してよいが、意図的でありたい。

検証を習慣にする

Osmani が最近検証について多く書いてきたのは、ボトルネックがコーディングから「自分が正しいと確信すること」に移ったと考えるからである。エージェントに検証手段（E2E テスト・プロパティテスト・実際のアプリ操作）を渡せば、変更し・検証を走らせ・出力を読み・やり直す、を人が何かを見る前に済ませる。Boris Cherny の言う「Claude に自分の仕事を検証する手段を与える」で、Osmani はこれを良い結果を得る最も重要な要素の一つに数える（この原則を MCP 構成に落とした例は claude-code-mcp-stack）。全行を読む代わりに、こうしたループを組み、証拠をレビューする側に回る。

ただし検証も降伏しうる。「結論を支える証拠はあるか」が「チェックは緑になったか」に置き換わる。エージェントはテストを作るのが安いので緑は大量に見えるが、壊れた機能を捕まえないテストが通っていることはありうる。機能と同じ誤りを持つテストは通り、緑のチェックは1つの性質しか伝えないのに、全部を覆っていると想像しやすい。Osmani の処方は次のとおり。

  • チェックが緑になったら何を証明したかを問い、次に何を証明しなかったかを問う。
  • 「検証済み」の定義を事前に決める。事後にはどんな結果でも合理化してしまう。
  • エージェント作業の終了線は具体的なもの（通ったテスト・スクリーンショット・ログ・トレース）にする。「終わったように見える」という解釈の余地を消す。完了通知が来たら要約を見る前に、実行されたコマンドとその出力を先に読む。
  • Claude Code には新しいコンテキストのサブエージェントで自分の仕事を自己批評させられる。思い出したときだけでなく毎回走るようループに焼き込む。Osmani は最後に「何か見落とした？」と必ず聞く。フロンティアモデルで複雑な機能を仕上げてレビューした後でも、2〜3件は返ってくるからだという。
  • 深く見るべきときを知るのも技能で、Osmani の好きな目安は Claude Code チームのレビュー記事（agent-era-code-review）の「チェックが何を見逃すか言えないなら、素早い承認でなく本物のレビューを頼め」である。

これはコード以外にも当てはまる。エージェントが顧客との通話50件や競合分析を合成したなら、原資料を数件確認して要約が正確か見る。推奨の根拠になっている数字を1つ確認し、計算が正しいか見る。エージェントは検証の設定を安くした。難しいのは良い検証がどんなものかを知ることだ、と Osmani はまとめる。

生成物に本当に注意を向ける

600行の PR を渡されたとする。構造をざっと見て、全行は読まず、変数名は妥当でテストも通るので承認する。だが真ん中あたりにトランザクション境界の微妙な順序変更や、考えたことのないエッジケースの既定値の反転がある。レビューはしたが、見つけると分かっていたものしか見ていない。書くこととレビューすることは別の技能で、レビューがゴム印に変わる地点がある。Osmani は、AI が書いたのではないつもりで差分を読み、さらに差分の先にあるエージェントが決めたことを見ろと書く。長いセッションでエージェントは既定値・スコープ外・要件が衝突したときどちらを再解釈するか、といった小さな決定を大量に下しているが、「すべて順調」という要約には出てこない。だから決定と前提の一覧を出させ、自分にクイズを課す。数行を無作為に選び「この行は？」と問う。文書なら閉じて主張の骨子を記憶から書き出す。長いセッションでは Claude に変更の報告書を書かせ、末尾にクイズを付けさせて「満点で通るまでマージしない」ルールを置く人もいる。出荷するものは守れる程度に理解しておく。いつか誰かに聞かれうるからだ。

エージェントは注意を守る側にも使える。Osmani は多数の PR が来る OSS プロジェクトで、何が来ているか・ガイドラインに反するものはどれか・自分の注意が要るのはどこか、の絞り込みにエージェントを使う。判断を自己決定させることはまれだが、集中すべき場所まで狭めてもらえば、その変更が正しい問題を正しく解いているかを実際に考えられる。

量については正直になれ、と Osmani は言う。Osmani がorchestration tax（オーケストレーション税）と呼ぶのは、エージェントが生成する量と、自分の名前を付けて出せる量との差である。完成品が処理できるより速く積み上がるなら、それを直すまでセッションをもう1本足しても助けにならない。チェックを締めて自分が要る量を減らすか、減速する。支えられる量より多く生み出しているとき、それはレビューではなく祈りだ、と書く。

入力の質が出力の質を決める

人間のメンタルモデルは今も関わるが、位置が中央から前端と後端に移った。前端はタスク記述とコンテキスト、後端は出力のレビューで、ここにエネルギーを置く。だから良い入力が出力の質に効き、Osmani は良いプロンプティングを批判的思考の技能と見なす。昔は曖昧な依頼を出すと誰かが問い返し、「実は自分でも決めていなかった」と気づけた。エージェントは多くの場合そこで止めず、抜けを埋めて「できたように見えるもの」を返すが、背後の考えはまだ曖昧なままだ。Osmani はこれを intent debt（意図の負債）、つまり自分が書いていない成果物に潜む暗黙の目標・制約・根拠と呼び、他の負債と違って自分以外には直せないと書く。意図は自分から出すしかない。

プロンプトは問題に対する自分の理解の反映で、明確に表現できないなら頭の中でも明確でないかもしれない。助けを頼む前に自分の言葉で依頼の brief を書く。読者・対象外・完了の定義を記す。2巡目の修正で届かなければ、微調整をやめてプロンプトを書き直す。エージェントに手伝わせてもよく、Osmani は Andy Clark の「委任」と「協働」の区別を好む。協働では、プロンプトが出力を鋭くし、出力が次のプロンプトを鋭くし、問題のメンタルモデルが鋭くなる相互増幅の循環に入る。不明確ならエージェントに「理解できていないことについて自分をインタビューさせる」。自分のメンタルモデルが磨かれた状態でセッションを閉じられたら成功の印だという。入力の連鎖にも注意が要り、各エージェントが前のエージェントの要約をそのままコンテキストに渡していくと、3番目のエージェントは原典を読んでいない。

出力には自分の基準が要る。Osmani は多くの創作媒体で AI を試したが、大半は基準に届かず見せていない。すべてが整った書式で自信ありげに出てくるので、磨かれていることはもはや有用な信号ではない。AI は作るのを速くしたが、自分に帰属させて平気でないものは出さない。基準に満たなかったら、その理由を共有設定・フック・テストに書いて再発を防ぐ。それが好み（taste）の複利の仕方で、不採用の理由を書き残すこと自体が良い習慣だと Osmani は書く。

「モデルの方が上手くなるのに」への答え

この分野に強気なら、1〜2年でモデルが自分の検出できることを検出できるようになるのに、なぜ技能を保つのかと思うだろう。Osmani は検出の多くでその見立ては正しく、自分も検出をエージェント側へ押し出すよう主張してきたと認める。それでも重要な理由は、結局誰かが出荷物に責任を負うからである。AI がどれだけ手伝っても人間が責任を取る。あるタスクでエージェントをどれだけ信頼するかは、それ自体が判断であり、モデルが間違える箇所は変わり続けるので、校正を保つには仕事をレビューし続ける必要がある。Anthropic が自社のエンジニアと研究者を調べた研究はこの罠を監督のパラドックスと呼ぶ。「Claude を監督するには、AI の過剰利用で萎縮しうるコーディング技能そのものが要る」。Osmani にとって最も重要で、より良いモデルが解いてくれないのは、何を作るか・なぜそれに価値があるか・誰に影響するか・何を犠牲にするか、という問いである。エージェントはそれを考え抜く助けにはなるが、答えは自分のものだ。仕事と監査の多くは外せるが、説明責任は外せない。

日々の実践

すべてを厳密にやる必要はなく、自分の働き方に合うものを差し込めばよい、と Osmani は書く。

  • 週に一度、エージェントなしで少しコードを書くか、忘れたら困ることを1つ実際にやる。Osmani はこれを校正の練習と呼ぶが、道徳的な意味ではない。
  • 月に一度、やめたことを書き出し、やめたままでよいものを決める。古い記事の問い「AI が無かったらどれだけ迷子になるか」は今も有効だという。
  • 理解を超えるものは学びに行く。見慣れない言い回しに出会ったら一行の説明を検索して済ませることもできるが、Osmani はどこに位置づくかが見えるまで少し調べる方を好む。
  • 機械を正しく点検するのは本物の仕事で、そうでないふりをするとチームはやらなくなる。無料ではないので予定に線項目として入れれば実際にやる。
  • 使わなくなった技能は、想像より速く消える。手放す気のないものは使い続ける。

持ち帰りとして Osmani は次を挙げる。意図的であれ（エージェントはクイズもインタビューも証拠提示もできるが、設定した場合だけ）。スペクトル上の自分の位置に正直であれ。仮説を持て。緑のチェックは1つのことしか意味しない。証拠を見よ（要約の前に何を実行し何が返ったかを読む）。何を決めたかを知るために読め。プロンプトを練れ。基準を決めて守れ。重要な技能は手で使い続けよ。試しに、頼む前に何が起きるかを書き、終わったらエージェントが確認しなかったことを1つ書いて、出力の読み方が変わるか見てほしい、と締める。

他ページとのつながり（wiki 側の推論）

  • cognitive-debt の shin1x1 の「説明できないものは出さない」と、本ページの「保守する人の前で賭けられるか」「自分に帰属させて平気でないものは出さない」は同じ基準線を別の言葉で置いたものと読める。本ページはそれを、コード以外の納品物と検証の設計にまで広げている。
  • ai-review-bottleneck が制約理論で描いた「読んで直す工程」の詰まりは、本ページの orchestration tax と同じ現象である。@smark_x が流入の量と質を絞る5策を出したのに対し、Osmani は「チェックを締めるか減速する」の二択に要約し、セッションを足しても解決しないと同じ結論を置く。
  • ai-teacher-prompt の教師役プロンプトと本ページの「報告書の末尾にクイズを付け、満点までマージしない」は、Anthropic 社内の Stay in the Loop 実践を同じ目的（理解の再構築を手順に焼き込む）で別の形にしたものと考えられる。

問い

  • 「検証済み」を事前に定義する習慣は、このwikiの ingest・weekly のような文章生成の工程にも置けるか。終了線を「ファイルが書かれた」でなく「原文の数値を1つ突き合わせた」に変えると何が変わるか
  • 複数モデルに反対側を論じさせる手順は、ai-review-bottleneck の「読む量が増える」問題と衝突する。どの判断の重さからこの手順を払う価値が出るか
  • 「月に一度やめたことを書き出す」を実際にやったとき、意図せず手放していた技能は何か
