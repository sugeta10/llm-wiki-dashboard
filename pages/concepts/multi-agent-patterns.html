Multi-Agent Patterns

複数のAIエージェントが協調してタスクを処理するアーキテクチャパターン。単一エージェントの限界を超え、専門化と並列実行によって複雑タスクを高速・高品質に処理する。

なぜマルチエージェントか

単一エージェントは「優秀な一人の従業員」。5つのサブタスクを順番にこなすため遅く、全方面に注意が分散して品質も中程度になりやすい。

マルチエージェントは「専門チーム」： - 速度: 並列実行により処理時間が大幅短縮（例: 1時間 → 15分） - 品質: 各エージェントが得意領域に集中するため各パートの品質が上がる - スケール: タスク量が増えてもエージェント数を増やすだけで対応可能

3つの基本パターン

Pattern 1: Pipeline（パイプライン）

エージェントが順番にバトンを渡す直列構成。後のステップが前のステップの出力に依存する場合に適する。

Research Agent → Analysis Agent → Writing Agent → Review Agent
  • 各エージェントが明確な入力・出力を持つ
  • 前段の出力を後段が処理するため、出力フォーマットの統一が重要

Pattern 2: Fan-Out（ファンアウト）

コマンダーエージェントが大タスクを分割し、複数ワーカーエージェントに並列配布する構成。

Commander Agent
├── Worker 1 → analyze document A
├── Worker 2 → analyze document B
├── Worker 3 → analyze document C
└── Worker 4 → analyze document D
  • 同じ操作を多数のアイテムに独立して適用する場合に最適
  • Netflix がビルドログの並列分析に使用するパターン

Pattern 3: Specialist Team（スペシャリストチーム）

異なる専門性を持つエージェントが単一の複雑タスクに協調する構成。

例（製品ローンチ）: - Market Research Agent: 競合データ・市場トレンド分析 - Technical Agent: 実現可能性・アーキテクチャ評価 - Financial Agent: コスト試算・価格モデル構築 - Copy Agent: マーケティング資料・LPコピー作成 - Review Agent: 一貫性・品質チェック

Harvey（法律AI）がこのパターンを採用：リサーチ・判例分析・文書作成・コンプライアンス確認を専門エージェントが分担し、完全な法律パッケージを生成。

Anthropicの5パターン（Claude Code公式）

Anthropicが公開したマルチエージェント協調パターン。「まず Orchestrator-subagent から始め、困った課題が出たら別のパターンへ進む」という進め方を推奨している。

# パターン 強み 弱み 推奨環境
1 Generator-Verifier 品質が重要で検証基準を明示できる 基準が曖昧だとVerifierが機能しない Local
2 Orchestrator-subagent 短く明確なサブタスクに分解できる（★推奨スタート） 親がボトルネックになりやすい Local
3 Agent Teams 長く・並列・独立して走れる仕事がある Worker間の衝突・完了検知が難しい Cloud
4 Message Bus イベント駆動で処理が分岐しエージェントが増える デバッグとイベント追跡が難しい Cloud
5 Shared State 互いの発見を参照しながら探索を深める共同調査 終了条件がないと無限ループ Cloud

Generator-Verifier

一方が案を出し（Generator）、もう一方が審査する（Verifier）。NGなら差し戻してループ。「テストが全件通るか」「SQLインジェクションのリスクがないか」のような明示的な検証基準が必須。差し戻し上限とフォールバックも設計する。

Orchestrator-subagent

Claude Code自体がこのパターンの実装例。Orchestratorがタスクを分解してサブエージェントに並列配布し、最後に結果を統合。Pipline・Fan-Outパターンの実装に相当。

Agent Teams

Workerエージェントが担当領域の文脈を長期保持しながら走るパターン。Orchestrator-subagentとの違いはWorkerが生き続けること。ローカルでは耐障害性・競合管理の限界がありCloud（ECS Fargate + SQS FIFO）推奨。

Message Bus

EventBridgeなどをハブに各エージェントがpublish/subscribeで連携するイベント駆動型。疎結合でエージェント追加が容易だが、デバッグのために全イベントのログ記録が実質必須。

Shared State

中央司令塔なしに全エージェントが共通ストレージを読み書きして協調。終了条件（「最後の更新から30分経過」「調査エントリ100件超」など）を最初から明示的に設計しないと無限ループになる。

実装ステップ

Step 1: チームを設計する

実装前に以下を定義する: 1. 全体目標は何か 2. サブタスクの一覧 3. 並列実行可能なサブタスクと順次実行必須なサブタスクの分離 4. 各サブタスクの担当「スペシャリスト」は誰か

Step 2: 各エージェントを設計する

各エージェントに必要な3要素: - 明確な役割: "あなたは競合価格アナリストです。5つの競合製品の価格変化を追跡します" - 専用ツール: Web検索・ファイルアクセス・DB接続など役割に必要なもののみ - 定義済み出力: {"competitor_name": ..., "old_price": ..., "new_price": ...} のような構造化フォーマット

最重要: エージェント間の出力フォーマットを標準化すること。構造化されていないテキストと構造化JSONのミスマッチがハンドオフ失敗の最大原因。

Step 3: オーケストレーションを構築する

claude-managed-agents ではAPIでマルチエージェント協調をネイティブサポート。決定すべき事項: - どのエージェントを並列実行するか（互いに依存しないもの） - どのエージェントを順次実行するか（前段の出力を必要とするもの） - エージェント間のデータ受け渡し方法（共有ファイル・構造化出力・直接通信） - フォールバック動作: あるエージェントが失敗した場合の処理（パイプライン全体をクラッシュさせない）

Step 4: Dreaming でメモリを強化する

claude-managed-agents の Dreaming 機能: セッション間でエージェントが過去の学習を活用できる。Harvey での実績は完了率約6倍向上（プロンプト変更なし）。

Step 5: Outcomes で品質ループを定義する

成功基準をルーブリックとして定義し、エージェントが自己評価・反復する仕組みを設定する。

Step 6: シンプルなタスクから始める

2エージェントのパイプラインから始める。通信・出力フォーマット・エラーハンドリングを確認してから段階的に拡張する。10エージェントシステムを最初から設計しない。

Step 7: モニタリングと反復

注意すべき問題: | 問題 | 症状 | 対策 | |------|------|------| | ハンドオフ失敗 | 次エージェントが前の出力をパースできない | 出力フォーマット仕様を厳密化 | | 冗長な作業 | 複数エージェントが同じことをする | 各エージェントのスコープを極めて具体的に | | 品質劣化 | パイプラインが長くなるにつれ品質低下 | 重要チェックポイントにレビューエージェントを追加 | | トークン肥大 | エージェントが不必要に冗長な出力を生成 | 出力長に制約を追加 |

よくある失敗と回避策

  1. エージェントを汎用にしすぎる: 専門化こそマルチエージェントの価値。各エージェントは1つのことを極める
  2. 出力フォーマット非標準化: エージェント間の「データ契約」（フィールド・フォーマット・欠損時の扱い）を事前に定義する
  3. 最初から多並列: 2エージェントから始めて段階的に追加する
  4. エラーハンドリングなし: 「価格データが取得できない場合は過去データで継続し、レポートにフラグを立てる」のような明示的なフォールバックを定義する
  5. トークンコスト無視: マルチエージェントは単一エージェントより多くのトークンを消費する。プロンプトを簡潔に保ちコストを監視する

実装例（本番稼働）

週次市場インテリジェンスレポート: - Agent 1〜3（並列）: Web調査・競合モニタリング・SNSリスニング - Agent 4: 分析（1〜3の結果を受取り、重要な5事象を評価） - Agent 5: レポート執筆（分析結果から経営サマリー作成） - Agent 6: 品質レビュー（ルーブリック採点・修正依頼）

結果: 手動で半日 → シングルエージェントで1時間 → マルチエージェントで15分

採用企業: - Netflix: 数百ビルドのログを並列分析（Fan-Out パターン） - Harvey: 複数文書にまたがる法律作業の協調（Specialist Team パターン） - Shopify: 2026年Q3までに自律コーディング90%を目標

フリーランス・個人活用

Anthropicが公開しているエージェント量産手法は、英語圏のフリーランサーがいち早く活用し始めているとされる。数百体規模のエージェントを並列稼働させることで、従来は企業が担っていた規模の仕事を個人が請け負える可能性がある。ai-income-retirement-strategy の「AIによる収益自動化」戦略とも親和性が高い。

観察ログ（未検証）

  • 2026-03-15 (@akshay_pachaar): サブエージェントとエージェントチームの本質的な違い:
  • サブエージェント（fire-and-forget）: 独立コンテキストで短命動作。完了結果のみ親に返す。エージェント間通信なし。目的は「コンテキスト圧縮（膨大な探索を信号に凝縮）」
  • エージェントチーム（ongoing coordination）: 長期稼働・ピアツーピア直接通信・共有タスクリスト（blockedBy フィールドで依存管理）。リードが常に介在しなくてよい
  • 2026-03-15: コンテキスト中心分解（Context-centric decomposition）: タスクを役割ではなく「コンテキスト境界」で分割する。2つのサブタスクが深く重複するコンテキストを必要とするなら同一エージェントへ。コーディングエージェントが機能実装とテストを両方担当すべき理由もこれ（ハンドオフでコンテキストが劣化するコスト > 並列化の利益）
  • 2026-03-15: 5つの古典的オーケストレーションパターン（Anthropic公式5パターンとは別の分類）:
  • Prompt Chaining: 前ステップ出力を次ステップが処理する順次型。順序と依存がある場合
  • Routing: 分類器がタスクを専門ハンドラーへ振り分け。難易度でモデル選択しコストを制御
  • Parallelization: 独立サブタスクの同時実行（同一タスク複数実行→投票、または異なるサブタスクの並列）
  • Orchestrator-Worker: 中央エージェントが分解→ワーカーへ委任→統合。本番の最多構成
  • Evaluator-Optimizer: 生成と評価のループ。品質重視・1パスでは信頼できない場合
  • 2026-03-15: コーディングでの特別な注意: 並列エージェントが同時にコードを書くと互いに矛盾する暗黙の前提を持ち込む。コーディング用サブエージェントは調査・探索に留め、コードの同時執筆はしない
  • 2026-03-15: マルチエージェントを使うべき3条件のみ: コンテキスト保護（サブタスク情報が親に不要）・真の並列化（独立した調査）・専門化（矛盾するシステムプロンプトが必要 or ツール過多でパフォーマンス劣化）
  • 2026-03-15: 3つの典型失敗パターン: ①曖昧なタスク記述→複数エージェントが重複作業（明確な目標・出力フォーマット・スコープが必須）, ②検証エージェントが実際に検証せず完了宣言（明示的かつ具体的な検証基準が必須）, ③トークンコストの指数的増大（モデル階層化とバジェット制御が必要）
