エバーグリーンノートをCLAUDE.mdで育てる（tokuhirom / 64p.org）

TL;DR: 調べ物に答えた直後に「これをノートに残すか」をAIから聞かせる一条を置くと、日々の質問がそのまま個人ノート網の成長に変わる。

AIに調べ物を頼んで答えを得た時点で、その内容はふつう会話ごと流れて消える。tokuhiromが自身の公開ノートサイト64p.orgのCLAUDE.mdで実装しているのは、回答の終端に分岐を1つ差し込むことである。「〇〇ってどういう用途なの？」のようなオープンクエスチョンに答えたら、その内容を /notes/ に書き残すかどうかを聞くこと——この一条があるだけで、質問のたびにノート化の機会が発生する。tokuhiromはXで「こんな感じでやると自分のノートがどんどん育つ。何言ってんのかよくわからん用語とかあったらさらに質問すればさらに育つ」と述べている。ノートの狙いはAndy Matuschakのエバーグリーンノート、つまり使い捨てのメモではなく時間をかけて育ち他のノートと繋がっていく知識のネットワークだと、CLAUDE.md冒頭で明示されている。

flowchart TD
  Q["素朴な質問"] --> S["WebSearch/WebFetchで最低1回裏取り"]
  S --> A["回答"]
  A --> P1["「ノートに残しますか？」と提案"]
  P1 --> N["notes/src/*.md を新規作成"]
  N --> L["既存ノートをgrepし双方向にウィキリンク化"]
  L --> C["git commit（pre-commitでcreated/updated自動付与）"]
  C --> B["regen-index.pl：HTML・タグ・バックリンク生成／リンク切れ警告"]
  N --> P2["「この用語も別ノートに切り出しますか？」と提案"]
  P2 --> Q

育つ仕組みは「提案させる」2つの条文

ノート網が伸びる駆動力は、書き方のルールではなく2つの能動的な提案にある。1つは上記の追記提案。もう1つはノート切り出し後の深掘り提案で、新規ノートを作ったらその本文中に「まだ独立ノートになっていないが深掘りの余地がありそうな概念」——説明の中で触れただけの関連用語や隣接概念——が残っていないか確認し、「〇〇についても別ノートとして切り出して調べられそうですが、書きますか？」と提案せよ、と指示している。分割した直後もさらに切り出せる概念がないか確認する。1本のノートが次のノートの候補を吐き出す構造になっており、これが「わからない用語をさらに質問すればさらに育つ」の実体だと考えられる。

エバーグリーンノートの原則を6条に落とす

CLAUDE.mdはノートの設計原則を6つ挙げている。

  1. 原子性 — 1ノート1概念。複数概念を詰め込まず別ノートへ切り出し、ウィキリンク（ファイル名 記法）で繋ぐ
  2. 概念指向 — 出来事の記録や単なる要約でなく、概念・トピックそのものを主語にする
  3. 密度の高いリンク — 新規ノート作成時に既存ノートをgrepして今回のトピックへの言及を探し、プレーンテキストで言及している箇所を見つけたらそちら側もリンク化する
  4. 連想的オントロジー優先 — フォルダ階層でなくウィキリンクと #tag で関連付ける
  5. 自分のために書く — 前置きや読者への配慮は不要、ラフなメモでよい
  6. 追記後は章構成を見直す — 追記した節だけでなくノート全体の見出しの重複・順序・冗長な繰り返しを点検し、必要なら既存見出しの位置や粒度も直す

原則3が片方向でなく既存ノート側の書き換えまで含む点と、原則6が追記のたびに全体構成へ戻る点が、放置すると継ぎ接ぎで劣化するノートの実務的な歯止めになっている。原子ノートが同じ分野に3つ前後たまったら、深掘りせず配下ノートの位置づけを一言ずつ添えて束ねるハブノート（MOC: Map of Content）の作成を検討し、配下側にも ## <ハブノート名>の中での位置づけ という見出しで逆リンクを書く。

「何を主語にするか」を分岐条件で指定する

素材の種類ごとにノートの主語を決める条文があり、ここが要約の質を左右する。技術記事のURLを渡された場合、記事・発表・実装そのものが有益なら記事のトピックを主語にし、記事が要素技術の紹介にとどまるなら記事ではなく紹介されている要素技術を主語にする（記事は概念の入り口として使う）。X上の発言を発端にする場合は、投稿を主とした構造にし、「Xでこう言っていた → それを踏まえてこう考えた」の順で書いて、地の文で発言内容を要約・言い換えて済ませない。ステータスURLを単独行で貼ればビルド時に公式ウィジェットの埋め込みへ変換されるので、引用構文で本文を手打ち転記する必要もない。海外ブログの紹介でも同様に、原文の内容・構成を尊重し、自分の考察は別セクションに分ける。

捏造を防ぐ側の条文

育てる仕組みと対になって、混入を止める条文が置かれている。

  • 事実・知識を問う質問には、自分の知識だけで答えられそうに見える一般的な質問も含めて憶測で即答せず、最低1回はWebSearch/WebFetchで裏取りしてから答える（カットオフ以降の新情報と記憶違いを避けるため）
  • 検索が空振りしたとき「これはおそらく〇〇というジャンルの話だろう」という思い込みで検索語を狭めたまま再検索を繰り返さず、まずジャンルの決め打ち自体を疑って固有名詞単体や中立的な語へ広げ直す
  • 根拠のある出典がない情報は載せない。裏取りできなかったものは書かないか推測と明記し、ウェブ調査の内容は末尾に「出典」セクションを設けてリンクする
  • 特定のプロダクト・技術・サービスを批判・けなすニュアンスを入れない。出典記事が「カルト」のような評価的・煽情的な語で形容していても、それを見出しや地の文へ持ち込まず背景の客観的事実だけを抽出する
  • 医療トピックは厚生労働省など国内の公的機関を優先する（技術・プロダクトでは海外の一次情報を優先するという方針の明示的な例外。診断基準・治療方針・薬剤の扱いは国内運用に依存するため）

手を動かした記録は別ノートに切る

説明を読むだけでなく実際にマシン上でコードを書いて動かしてから書け、という条文もある。ネットワーク・カーネル周りは動かさないと理解が浅くなりがちなため最小限の実験コードを優先的に検討する、という理由づけが添えられている。ただし実験の記録は概念ノートに混ぜ込まず <トピック>-experiment.md として切り出し、概念ノート側からリンクする（原則1の原子性）。実験ノートには目的・使った素材・躓いた点と対処・実行結果・コードから読み取れることを書き、感想ではなく再現可能な記録にする。実行前には何を試すかを説明してユーザーの許可を取る。

決定論的な足回りをAIに任せない

日付とリンク整合性は人間にもAIにも書かせていない。git commit 時にlefthookのpre-commitフック（update-note-dates.pl）がステージされた notes/src/*.md のfrontmatterに created / updated を付与・更新する。ファイルの stat() のmtimeには依存させていない——新規cloneやCIのビルドではmtimeが壊れるためで、frontmatterが無い場合のみmtimeへフォールバックする。ビルドの regen-index.pl がHTML・タグページ・バックリンク（「🔗 リンクされているノート」）を自動生成し、存在しないファイル名へのウィキリンクはビルド時に警告が出るので気づける。生成物は .gitignore され、GitHub Actionsがデプロイのたびに再生成する。mdのみの変更はPRを作らず直接masterへpushしてよく、テンプレートやビルドロジックに手を入れたときだけPRを作る、という運用の軽重も条文化されている。

記法を増やすほど誤爆する問題を、仕様側で潰す

ウィキリンク・タグ・図・数式と記法を足していくと、本文中のただの記号がリンクやタグに化ける事故が増える。64p.orgのCLAUDE.mdは、その境界を仕様として明文化している。

タグは # の直後が英字または日本語（Unicodeの「文字」全般）で始まるものだけを認識し、数字・アンダースコア始まりは弾く。これは #1234 のようなIssue/PR番号や #40262 のような参照番号をタグと誤認しないための制約だと理由まで書かれており、日付や連番をタグに使わないことも併記されている。foo#bar のように直前が英数字の場合も、URLフラグメント（...#section）やC#のような固有名詞と区別できないため無視する。一方で句読点や括弧の直後（文末。#tag）は認識するので、日本語の文はスペースなしでタグを続けられる。見出し行 # タイトル が誤認識されないのは、# の直前が空白か行頭であることを要求しているためである。英字タグは小文字へ正規化される（#AI と #ai は同一）が、日本語タグは正規化されないため表記ゆれがそのまま別タグになる、という副作用も明示されている。

そして ...・#tag・$$...$$・\(...\) のいずれも、コードブロック・インラインコード・数式ブロックの中では解釈されない。#include や #!/usr/bin/env、シェルの $$ を含むコード例を安全に貼れる。図と数式はビルド時に mermaid のフェンスを <div class="mermaid"> へ、TeX記法を <div class="math-display"> / <span class="math-inline"> へ変換し、閲覧時にmermaid.jsとKaTeXをjsdelivr CDNから遅延読み込みしてクライアントサイドでレンダリングする。図や数式を含むノートのページだけがライブラリを読み込むので他ページには影響せず、mermaidはダーク/ライトテーマの切替にも追従して再レンダリングされる。ネットワーク構成図・シーケンス図・状態遷移はASCIIアートで代用せず図で、数学・信号処理・物理の式はユニコード文字で代用せずTeX記法で書け、と使いどころまで指定されている。ハブノートに付ける #moc タグは、/notes/tags/moc.html でハブノート一覧を一望するための約束事である。

問い

  • このvaultのCLAUDE.mdのQuery操作には「新しい洞察があれば追記」とあるが、回答後にノート化するかを聞くという一手は無い。提案を挟む方が実際に育つのか、それとも聞かれること自体が摩擦になるか
  • 原子性（1ノート1概念・積極的に切り出す）と、このvaultのingestの粒度判定（既存ページへ統合する方に倒しがち）はどちらが後のQueryに効くか。tokuhiromは切り出し側、こちらは統合側に倒している
  • 「一般的に見える質問にも最低1回は裏取り」を全質問に課すコストは見合うか。裏取りの有無を質問の種類で分ける基準は作れるか
  • このvaultはタグをfrontmatterの tags: に置き本文に #tag を書かないので、ウィキリンク以外のフラットな関連付け手段を持っていない。64p.orgの #tag に相当する横串（例: #moc でハブノートを一望する類）は必要か、それともindex.mdが代替しているか
