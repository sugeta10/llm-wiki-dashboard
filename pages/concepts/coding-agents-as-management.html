コーディングエージェントがあなたをマネージャーにした（Addy Osmani）

TL;DR: エージェントと一日中働くことは、タスクを選び・指示を書き・委任し・追い・評価し・何を出荷するか決める「管理」そのものだと Addy Osmani（Claude Code チーム）は書く。エージェントから最も成果を引き出すのはプロンプト技術が上手い人ではなく管理を学んだ人であり、良いエンジニアリングマネージャーの実践（検証手段を渡す・文脈を渡す・修正を複利にする・判断は任せ譲れぬ線だけ強制する・計画を先に置く・早く舵を切り速くやり直す・判断は委任しない・無人の走行を設計する・注意でなく検証を拡張する・作らないことを決める）が、影響の大きい順にそのままエージェント運用の実践になる。

Osmani がこの主張を「歓迎されないかもしれない」と断るのは、尊敬するエンジニアの多くが仕事に近くいたくて個人貢献者（IC）の道を選び、マネージャーになった友人がカレンダーの中に消えていくのを見てきたからである。Osmani の言う「管理」はその像ではなく、「他者の仕事を可能にすることで良い成果を生むこと」という限定した意味で、エージェントがマネージャーや同僚の代わりになるとも言っていない。悪いマネージャーへの不満はすべてエージェントとの対話のバグ報告になる、と Osmani は書く。曖昧で文脈を欠き期待が動き続ける引き継ぎを受けた経験があるなら、良い引き継ぎがどういうものかを IC は既に知っているからだ。この記事は Osmani の前作2本（「コーディングエージェントにはマネージャーが要る」は wiki 未収集、委任の静かなリスクである認知的降伏は critical-thinking-with-agents）に続くもので、良いエンジニアリングマネージャーの実践と、Claude Code を使い作る中で分かったことを対応づけ、影響の大きい習慣から順に並べている。

  A --> V["検証器を実行<br/>テスト・ビルド・lint・スクリーンショット"]

  V -->|合格| P["証拠を提示<br/>実行したコマンドと出力"]

  R --> D["人間が判断<br/>製品・セキュリティ境界・出荷"]

1. 自分の仕事を確かめる手段を渡す

良い実践: テスト・ビルド・スクリーンショットのような検証の機構を与え、結果を証拠として見せさせる。アンチパターン: 「終わったように見える」を確認と見なし、自分がエージェントのテストスイートになる。

経験あるマネージャーに「全部を読まずにチームの仕事の質をどう確信するか」と聞けば、CI・コードレビュー・ダッシュボード・オンコールといったガードレールの話をする、と Osmani は書く。ガードレールを作らない未熟なマネージャーは自分で全部を検証し、四半期のうちにボトルネックになる。エージェントも同じで、Claude Code のベストプラクティスガイドが説明するとおり、エージェントは作業が終わったように見えた時点で止まる。検証が無ければ「終わったように見える」が唯一の検証になる。検証手段があれば、作業する→検証器を走らせる→失敗を見る→自分で直す、をエージェント自身が回せる。UI の変更なら、実際にブラウザでページを開いて動き・見た目が良くなるまで繰り返させる。

検証機構は合否が確定的に出るものなら何でもよい。テスト・ビルドの終了コード・リンター・差分スクリプト・スクリーンショットが例である。ガイドは、その検証を走らせるコマンドが CLAUDE.md（エージェントが毎セッション最初に読む指示ファイル）に置ける最も有用な1行だと述べる。検証をワークフローに入れる4つの方法を Osmani は挙げる。

  • 頼む: 「終わったら auth のテストを走らせ、通るまで続けて」
  • ゴールを設定する: /goal で別モデルが毎ターン後に条件を判定する。長い背景作業で最も有用（claude-code-goal）
  • 強制する: Stop hook で型検査が通るまでターンを終えさせない
  • レビューさせる: /code-review が会話を見ていない新しいサブエージェントに差分を送る。著者が自分の PR を承認しないのと同じ

レビューの範囲は制御できる。「問題を探せ」と頼めば必ず何か見つけるが、「正しさの問題だけを探しスタイルは無視せよ」と頼めばそうする。良いマネージャーがフィードバックの頼み方を学ぶのと同じだ、と Osmani は言う。Skills・hooks・subagents・MCP という Claude Code の道具立ての大半は、仕事をすることと仕事を検証することの隙間を埋めるためにあり、人の注意はエージェントが検証できなかったものだけに向ける。経験あるエンジニアリングマネージャーがやっていることと同じである。

2. 明確な文脈を設定する

良い実践: リポジトリを見ても分からないこと（タスクの目的と重要な理由・制約・スコープ外・成功基準）を要約して渡す。アンチパターン: 1行のタスクを渡して本当の期待は頭の中に置く。あるいはコードを読めば分かることでブリーフを膨らませる。

効果的なマネージャーは望む成果・制約・目的を明確に書き、どうやるかは仕事をする人に任せる。軍では commander's intent、Netflix では「context, not control」と呼ぶ、と Osmani は書く。エージェントとの難しさは、何の文脈が欠けているか分かりにくいことにある。エージェントが最初にするのはコードを読むことで、現行モデルはフォルダ構造・規約・テストの設定を人が説明するより速く掴む。書く前に、エージェントが自力で分かることは何かを考える。コードに書いてあって実際に読みに行くなら、言わなくてよい。言葉はリポジトリに無いもの、たとえば会議での決定・誰かのデプロイ手順・なぜこのタスクが重要か・今回の「完了」が何を意味するかに使う。記事には「ダッシュボードを速くして」という曖昧な依頼をプロンプトに変換する例があるが、数値を含むプロンプト本体は画像でキャッシュに未収録である。

毎タスクでやる必要はない、と Osmani は書く。探索的な作業なら汎用的なプロンプトで進めながら少しずつ詰めればよい。プロンプトを書く準備ができていないなら、エージェントに仕様が書けるまで自分をインタビューさせ、仕様をファイルに保存し、新しいセッションでそこから作らせる。その仕様は後でレビューの基準にもなる。Issue トラッカー・エラーダッシュボード・チームチャットのような他の道具へのアクセスも必要なら渡す。チームの新入社員と同じ扱いをする。gh のように既に知っている CLI なら何も言わなくてよいことが多い。

3. すべての修正を複利にする

良い実践: 同じことを2回以上直したら、チームの CLAUDE.md に書くか共有スキルにする。時間が経ったら、新しいモデルでその修正が不要になっていないか確かめる。アンチパターン: 毎セッション手で直す。自分のマシンにしかない暗黙知に頼る。

CLAUDE.md の価値を最大化するチームは半ば頻繁に更新し、防ぐ価値のある失敗から得た教訓を書き残す。コードレビューで @claude をメンションしてフィードバックを恒久的な方針に変えるチームもある、と Osmani は書く。CLAUDE.md は簡潔に保つ。入れるべきものは次の4種である。

  • 検証のやり方（正確なコマンド）
  • 誤解を招くコード領域
  • リポジトリに無い決定
  • 2回直したこと

どれも書かれた情報の複利の例で、人がチームを去りモデルが置き換わっても残る。

4. 判断は任せ、曲げられないものだけ強制する

良い実践: 既定ではエージェントに判断させ、常に起きなければならない・決して起きてはならない少数のことだけを hooks や deny ルールで強制する。アンチパターン: ALL CAPS のルールを書く。任意の好みに hook を定義する。古いモデル向けの習慣を、新しいモデルが卒業した後も維持する。

Andy Grove の『High Output Management』はこれを task-relevant maturity と呼ぶ。監督の度合いは、その人の全体的な能力ではなく、その特定のタスクでの実績に依存させる。新任マネージャーへの古い助言も同じことを言っていて、自分が心地よいより少し広い裁量を与えつつ、支え、責任を持たせる。Claude Code はこれを明示的にしている、と Osmani は書く。プロンプト・CLAUDE.md・スキルはモデルが検討して従うか選べる要請で、hooks・deny ルール・managed settings は常に強制される要件である（公式の振り分けフレームは claude-code-instruction-methods）。多くの場合はエージェントに判断させたい。実際のコードを見ているモデルの方が、事前に決めたルールよりもガイドラインが当てはまるかを判断しやすい場面が多いからだ。強制は「生成されたクライアントは編集しない」「ライセンスヘッダーのスクリプトは必ず走らせる」のような硬い要件に使う。新しいターミナルと VS Code のセッションは auto mode で始まり、本番へのデプロイや他人の作業への force push のような安全でない振る舞いを分類器が除外する、と Osmani は書く。

ガイドの助言には両面がある。CLAUDE.md の1行をいくら強調してもエージェントが拾わないなら、それは hook にすべきである。逆に hook が要件ではなく好みを表しているなら外して、エージェントに判断させる。チームがもう役に立たないプロセスを廃止するのと同じだ。新しいモデルが出たときにも調整する。ガイドはやめてよい習慣の一覧を持っていて、ALL CAPS の指示・「もっと深く考えて」（effort は設定項目になった）・「怠けるな」が挙がる。現行モデルではこれらは過剰な強制と過剰な作業につながる。エージェントにおいては過剰なプロセスが新しいマイクロマネジメントである、と Osmani はまとめる。

5. 作る前に計画する

良い実践: 着手前に合意した計画を置き、隠れた前提を読み取り、重ならない並列作業に分割する。アンチパターン: 複数のエージェントに重なるタスクを同時にやらせ、午後をマージ競合と重複した決定の解消に使う。

良いワークフローは、まずプランモードに入って正しい計画になるまで反復し、それからコーディングを委任することだ、と Osmani は書く。良い計画があればモデルは一回で全部を作れることが多い。大きなタスクでは別のセッションを使い、スタッフエンジニアがするように計画を見る。これは設計レビューであり、誤った方向を捕まえる最も安い場所である。計画をレビューするときは隠れた前提を探す。1on1 なら「何が不確かか」と聞くのに相当する。

分解はエージェントに委任されつつある。Claude Code の /batch は大きな機械的変更を5〜30のタスクに分け、計画を表示し、別々の worktree（リポジトリの別チェックアウト）で実行し、各タスクに PR を作る。人が仕事を分ける必要はなくなり、スライスの重なりを確認し、共有インターフェースを先に入れることだけ見る。これが無いと偽の並列度が生まれる。重なるタスクを持つ5体のエージェントは5倍の成果ではなく、著者5人のマージ競合1件になる。

6. 早く舵を切り、速くやり直す

良い実践: 最初の1分を見て舵を切る。逸れたと見えたらすぐ直す。修正を2回失敗したら、新しいセッションでより良いプロンプトから始める。アンチパターン: 3回目・4回目の修正を重ねて、依頼そのものを直さない。

経験あるマネージャーは、有能な人が何度も外すなら問題は上流、つまり指示・文脈・スコープにあるかもしれないと知っている。エージェント版は明示的で、逸れたら Esc を押す。2回修正に失敗したらセッションをクリアし、学んだことを入れたより良いプロンプトを書く。3回目の修正は、モデルが読み直し処理し直さなければならない情報（失敗した試みを含む）を増やすだけだ、と Osmani は書く。

安い巻き戻しも状況を変えている。/rewind はコードと会話を以前の地点に戻すので、まず野心的な方法を試すリスクが下がる。良いマネージャーは部下にも同じことをする。取り消しが安いなら野心的な方法を試させ、後でふりかえりを行い、該当すれば直し方を一般化して CLAUDE.md に入れる。

7. 仕事は委任し、判断は決して委任しない

良い実践: エージェントが仕事をし、人が重要なこと（製品判断・セキュリティ境界・何を出荷するか）を決める。すべての差分を、自分が呼び出されるつもりで扱う。アンチパターン: テストが緑で名前が妥当だからと大きな差分を承認する。それはコードレビューではなくコードの追認（code ratification）である。

「部下が出荷したのであって私ではない」と言えるマネージャーはいない。走らせるすべてのエージェントについて同じだ、と Osmani は書き、自分の失敗を挙げる。競合とのギャップを調査してローカルの PR を書けとエージェントに指示し、調査を読み、コードを流し読みし、ユーザーにとって得るものが少ないのに複雑さを増す変更をもう少しで push するところだった。仕事を委任し、判断まで委任しかけた。600行の差分で名前は妥当でテストは緑、だから承認、という罠には落ちやすい。

分担は次のようにするのが理にかなう。スタイル・lint・レビューへの追従・典型的なバグ・ユニットテストはエージェントに、セキュリティ境界・コンプライアンス・製品判断は人に。調整も同じで、引き継ぎの追跡はエージェントができるが、競合する要求の裁定と人に実際にコミットさせることは人の仕事である。

すべての変更の内側のループにいる必要はない。所有すべきは外側のループで、制約は何か・出力をどれだけ実際に読むか・どの証拠を残すか・人が何にサインオフするか、である。変更は小さく保つ。レビューの単位は理解の単位だからだ。

8. 自分を必要としない走行を設計する

良い実践: 自律タスクを走らせる前に、完了の定義・自己検証・境界・ガードレール・人の承認を定める。アンチパターン: 完了の定義も停止点も無いまま就寝前に長時間プロセスを始め、翌朝、誤った前提で一晩働き続けたモデルを見る。

スキップレベルのマネージャーは個々のエンジニアの仕事ではなく、目標・ガードレール・チェックポイント・リードの仕事を管理する。AI エージェントも似た軌道にある、と Osmani は書く。すでにタスクの一部をサブエージェントに委任し、スケジュール・CI の失敗後・新しい PR が開いた後に自律的に走れる。フロンティアは、自律的に開始し、自己検証し、判断が要るときだけ人を呼ぶ自己統治システムである。人の役割はセッションを制御することからループを設計することへ移る（loop-engineering）。無人の走行を設計するときの5つの問いは、良いマネージャーがシニアエンジニアにプロジェクトを渡して休暇に出る前に聞くものと同じだという。

  1. 完了が何か知っているか（ゴール条件・仕様ファイル・緑にすべき失敗テスト）
  2. 自己検証の機構があるか（テストスイート・Stop hook・レビュー工程）
  3. 境界は何か（権限制御・サンドボックス・worktree・push してよい1本のブランチ）
  4. ガードレールは何か（ターン上限・支出上限）
  5. 出力はどこに出て、誰が承認するか（PR か要約、非可逆の行為は人が承認）

ガイドにはマネージャーが良い実践と認めるであろう習慣がさらに2つある。パイロット、つまりバッチジョブをまず3ファイルで走らせ、プロンプトを直してから残りを回すこと。そして新しいものは最初の数回を見てから無人を信頼すること。試用期間と考えればよい、と Osmani は書く。

9. 注意でなく検証を拡張する

良い実践: チェック・ゴール・新しい文脈のレビュアーが監視を引き受けられる速さでだけエージェントの利用を増やし、スループットに加えて品質を測る。アンチパターン: よくレビューできる数より多くのセッションを開き、AI が書いたコード量で成功を測る。

マネージャーは管理限界（span of control）をすぐ学ぶ。直属の部下が一定数を超えると全員がマネージャーの時間を減らされ、品質が落ちる。エージェントも同じで、Osmani はこれを orchestration tax（オーケストレーション税） と呼ぶ。最初の数体を超えると、追加の1体ごとに前より多くの注意を要する。Osmani 自身は多くの日に背景エージェント4〜5体とローカルセッション数本を回し、それでも多すぎる日があると書く。

多数のセッションを管理するのは超集中の問題ではなく、監視の大半を自己評価・ゴール・新しい文脈のレビュアーに委ね、注意を判断のために取っておくことである。ポーリングではなく通知、背景ジョブの一元ビューも助けになる。監視を増やすことでエージェントを増やすことはできず、監視の必要を減らすことでしか増やせない。そのうえで活動ではなくシステムを測る。有用な指標は PR のサイクルタイム・新メンバーの立ち上がり時間・revert や手戻りの頻度である。AI が書いたコードの割合を測るのは有用な目標ではない。目指すのは品質と信頼性だからだ。Grove の「対抗指標とともに測る」の規則がここに当てはまる。マージされた PR 数を測るなら、revert と手戻りも測る。

10. 作らないことを決める

良い実践: 誰が必要としているか・どう効いたと分かるか・何があれば止めるかを問い、仕掛り（WIP）を制限する。アンチパターン: 作るのが安いからと、もっともらしいアイデアを全部 PR に投げる。結果、チームがレビューし・セキュリティを確保し・保守しなければならない雑多な引き出しができる。

マネージャーが言う最も重要な言葉はしばしば「ノー」である。エージェントがあるとノーと言うのは難しくなる、と Osmani は書く。始めるのはほぼ無料で、昼までにどんなもっともらしいアイデアも PR にできる。だが残るのは、チームがレビューし・守り・支え・保守しなければならない PR の山である。レビューと検証が今や希少資源になった。昔からの管理の問いの重要性はむしろ増している。誰が求めたのか。成功をどう測るのか。いつ止めるかをどう知るのか。作るのが安いなら、難しい問いは「できるか」ではなく「すべきか」である。

アナロジーが破れるところ

良い実践: 管理のベストプラクティスに従いつつ、エージェントというモデルの差（安い手戻り・同意の速さ・モデルのリリースごとに移る強み）を織り込む。アンチパターン: エージェントをジュニア開発者と同じだと考える。5体を回せるから5人を管理する準備ができていると思う。

アナロジーは有用だが不完全で、この仕事の優れた実践者はどこが不完全かを知っている、と Osmani は書く。

  • 人の管理の方が難しく、技能は戻らない。 5体のエージェントを回したからといって5人を管理する準備にはならない。動機・衝突・キャリア開発・月単位の信頼構築に相当するものは無い。
  • 手戻りがほぼ無料。 人には決して頼めないことをエージェントには頼める。ホワイトボードで起きるような技術論争なら、エージェントに2〜3案を作らせて比較できる。
  • エージェントに経験は無く、ノートがあるだけ。 auto memory は1台のマシン上のメモに過ぎず、同僚のセッションには移らない。キャリアを通じて培う経験と判断ではないので、教訓はチーム全体のために書き残す必要がある（同じ問題を扱うのが skills-over-memory）。
  • エージェントは熱心で自信がある。 良いエンジニアに間違ったことを頼めば押し返すが、エージェントは言われたことをやりがちで、人は過信しがちである。Wharton の認知的降伏の研究では参加者は誤った AI の答えをほとんどの場合受け入れ、しかも自信を深めた。自分の答えに反論させることで過信に対抗できる。
  • アーキタイプは1つだけで、数か月ごとに変わる。 人のチームは多様な技能と強みを持つが、すべてのエージェントは同じ強みと弱みを持ち、それがモデルのリリースごとに移る。
  • ジュニア開発者の育成は依然必要。 エージェントが初級の仕事を引き受けると、ジュニアが基礎を学ぶための反復をマネージャーとして意図的に作らなければならない。
  • 人のチームは依然重要。 エージェントの管理に一日を使い、まとまったチームを作るための時間を押し出していることに気づかないことがある。そうしてはいけない、と Osmani は書く。

肩書は要らない

良い実践: 良いソフトウェアが生まれるようにすること、つまり文脈を設定し・完了を定義し・よくレビューすることに力を注ぐ。アンチパターン: ブリーフ不足で未チェックのエージェントを回しながら、コードの行数で自分を評価する。

良いスタッフエンジニアは昔からこうだった、と Osmani は書く。設計文書を書き、文脈を設定し、徹底的にレビューし、周囲の人を良くする。エージェントは全エンジニアに初日からそれをさせ、管理の速習コースになる。フィードバックは四半期ではなく分単位で返り、自分の誤りは自分で取り消せる。仕事はコードを書くことから、良いコードが書かれる理由になることへ移りつつある。生まれつきの名マネージャーも名エンジニアもおらず、技能は昔と同じく練習で作る。ただしエージェントがあれば練習は安い。Osmani が試してほしいこととして挙げるのは次の6つである。

  • すべてのタスクに、実行できるチェックを。証拠を求める
  • エージェントに見えないことを伝え、見えることは省く
  • コードを書く前に計画を話し合う
  • 2回直したことは CLAUDE.md に記録する。繰り返す作業フローはスキルにする
  • 2回修正に失敗したら再起動し、プロンプトを言い直す
  • 自分が呼び出されるつもりで差分をレビューする

マネージャーになりたくなくてよい。だがエージェントで上手くやるエンジニアは、途中で管理を学んでいるはずだ、と Osmani は締める。

他ページとのつながり（wiki 側の推論）

  • critical-thinking-with-agents は同じ Osmani が個人の認知の側（仮説を先に書く・「検証済み」を事前に定義する・エージェントが決めたことを一覧させる）から書いたもので、本ページはマネージャーの実践の側（検証手段を渡す・文脈を渡す・要請と要件を分ける）から同じ問題を扱っていると読める。orchestration tax は前作では「生成する量と自分の名前を付けて出せる量の差」、本ページでは「追加の1体ごとに増える注意のコスト」と定義が少し違うが、同じ現象の二つの言い方と考えられる。
  • 本ページの「要請／要件」の線は claude-code-instruction-methods の公式フレームと同じ区分で、本ページはそれに管理論の根拠（Grove の task-relevant maturity）と、「強調しても拾われない1行は hook に、好みを表す hook は外す」という両方向の運用ルールを足していると考えられる。
  • 「コードレビューでなく追認」は、agent-era-code-review が描く Claude Code チームのレビュー再設計を個人の運用規模に引き下ろしたものと読める。「作らないことを決める」が挙げる「レビューと検証が希少資源」は、そのレビュー工程の上流で流入を絞る話である（同じ詰まりを制約理論で扱うのが ai-review-bottleneck）。
  • 「作らないことを決める」は、ai-native-engineering-org で Sashank Gondala が出荷工程を自動化した先の次のボトルネックとして挙げた「何を作るか決める工程」と、別の会社から同じ地点を指していると考えられる。
  • 「自分を必要としない走行を設計する」の5つの問いは、claude-code-long-task-harness の7層（CLAUDE.md・スキル・MCP・権限とフック・証拠を返すレビュアー・effort・/goal）とほぼ同じ部品を、運用者が走らせる前に確認する問いの形に並べ替えたものと読める。

問い

  • 自分の CLAUDE.md と hook のうち「好みを強制している hook」と「強調しても拾われない1行」はそれぞれどれか。Osmani の両方向ルールで棚卸しすると何が動くか
  • 「2回修正に失敗したらセッションを捨てる」は、3回目の修正が成功する割合が本当に低いことを前提にしている。自分のセッション履歴で数えて確かめられるか
  • 無人走行の5つの問いをこの wiki の launchd による ingest に当てはめると、欠けているのはガードレール（支出上限）か、非可逆の行為への人の承認か
