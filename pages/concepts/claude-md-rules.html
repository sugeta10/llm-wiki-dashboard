CLAUDE.md 行動ルール設計

CLAUDE.md は claude-code の動作を規定する行動契約ファイル。ウィッシュリストではなく、「この命令でどの失敗モードを閉じるか」を根拠に記述する。

Karpathy 発端

2026年1月末、andrej-karpathy が Claude のコーディング問題を3点指摘するスレッドを投稿： - サイレントな誤った前提: 聞かずに推測して進む - 過剰複雑化: 不要な抽象化・スペキュレーティブ機能の追加 - 直交的破壊: 触れる必要のないコードまで変更する

Forrest Chang がこの指摘を4ルールに変換して GitHub へ公開 → 初日 5,828 stars、2週間で 60,000 ブックマーク、2026年最速成長シングルファイルリポジトリ（120,000 stars）。

基本4ルール（Karpathy/Chang）

ルール 内容
Rule 1: Think Before Coding 仮定を明示。トレードオフを表面化。推測前に質問。シンプルな代替案を提案する
Rule 2: Simplicity First 問題を解く最小限のコード。不要な抽象化禁止。シニアエンジニアが複雑と呼ぶなら簡略化
Rule 3: Surgical Changes 必要な部分のみ触れる。隣接コード・コメント・フォーマットを「改善」しない
Rule 4: Goal-Driven Execution 成功基準を定義し達成まで繰り返す。手順指示ではなく成功形を与える

→ 未管理セッションの失敗モードの約40%を閉じる効果。

追加8ルール（May 2026 対応）

30コードベース × 6週間のテストから導出。Karpathy の4ルールが対象としなかった エージェント運用・マルチステップ問題 に対応。

ルール 閉じる失敗モード
Rule 5: 言語タスク以外をモデルに委ねない 非確定的な判断（リトライ可否等）にLLMを使うと毎回結果が変わる。決定論的処理はコードで実装する
Rule 6: ハードトークン予算 無制限ループで50,000トークン消費も発生する。セッション・タスク単位でトークン上限を明示する
Rule 7: 競合は平均化せず表面化 コードベース内に矛盾するパターンが2つある場合、両方を混ぜた不整合コードを生成する。競合検知時は確認を取る
Rule 8: 書く前に読む 隣接コードを理解せず類似コードを重複作成することがある。新規コード作成前に周辺を必ず読む
Rule 9: テストは目的ではない 「テスト通過」を目標にすると意味のないテスト（定数を返すだけ等）を書く。動作の正しさを検証する目的で書く
Rule 10: 長時間操作にチェックポイント 多ステップリファクタで途中失敗が後工程まで伝播する。Nステップごとに進捗を確認・コミットする
Rule 11: 慣習はノベルティより優先 既存パターンがあるのに独自パターンを導入する。コードベースの既存スタイル・パターンに従う
Rule 12: 失敗は可視化して隠さない 「正常完了」しながら実は失敗（スキップ・定数返却等）していることがある。エラー・スキップは必ず表面化する

測定効果

設定 ミス率 CLAUDE.md コンプライアンス
ルールなし 41% —
基本4ルール 11% 78%
12ルール 3% 76%

コンプライアンスをほぼ維持しながらミス率を追加削減 → 8ルールは4ルールと競合しない。

制約・注意事項

  • 200行上限: CLAUDE.md が200行を超えると重要ルールが埋もれコンプライアンスが急落
  • 14ルール上限: 18ルールでテストするとコンプライアンスが76% → 52%に低下
  • ルール > 例: 例はコンテキストを重く消費し過学習を招く。抽象的な命令形ルールの方が効果的
  • 「シニアに」は無意味: Claude はすでに自己をシニアと評価している。命令形の具体的ルールが有効
  • capability-agnostic: ツール依存のルール（「eslintを使え」等）はツール非存在時に無言で失敗する。「コードベースの強制スタイルに従え」のように記述する

Karpathy 4ルールの限界（May 2026 時点）

課題 内容
長期エージェントタスク ルールがコード生成の瞬間を対象としており、マルチステップパイプラインを対象外とする
マルチコードベース一貫性 「既存スタイルに合わせる」はスタイルが一つであることを前提とする
テスト品質 「テスト通過」を成功基準にするため、意味のないテストを書いても合格する
Production vs Prototype 「シンプリシティファースト」がプロトタイプで必要な探索的コードも制限する

自律運用での実践知（観察ログ・未検証）

長時間の自律タスクを回す現場では、ミス防止より「捏造とスコープ逸脱を止める」定型文が効くという報告が出ている。

  • 2026-06-11 @AI_masaou: claude-fable-5 を数時間ぶん回す自律タスクで効く定型文が結局4つに集約されたと投稿。記事への導線つきteaserで本文では2つのみ可視: 1. 報告の前に各主張をツールの実行結果と突き合わせて監査させる → 捏造された進捗報告がほぼ消えると主張。Rule 12（失敗を可視化して隠さない・正常完了を装う問題）を自律ランで強化した形 2. 頼んでないことはするな／相談されただけなら直す前に見立てを返せ、と境界を引く → Rule 3（Surgical Changes）と claude-md-persistent-contract の②暴走止め（勝手なアクション禁止・スコープ厳守）に対応
  • 自律実行が長くなるほどコード生成の瞬間を縛る基本ルールより、報告の正直さと境界の維持が支配的になる、という loop-engineering のEscalation/Verification設計とも整合する観点。残り2つの定型文は元記事未取得のため捏造せず保留。

MEMORY.md + ERRORS.md 補助ファイル

claude-md-rules の記憶補完として、同リポジトリルートに以下を併置する実践が広がっている：

  • MEMORY.md: セッション間で持ち越したい意思決定ログ（「PrismaではなくDrizzleを選んだ理由」等）
  • ERRORS.md: 過去の失敗パターン記録（Claudeが再度同じ誤提案をするのを防ぐ）
