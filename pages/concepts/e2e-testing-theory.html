E2E テスト大全：E2E テスト周辺の理論（Kuniwak）

TL;DR: E2E テストは全構成要素を本物で結合する忠実度の高い手法だが、実行コスト・保守コスト・原因調査範囲・結果の不確実性・組み合わせ爆発という 5 つの数理的制約を免れず、テストを書くのが AI になっても制約は変わらないので、分岐網羅は単体テストに、結合バグは設計段階の形式手法に、E2E は主要フローの貫通確認・外部連携の忠実度・性能と使用性の確認に限定して配置せよ、と Kuniwak（@orga_chem）が定義・欠陥分類・分類体系・実装パターンまで体系化した記事。

記事の背景は、AI のコード生成能力の向上で「E2E テストの実装は全部 AI に任せれば解決する」「AI に設計と実装を任せているので単体テストや結合テストが確認にならない」と語られる一方、現場では壊れやすい・遅い・Flaky（結果が不安定）という課題が残っている、という X を中心とした議論の過熱である。Kuniwak（GitHub では Yuki Kokubun・Formal Methods Learner・Software Engineer in Test と自己紹介。spec-ssot-view-separation の note 記事ではコインチェック株式会社所属）は、長年「E2E 戦士」として E2E 自動化と格闘し理論を探究してきた集大成として本稿を書いたと述べ、賞味期限の短いツール固有の知識を避け、グラフベーステストや ContextStream パターンのような自身の独自整理の用語には [^独自用語] の印を付けている。AI に指示するときの注意として Kuniwak は、独自用語は単語だけでは AI に伝わらないので、本稿の定義文やコード例をそのままプロンプトに含めよ、と明記する。初中級者には持続可能な E2E を自ら設計し AI に指示するための辞書を、上級者には「なぜ E2E は脆いのか」「なぜ単体テストとの分担が要るのか」の数理的な裏付けを提供する、というのが本稿の狙いである。

境界と定義

Kuniwak の定義では、E2E テストは利用者が直接接するインターフェースから永続化層までの全構成要素を結合し、インターフェース側から操作と検証を行うテストである。インターフェースは GUI なら画面、API サービスなら公開エンドポイントで、E2E は UI を伴うシステムに限らない。結合する要素の扱いは自組織の制御下かで分かれ、自社のバックエンド・DB・ワーカーは本物を結合し、外部の決済代行や ID プロバイダはテストダブル（スタブやモック）への差し替えを許容する。

ここから 2 つの区別が出る。UI を「状態を受け取り描画結果を返す関数」として設計し UI カタログ上でスクリーンショット差分（Visual Regression Testing）やコンポーネントのイベント検証を行うテストは、UI のテストではあるが DB やバックエンドと結合していないので E2E ではない。逆に、公開 Web API やバッチパイプラインがインターフェースなら、UI を一切操作せず API を叩いて永続化層への反映を検証するテストも E2E である、と Kuniwak は整理する。

検知できる欠陥の 4 分類

Kuniwak は E2E で検知できる欠陥を、上位の基準への適合性を問う正当性違反と、問題領域への適合性を問う妥当性違反に大別する。これは Boehm の検証（正しく作っているか）と妥当性確認（正しいものを作っているか）の区別に対応する。

大分類 小分類 定義（Kuniwak） 踏切の例
正当性違反 活性違反 仕様上受け付けねばならない操作を実装が拒否する 電車がいないのに遮断機が上がらない
正当性違反 安全性違反 発生してはならない状態に遷移する、または実行されてはならない操作を受け付ける 電車が通過中なのに遮断機が上がる
妥当性違反 性能劣化 過去版や基準値と比べ応答時間やリソース消費が悪化する 接近から遮断完了まで 5 分以上
妥当性違反 低使用性 認知負荷や操作の手間が大きく目的達成が困難 警報灯が虹色に点滅し切迫度が分からない

活性と安全性の定義は、プロセス代数 CSP（Communicating Sequential Processes）の安定失敗詳細化におけるトレース集合と失敗集合の絞り込みに対応させた定式化で、分散システムで広く使われる Alpern と Schneider の安全性・活性分解とは分類基準が異なるため同定理の帰結は適用できない、と Kuniwak は脚注で断る。モデルベーステストで標準的な適合関係 ioco でも入力完全な仕様のもとでは同等の性質が得られるが、設計検証と同一のモデルを一貫して使うため CSP を採った、という。

利点：結合バグ・忠実度・内部設計への非依存

結合バグの検出。個々のコンポーネントの単体テストが全部通っていても、前段の事後条件と後段の事前条件（契約による設計の言葉）に不整合があると結合時に欠陥が出る。Kuniwak の例は Myers の三角形問題で、「3 要素が数字として解釈できれば自然数の組を出す」バリデーションと、「3 辺が三角形の成立条件を満たし昇順に整列している前提で種類を出す」分類器を結合し、文字列 "5, 1, 1" を与えると、分類器が末尾を最大辺とみなして 5 + 1 > 1 だけで成立と判定し、二辺が等しいので「二等辺三角形」を返す。各単体テストは合格しているのに、前段の出力仕様が後段の入力前提を保証していないため欠陥が生じる。ただし結合バグの検出手段は E2E に限らず、要求仕様をコンポーネント仕様へ分割する設計段階で詳細化関係を検証すれば実装前に見つかる。E2E で結合バグを見つける行為は、設計段階で検出できた不整合を実装後まで持ち越して検知している側面を持つ、と Kuniwak は書く。

高い忠実度。単体テストのテストダブルが本物の挙動（例外条件・境界値・遅延）を正確に模倣していないと偽陽性・偽陰性が出る。E2E はなるべく本物同士を接続するのでこの乖離を減らせる。

内部設計への非依存。依存性注入が無くグローバル変数やシングルトンが多用されたコードは単体で初期化すること自体が困難だが、E2E は外部境界からブラックボックスとして駆動するので内部がどれほど密結合でもテストを書ける。レガシーコード変更時の保護ネット（Feathers）として E2E が重宝される理由である。

欠点と 5 つの数理的制約

Kuniwak は E2E の多用戦略が失敗しやすいことを、Google のテスト基盤チームの同趣旨の指摘（Wacker 2015）も引きつつ、各コンポーネントが下位層の N 個を結合する木構造が M 層続くモデルで説明する。数値はすべて Kuniwak のモデル上の例示である。

制約 Kuniwak の説明 数値例（N=4・M=4・K=4）
実行コスト 単体は 1 ケース ms オーダー、E2E はブラウザ起動・通信・レンダリングで数十秒オーダーと 4〜5 桁の差。CI の許容時間が一定なら E2E のケース数は原理的に 4〜5 桁少なくならざるをえない。並列化は 4 桁の計算資源を並べるコストを考えれば埋まらない —
保守コストと脆さ 1 コンポーネントの仕様変更で、単体は該当する K 個の修正で済むが、E2E は変更箇所を通る全シナリオに波及する（ログインに 2 段階認証を必須化するとログインを要する E2E が全部壊れる） コンポーネント 4⁴ = 256 個。単体の修正 4 件に対し E2E は最大 256 × 4 = 1,024 件、256 倍
原因調査範囲 単体の失敗は原因候補 1 個、E2E は結合された全部から切り分ける 原因候補は最大 Nᴹ = 256 個、調査時間も最大 256 倍
結果の不確実性 失敗が独立と仮定し、個々の事象の失敗率 0.1% でも直列 100 個で全体の成功率は (1 − 0.001)¹⁰⁰ ≈ 90.5%。障害間に相関があるので独立の仮定は上界も下界も与えないが、結合数とともに不確実性が累積する傾向を示す。Google もテスト実行の一定割合が不確実だと報告（Micco 2016） 10 回に 1 回は欠陥と無関係に失敗
カバレッジの組み合わせ爆発 N 通りと M 通りの分岐を持つ 2 コンポーネントの直列結合で、単体は N + M、E2E は N × M ケース要る。直列数が増えると指数的に増大し、E2E だけで全組み合わせを網羅する方針は破綻する。結合バグを見つけきることは、設計段階で形式手法を使わない限りどこかで諦めねばならない 単体 8 ケース、E2E 16 ケース

実行速度の緩和策として、目的の画面状態までの前処理を UI 操作でなく API 直接呼び出しや DB への直接レコード挿入で代替する手法があるが、バイパスした処理の結合を省いているため実際には再現できない状態を作りうる、つまり忠実度を部分的に犠牲にするトレードオフだ、と Kuniwak は注意する。

AI 時代でも制約は不変。生成 AI でテストコードの記述速度は上がったが、実行時間の物理的遅延・ネットワーク越しの確率的失敗・組み合わせ爆発は作成者が人間から AI に代わっても解消されない。AI エージェントに E2E の実行と自動修正をループさせると 1 試行ごとに数十秒から数分の待ちが発生し、完了までの所要時間が肥大化する。テスト容易な内部設計を行い単体テスト主体の開発ループを AI に指示するほうが効率的だ、と Kuniwak は述べる。

配置の原則と AI への指示の仕方

原則は「欠陥の性質に応じた適切なレイヤーでこまめに検証する」で、Kuniwak はテストピラミッド（Cohn・Fowler）から各層に役割を割り当てる。単体テスト層は分岐網羅や境界値分析など論理的正確性を担い、組み合わせの大部分をここで試す。結合テスト・E2E 層は仕様間の整合性（結合バグ）と実環境での忠実度を担い、ケース数を厳選する。設計検証（形式手法）は、結合バグを実装前に排除できる環境なら CSP などのリファインメント検査を設計段階で適用すると投資対効果が高い。

AI への指示例として Kuniwak は、EC サイトの決済に「プレミアムチェックアウト」を足す場面で 2 つの指示を対比する。指示パターン A「機能を実装し、ブラウザ上で商品をカートに入れ通常とプレミアムの決済が完了することを E2E で検証せよ」では、AI は UI 操作を含む E2E を生成してブラウザを起動し、描画待ちやセレクタ不整合のたびに修正ループが回り長時間かかる。指示パターン B「チェックアウト処理をストラテジーパターンで設計し、通常とプレミアムの判定・割引計算を独立したクラスに分離せよ。各ストラテジーの仕様分岐は単体テストで網羅し、E2E には『プレミアム会員でログインするとプレミアム経路が選択される』代表 1 シナリオだけ追加せよ」では、分岐網羅がミリ秒で終わる単体テストに押し込められ、AI は短時間で試行錯誤を終え CI も圧迫しない。AI の能力を引き出すには、開発者側がテストの数理的特性を理解し、アーキテクチャとテスト配置へ誘導する必要がある、と Kuniwak は結ぶ。

E2E テストの分類体系

Kuniwak は E2E を入力と仕組みで分類し、いずれも手動・自動の両方があるとする。

手法 入力 テストオラクル（合否の判定基準） 検知できる欠陥 カバレッジの増やし方
例ベース UI 操作と表示確認の系列（イベント列）＋実装 1 トレースとその期待結果の組 主に活性違反。アサーションを書けば安全性違反・性能劣化も シナリオ数を増やす
グラフベース [^独自用語] 状態遷移モデル（形式仕様）＋実装 トレース集合と失敗集合 活性違反・安全性違反・性能劣化 実行時間を増やす
モンキーベース [^独自用語] 実装のみ 暗黙的オラクル（クラッシュ・未処理例外・HTTP 500 など） 対象に依存しない一般的な安全性違反・性能劣化 実行時間を増やす
ペルソナベース [^独自用語] 想定ユーザーのペルソナ記述＋実装 1 層目はゴール到達、2 層目は到達までの手数・時間・誤操作・迷いのコスト 低使用性 ペルソナの種類を増やす
エラー推測ベース 過去の欠陥統計＋実装 テスターの頭の中の暗黙の状態遷移モデルと暗黙的オラクル 過去に経験した類型の活性・安全性違反 実行時間かシナリオを増やす

前 3 つが機械的な規則やモデルで操作を選ぶルールベース、後 2 つが人や AI の判断で選ぶ非ルールベースである。グラフベーステストの仕組みは、実行済みイベント列 p について、p が仕様のトレース集合に含まれるかを確認（含まれなければ安全性違反で停止）→ 実装の安定状態で拒否されるイベント集合を計測し仕様の失敗集合に含まれるかを確認（含まれなければ活性違反で停止）→ 実行可能イベントから探索アルゴリズムで 1 つ選び p の末尾に追加して実行 → 反復、という手順である。UI 要素の無効化や非表示は実行不能とみなし、押下後にエラー表示が出る要素は実行可能としてエラー状態への遷移として検証する。疑似乱数による探索は深さ方向に偏るので定期的に初期状態へリセットして幅を確保する。トレース集合や失敗集合を外延的に書き下すのは無理（A→B→A→B を繰り返すだけのモデルでもトレース集合は無限）なので、意図した集合を持つ状態遷移モデルを構成する。例ベースのテストは、この 2 集合それぞれの補集合から 1 要素を抜き出すことに相当する、と Kuniwak は位置づける。モンキーベースの暗黙的オラクルは、404 Not Found のように正常系でも出るものがあるので仕様に応じた調整が要る。ペルソナベースは、LLM を使う自律エージェントにペルソナを与えて操作させれば人間のユーザビリティテストの前段スクリーニングになる。

戦略の選び方

冒頭の図のとおり、Kuniwak の推奨は状態遷移モデルに基づくグラフベースと、高価値シナリオ（会員登録→カート→クーポン→購入完了のような一連の流れ）を固定した例ベースの併用である。グラフベースは状態空間を確率的に巡回するので高価値シナリオを限られた時間内に確実に実行する保証が無く、高価値シナリオは例ベースで明示的に固定し、未知の遷移や境界的なパスの探索をグラフベースに委ねる。状態遷移モデルは単にテスト入力であるだけでなく、開発初期に AI エージェントや実装者への厳密な仕様として流用でき、PlantUML のステートマシン図のサブセットからモデルを生成・検証するツール（Kuniwak の puml-parallel など）を使えば仕様策定とテスト自動化の基盤を同一資産から構築できる、と Kuniwak は書く。モデルを書くコストを払えず欠陥統計があればエラー推測ベースを、どちらも無い新規システムなら既成のクローラーや GUI 探索ツールを流用できるモンキーベースを、高価値シナリオの例ベースに組み合わせる。使いやすさも見たいならどの構成にもペルソナベースを足す。

自動 E2E テストの実装パターン

  • ReusableOperator パターン [^独自用語]: セレクタ指定・文字入力・クリックといった低レベル操作と高レベルなイベントを疎結合に分離し、イベント名をキーとする辞書（Map<Event, Operator>）に具象操作を定義して、シナリオ側は辞書の操作を呼ぶ。UI のセレクタや DOM 構造が変わっても修正は辞書内の関数 1 箇所で済み、シナリオ本体を書き換えない。グラフベースやモンキーベースで抽象イベントをブラウザ操作へ写す実行エンジンとして多用される
  • PageObject パターン: ReusableOperator のイベントと操作の対応を「画面」や「UI コンポーネント」単位でクラスやモジュールにまとめたもの。Selenium プロジェクトの実践から生まれ、例ベースのテストコードの整理で広く普及（Fowler 2013）
  • ContextStream パターン [^独自用語]: 画面遷移を「画面型と文脈型を受け取り次の画面型と文脈型を返す非同期関数」(Screen₁, Context₁) → Promise<(Screen₂, Context₂)> と定義し、関数プログラミングのコンビネータで合成する。多相的な静的型と組み合わせると「ログイン画面の後にしかマイページは開けない」「未認証の文脈では注文確定画面を呼べない」という遷移の前後関係をコンパイル時に検査でき、画面の不整合がテスト実行前に弾かれる。脚注では、PageObject の代替として 2016 年に提唱された Screenplay パターンが Actor を中心に Task や Interaction を順次実行する一対象のモノイドの構造を持つのに対し、ContextStream は画面型と文脈型の直積を対象・遷移関数を射とする多対象の圏を形成し、射の結合可能性が静的型で拘束されるため無効な遷移の合成を構造的に防げる、と対比する
  • Record & Playback パターン: 人や AI の操作履歴を JSON や YAML のイベント列として保存し再生エンジンで逐次実行する。作成の初速は高いが、DOM のわずかな変化やタイミングの変化で再生が失敗しやすい
  • テストケース連鎖パターン [^独自用語]: ケースごとにブラウザを再起動して初期状態からやり直す独立性の原則を厳格に守るとログインやデータ作成が反復されるので、「A が成功した場合に限り A の終了状態を引き継いで B を開始する」依存関係をランナーに宣言する。ランナーは依存グラフを解析し、イベント列集合の接頭辞木（Trie）を走査するように実行計画を生成し、先行が失敗したら後続を自動で「スキップ」にしてレポートの正確性を保つ。A の DB 副作用やセッション変更が B に影響して偽陽性・偽陰性を起こすリスクがあるので、副作用の局所化とテストデータの分離が前提

実行タイミング

タイミング 利点 欠点 適用（Kuniwak）
実装前（先行実行） トップレベル仕様を起点に開発でき、「定義した E2E シナリオの何本が通ったか」が客観的な進捗指標になる UI レイアウトや API 細目が未確定だと実装都合の変更ごとに書き直し 仕様が強固に確定した基幹業務・グラフベース（状態遷移モデル先行）
結合後（追認実行） 動いている画面に対して書くので手戻りが少ない 「本来あるべき仕様」でなく「現に動いている実装」を無批判に追認しバグを正解にしやすい。終盤まで全体を検証できず結合バグ発覚時の手戻りが大きい 探索的な新規開発・既存システムのリグレッション防止

取り上げなかった 3 題

Kuniwak が意図的に扱わなかった題と理由も記事にある。テスト選択（欠陥を検知しそうなケースだけ走らせる技術）は研究は多いが現実の規模に適用できる実用的なものを見たことがなく、自身もマニュアル E2E のカバレッジから関数トレースとの関係を測り機械学習でテスト文から関数トレースを推測させたが、前提として人間が面倒な手順で大量に手動 E2E を実行する必要があり実用化の光を見ていない。自動修正（Self-Healing）は AI 以前からある概念で、セレクタのヒーリングはオラクルの核心を書き換えないので実害が少なかったが、それを超えた修正は実装の追認でしかなく、無意味なだけでなく計算コストを無駄にするので有害ですらある。並列化は代表的な選択肢だが、環境の独立性の担保方法がアプリケーションごとにまちまちなので言及を避けた。記事末尾では Kuniwak が関わる Podcast くわラジ（@kuwa_raji）の第 26 回「E2E テストに全振りするな」を案内している。

他ページとのつながり（wiki 側の推論）

  • behavioral-specification は同著者が「何を仕様として書くか」（変換システムとリアクティブシステム・状態遷移図・内部イベント τ）を示した前段で、本稿のグラフベーステストはその状態遷移図をテストオラクルとして再利用する。活性と安全性の分類も同じ CSP の土台に立つ
  • spec-ssot-view-separation は同著者の puml-parallel で仕様本体を SSoT として管理する技法で、本稿が「状態遷移モデルは仕様としても E2E の入力としても使え、同一資産から構築できる」と書く部分の実装側にあたる
  • parallel-e2e-testing（株式会社 Berry）は、Kuniwak が「環境の独立性はアプリごと」として省いた並列化を、per-test データ独立と storageState で具体化した実例である。Berry が「前提データ投入は UI を通さない」と決めたのは、Kuniwak が忠実度のトレードオフとして挙げる API/DB 直接投入のバイパスそのもので、Berry はそれを速度のために受け入れている
  • ai-coding-loop-formal（mizchi）が TLA+ や Alloy を仕様の検査に使う棚卸しに対し、Kuniwak は結合バグを実装前に排除する設計検証として CSP のリファインメント検査を置く。どちらも「AI が書く時代でも形式手法の置き場は設計段階」と見ている

問い

  • この vault の validate_wiki.py や公開サイトの検査は、Kuniwak の分類で言えば例ベースか、暗黙的オラクルのモンキーベースか。状態遷移モデルを書く価値がある対象（ingest の状態遷移など）はあるか
  • 指示パターン B（ストラテジーパターン＋単体網羅＋代表 1 シナリオ）を、自分が AI に実装を頼むときの定型文に入れると、修正ループの回数は実際に減るか
  • ContextStream の「遷移順を型で静的検査する」発想は、Playwright のテストコードに TypeScript で現実的に導入できるか。既存の PageObject からの移行コストはどのくらいか
