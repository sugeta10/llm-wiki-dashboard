エージェントを信頼するための逆ピラミッド（poteto）

TL;DR: エージェントの仕事を信頼できるようにする手段を、コードベース改善・静的解析・散文（ルールやスキル）・人間レビューの4層に分け、努力の大半を上の決定論的な層に置いて人間レビューを最小にする、pstack 作者 @poteto の指針。エージェントを訂正するたびに「どの層で直すか」を選ぶための道具立てとして読める。

📌 X bookmark: 12,124（2026-10-17 時点）

エージェントがコードを着地させる速度は、人間が PR を1本ずつ精読できる速度を超えている。@poteto（表示名 lauren）は、React コアチームで React Compiler を作り、Meta・Netflix・Cursor で数百万行のコードに関わってきたと pstack の README で名乗り、X のプロフィールでは @SpaceXSI で Grok Bot に携わると書く。この投稿は「どうすればエージェントの仕事をもっと信頼できるか」を4層の手段に分解し、文面ごとエージェントに渡せる形で書かれている。添付画像は「whenever you correct your agent（エージェントを訂正するときはいつでも）」と題した逆三角形で、上から codebase・static analysis・prose・human review の順に層が狭くなる。投稿本文は X の長文投稿で、ブックマーク取得時の本文は冒頭で途切れていたため、全文は X API から取得した（取得結果は sources の全文メモに置いた）。

4つの層（投稿からの転記）

層 手段 @poteto の説明
1. コードベース改善 より良いアーキテクチャ・強い型と不変条件・明確な境界 ただの良いソフトウェア工学。エージェントは既存のものを真似て最短経路を取るので、「楽な道が正しい道」になるよう作る。コードで問題のカテゴリごと消せば、二度と考えなくてよい
2. 静的解析 lint ルール・テスト・CI・検証（例: TLA+） 問題を事前に捕まえる、トークン効率のとても良い手段
3. 散文（prose） コメント・ルール・AGENTS.md・スキル 強制できず、エージェントの判断に頼るものすべて。最小限に使う。ただし /create-verification-skill は使う
4. 人間レビュー PR を人が読む 最もスケールしない。エージェントが着地させる速度では全 PR の精読はほぼ不可能なので、その労力は最も効く地点、つまりエージェントが既定で正しいことをする環境の設計に使う

@poteto はこの4層を逆ピラミッドと呼び、努力の大半を上（コードベース）に、最少を下（人間レビュー）に置けと述べる。理由は、コードベース改善は決定論的なのでトークン効率が高く、「夜ぐっすり眠れる」からだと書く。

散文の層にスキルや AGENTS.md が含まれている点は見落としやすい。@poteto の分類では、スキルは「強制できずエージェントの判断に頼る」側であり、lint や CI と同じ層ではない。例外として名指しされた /create-verification-skill は、アプリの振る舞いを証明するスクリプト化された検証手段をプロジェクトに生成するスキルで、散文の層から静的解析の層へ検証を移すための道具と位置づけられる（スキルの説明は pstack を参照）。

エージェントに渡すプロンプト（投稿からの転記）

投稿の後半は、pstack を入れたエージェントに新しい Project としてそのまま渡す4ステップの指示文になっている。

  1. 私が PR・コード・アーキテクチャにフィードバックした Slack やチャットのメッセージ、コードレビューのコメントを見て回る
  2. /recall で過去のトランスクリプトから、私がエージェントをどう操縦しているかを学ぶ
  3. /poteto-mode で過去のコミットに /correct と /architect をかけ、エージェントが最もよく陥る落とし穴を見つける。そのうえで、私が所有するコードをエージェントに優しい形へ再設計する計画を提案する。未解決の問いは私に預けずプロトタイプで答え、計画は実データで裏づける
  4. 始める前に /sharpen と /in-your-own-words を使い、このプロンプトを私と確認する

各コマンドは pstack のスキルである。pstack の README によれば /correct は訂正の履歴から誤りの類型を掘り、効く最上位の層（アーキテクチャ、次に型・lint・CI、次にテスト、最後に文書）で直し、各規則と強制手段の対応表を保つ。この順序は逆ピラミッドの層の順と一致しており、投稿はその運用を読者自身のコードベースに適用させる手順と読める。同じ README の原則 encode-lessons-in-structure（規則は文章を増やすのでなく lint・メタデータフラグ・実行時チェック・スクリプトとして符号化する）も、散文の層から上の層へ移せという同じ主張である。

他ページとのつながり（wiki 側の推論）

  • correction-routing（@VibeMarketer_）は訂正を「事実・決定・ポリシー・スキル・ワーカー・機械的ゲート」の6分類で書き戻し先に振り分ける。@poteto の4層は、知識の種類でなく強制力の強さで振り分ける軸であり、6分類の「危険な操作→機械的ゲート」は上2層、「好み→ポリシー」は散文層に当たると考えられる
  • claude-md-multilayer-design（@ai_ai_ailover）の「同じ修正を二回したら仕組みへ昇格」「必ず守らせる境界は Permission・Hooks へ」は、Claude Code の設定の中で同じ方向を取る。@poteto はその外側、コードベース自体の改善を最上層に置く
  • ai-coding-loop-formal（mizchi）の「AGENTS.md は判断基準だけ」「仕様の正しさは TLA+ や Z3 で検査」は、散文を最小にし静的解析の層へ寄せる同じ配分と読める
  • agent-era-code-review（Anthropic）は人間承認をリスク別に0・1・2人へ絞り、「同じ指摘が続いたらスキル・lint・CLAUDE.md という発生源で直す」とする。@poteto の「人間レビューは最もスケールしない」を組織規模で実装した形と考えられる
  • uncle-bob-martin の「エージェントのコードは読まず極端な制約で囲む」は、最下層をほぼゼロにし上位層へ寄せた極端形にあたる
  • 手順の最後で使う /in-your-own-words は、同著者の goal-restatement-prompt と同じ「ゴールと問題を自分の言葉で言い直させる」内容をスキルにしたものである

問い

  • このvault の CLAUDE.md・LESSONS.md・memory はすべて散文の層にある。validate_wiki.py や hooks（静的解析の層）へ落とせる規則はどれで、落とした後に散文から消せる行は何行か
  • 「散文は最小限に」は、CLAUDE.md を厚くして当てた claude-md-rules の実測（ミス率41%→3%）と矛盾するか。それとも「まず散文で当て、効いた規則を上の層へ移す」という順番の話か
  • 努力の配分が逆ピラミッドになっているかを測る指標は何か。たとえば、訂正のうちコードや lint として恒久化された割合を追えるか
