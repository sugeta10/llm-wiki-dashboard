# 多エージェントシステムがエンジニアに課す新しい問題群（基盤・身元と権限・隔離・監視と停止）

> **TL;DR**: 数千のエージェントが持続的に働く多エージェントシステムは、基盤・身元と権限・隔離・監視と停止の4領域にまだ解かれていない工学問題を生むので、AI にアイデンティティ危機を感じているエンジニアこそそこへ深入りせよ、と Anthropic の head of platform である Katelyn Lesse が X 記事で説く。

エージェントは人間が1往復ごとに見るチャットから始まり、モデルが難しい問題に長く取り組めるようになるにつれてクラウドで動くようになり、同時にモデル同士が協働できるようになって、オーケストレーターがサブエージェントを生む構成や、実行以外の役（採点・助言・dreaming）を持たせる構成が作られた、と Lesse は経緯を整理する。その先にあるのが、本格的な研究・発見・ハードウェア設計のような難問に向けて数千のエージェントが持続的に働くシステムで、そこで新しい種類のソフトウェア工学の問題がすでに顔を出し始めていると Lesse は書く。主張の骨子は、モデルは今後も良くなり続けるが、その力を引き出して「病気の治癒のような良い結果」を世界が信頼できる形にできるかは、エンジニアがこれらの問題を解くかどうかにかかっている、という点にある。Lesse は Anthropic の head of platform で、以前は Stripe と Betterment に在籍したと X プロフィールに記す。

## 4つの問題領域（Lesse の整理）

### 基盤：Kubernetes の前提とエージェントの形が合わない

ソフトウェア業界は Kubernetes の上に積み上げてきたが、Kubernetes は無状態で複製されるアプリか、数の安定した有状態 Pod の集合のために設計されている、と Lesse は指摘する。エージェントはそのどちらでもなく、孤立した・有状態の・単一インスタンスのワークロードで、仕事の合間に任意の長さで遊休し、ツール・モデル推論・他のエージェント・人間の入力を待つ時間が長い。起動の速さが要るもの、計算資源の浪費を避けたいもの、桁違いの規模が要るものが混在する。Lesse は AI 基盤企業が新しいファイルシステムやサンドボックスを作っていること、Google のチームが新しいランタイムとして Agent Substrate を作っていることを挙げつつ、決めるべきことは山ほど残っていると書く。

### 身元と権限：認証は流用で進むが、認可は大きく未解決

認証（どのエージェントがその操作をしたかを特定する）には、マイクロサービスの世界で鍛えられた部品が使える。静的な鍵でなく短寿命の証明書を使うワークロード ID がその例で、人々がこれをエージェントに当てはめ始めている、と Lesse は述べる。一方で認可（エージェントに何を許すか）はずっと開いた問題だとする。多くのエージェントは人の代理として、その人の身元と資格情報でシステムにアクセスし操作する。この on-behalf-of（OBO、人の代理）の構成には、まず「操作したのは本人でなくエージェントだ」と識別する問題があり、さらに深い所に同意の問題がある。多エージェントシステムが何週間も働くとき、人はエージェントに何を許すかをどうやって意味のある形で承認するのか。ツール呼び出しの自動承認のような機能は助けになるが、大規模にはもっと深い権限設計が要ると Lesse は書く。エージェントが自分自身の身元で働く場合はさらに未解決で、協働するエージェント間で「頼んできた相手をどう信頼するか」も問題になる。

### セキュリティと隔離：未パッチの基盤ソフトの上で数千のエージェントが動く

ここ数か月、とくにここ数週間は、業界が当てられるより速く脆弱性が表面化しており、その多くは多くのシステムが依存する中核ソフトにある、と Lesse は書く（投稿は 2026-10-26 で、[[concepts/php-critical-vuln-2026-10]] の直後にあたる）。その上で信頼できないコードを書き、信頼できない内容を読む数千の持続エージェントが動くなら、未パッチの脆弱性はずっと危険になる。エンジニアがやるべき最重要のことの一つは、カーネル・ブラウザ・ランタイム・共通ライブラリを堅牢化する工夫だと Lesse は言う。多エージェントにはもう一つのひねりがある。侵害された1体のエージェントが注入された指示を協働相手に渡し、それが記憶に残って将来のエージェントがうっかり信じる。最初の1体が侵害されたとき系全体のどこまでが危険にさらされるかという被害範囲（blast radius）が現実の問題になるので、エージェントは強く隔離されたサンドボックス実行環境で操作すべきだと Lesse は結論づける。

### 監視と停止：改ざんできないトレースと、資格情報ごと止めるキルスイッチ

多エージェントシステムが良い方向に進んでいるかを確かめ、そうでなければ捕まえて切る道具が要る。Lesse が挙げる要件は3つで、エージェントを横断する OTel（OpenTelemetry）トレース、エージェントが自分のトレースも他のエージェントのトレースも書き換えられないこと、監視から起動でき系全体を一度に止めて資格情報も切るキルスイッチである。本当に難しいのは「系がいつ悪い方向へ向かっているか」を知ることで、問題を解こうとする善意の粘り強さは悪意とよく似て見える、と Lesse は書く。許可リスト外のドメインへ繰り返し到達を試みる、がその例である。

## エンジニアへのメッセージ

この文章は、自分の知識や技能が重要でなくなると考えてアイデンティティ危機にあるエンジニアに向けたものだと Lesse は明言する。これらの問題が解かれるか、多エージェントシステムが世界の難問を解けるかの分かれ目はあなたとあなたの技能であり、これらの領域に深く入り、新しいことを学び、意見を持て、と呼びかける。問題空間の多くは新しい解法に開いていて、いまはエンジニアとして歴史上もっとも面白い時期の一つだ、というのが記事の締めくくりである。

## 他ページとのつながり（wiki 側の推論）

- 監視と停止の要件は、[[concepts/models-as-insider-risks]] で Satya Nadella が求めた「権限・観測・停止をモデルの外に置く」「改ざん不能な証跡」「非常ブレーキ」を、基盤を作る側が実装要件として言い直したものと読める。Nadella が企業 CEO として業界標準を求めたのに対し、Lesse は解く側のエンジニアに宛てている
- 認可が「大きく未解決」という見立てに対し、[[concepts/ai-agent-governance]] の外部ポリシー（Cedar/Rex）や [[tools/1password-for-agents]] の資格情報単位の承認は、それぞれ実行時の操作可否と入口のサインインという部分への答えにあたる。Lesse が挙げる「週単位で働くエージェントへの意味のある同意」は、どちらも直接には扱っていない
- 認証の部品として挙がる「静的な鍵でなく短寿命の証明書」は、Anthropic 自身の API 認証にある [[concepts/workload-identity-federation]] と同じ考え方である
- 「業界が当てられるより速く脆弱性が出る」局面への対処は、組織の経営判断として [[concepts/cto-ciso-vuln-surge-playbook]] が米内貴志の4点を扱う。Lesse は同じ局面を基盤エンジニアの仕事（中核ソフトの堅牢化と強い隔離）として扱っており、両者は同じ出来事の組織側と基盤側にあたる
- 「侵害されたエージェントの指示が記憶に残り将来のエージェントが信じる」問題は、[[concepts/harness-seven-jobs]] が言う権限をモデルの外に置く設計と、[[concepts/multi-agent-patterns]] のオーケストレーター構成の双方に、記憶の出所管理という要件を足すものと考えられる

## 問い

- 自分の夜間自動処理（launchd で動く ingest など）に、「エージェントが自分のログを書き換えられない」「資格情報ごと止められる」最小構成はあるか
- 週単位で働くエージェントに対して、どの粒度の承認が「意味のある同意」になるか。ツール呼び出しの自動承認で済む範囲と済まない範囲の境界はどこか
- 善意の粘りと悪意を区別する信号は、許可リスト外ドメインへの再試行のほかに何があるか
