AIエージェントガバナンス

本番環境でAIエージェントを運用する際の認可・実行制御の設計パターン。MCP認可と外部ポリシーを別レイヤーとして扱うことが重要。

MCP認可の位置づけ（ゲートウェイレイヤー）

**MCP Authorization**（OAuth 2.1ベース）は「誰が、どのMCPサーバーに、どのトークンでアクセスできるか」を扱う。

ただし、MCPサーバーへのアクセス認可と、エージェントが生成した個々の操作が業務上実行されてよいかは別問題：

  • Salesforce MCPに正しくOAuth接続できても → 「この顧客レコードを更新してよいか」は決まらない
  • GitHub MCPで認可されていても → 「main branchへの変更・リリースタグ打ちが許可されるか」は別

MCP認可はゲートウェイの認可（誰がサーバーにアクセスできるか）。業務上の操作可否は、そのさらに内側で別のポリシーとして扱う必要がある。

外部ポリシーによる実行制御

AWS **Rex**（Trusted Remote Execution）が示す設計思想：

  • スクリプト（「何をしたいか」）と **Cedarポリシー**（「何を許可するか」）を分離
  • エージェントが生成した実行内容と、組織が定める許可ポリシーを同じ場所に置かない
  • callerはpolicyを変更できない（実行環境が隔離）

> エージェントにやりたいことを生成させる。ただし、実行できるかどうかは外部ポリシーで決める。

**Cedar**はAWSがオープンソース公開した認可ポリシー言語。principal・action・resource・contextをもとにpermit/forbidを表現する（OPAのRegoに近い位置づけ）。

外部ポリシーで扱う要素

| 要素 | 内容 | |------|------| | 操作種別 | read / suggest / write / delete / spend / deploy | | 対象データ | 個人情報、顧客秘密、契約情報、社内機密、公開情報 | | 環境 | sandbox、staging、本番 | | 実行主体 | ユーザー権限、サービスアカウント、エージェント専用ID | | 承認要否 | 自動実行、事前承認、事後レビュー | | 監査ログ | 入力、判断、承認者、実行結果、失敗時の処理 | | 停止条件 | rate limit、異常検知、権限剥奪、rollback |

推奨アーキテクチャ

MCP認可（ゲートウェイ） → 外部ポリシー（実行制御） → Human-in-the-loop（承認フロー）

Human-in-the-loopは「UIでOK？と聞く」だけでは不足。誰が承認すべきか、どの条件なら不要か、承認記録をどこに残すか、後から説明可能かまで設計が必要。

Rexの限界

Rexが強制できるのはRex runtime内のRex SDK経由操作のみ。以下はカバー外：

  • MCPサーバー経由のSaaS操作
  • ブラウザを通じた管理画面操作
  • 複数ツールをまたぐ業務フロー（CRM読み込み → 契約書作成 → ワークフロー承認 → Slack通知）

Rexは「外部ポリシーで実行を縛る」設計思想の参照例であって、導入すれば企業ガバナンス要件を満たせるわけではない。
