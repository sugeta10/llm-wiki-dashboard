> **TL;DR**: 使用制限に当たるのはプランが安いからでなく使い方の設計が抜けているから、と @milesdeutscher が置き直した5ステップの運用フレーム。計画・チャット長・記憶・モデル・ツール枠をそれぞれ別の設計対象として扱う。

トークンを食うのはテキストチャット自体ではなく、コーディング・ビルド・デザインといった実行系タスクだと @milesdeutscher は観察する。ここから出てくるのは「何を作るかを考える工程」と「実際に作る工程」をどこで分けるかという配分の問題で、5つのステップはいずれもその配分を決める場所を1つずつ指している。関連: [[tools/claude-code]]・[[concepts/prompt-engineering]]

- **計画優先**: 計画フェーズを Haiku で行い、実装フェーズのみ Opus に切り替えてコストを抑える。
- **チャット長管理**: 長いチャットは「古いコンテキストを毎回再読み込みさせる」ためトークンを浪費し品質も落ちる。1つの長いチャットより3つの独立チャットの方が効率的で、Projects 機能でサブチャットを整理し新タスクは必ず新チャットで開くよう同氏は推奨する。チャットを切り替える際は「このセッションをコンテキストを失わずに再起動できるプロンプトを出力して」と依頼する「Mega Prompt」手法で引き継ぐ。
- **モデルスタッキング**: 軽タスクは Haiku、中タスクは Sonnet、重タスク・最終仕上げは Opus へエスカレーションする（[[concepts/llm-model-selection-strategy]]）。
- **記憶管理**: ルール・指示を書く Instructions.md と、継続更新する Memory.md の2ファイルを Claude Code / Cowork にアタッチする。
- **ツール分割と補助設定**: Extended/Adaptive Thinking は大半のタスクで OFF、Concise スタイルでトークンを節約する。プラン更新（$20→$100→$200）より追加クレジット購入の方がコスパの良いケースもあると同氏は指摘する。

## エスカレート式：下から始めて足りないときだけ上げる

Claude Code 運営アカウントの @ClaudeCode_love は、この5ステップを日本語で解説するにあたり、Step 4 のモデル使い分けを「エスカレート方式」と名づけた。Haiku（軽いタスク）から始めて Sonnet、Opus と順に上げ、本当に能力が足りないときだけ切り替える。「Opus を全てに使うのは近所のコンビニにフェラーリを出すようなもの」で、体感として90%のタスクは Opus 以外で処理でき、Opus が必要なのは残り10%だと @milesdeutscher は述べる。

計画と実行を分ける効き方は、同じファイナンス追跡アプリを作る2人の比較で説明されている。計画に2分しかかけず設計が甘いまま着手した側は3回作り直し、計画に20分かけて設計を固めた側は1回で完了した。考える時間をケチるほど作り直しの回数が増え、実行系のトークンがそのぶん膨らむ、という構造になっている。

チャット長の管理には、Project Instructions に「使用量を節約しようとしていることを踏まえ、簡潔に答え、適切なときは新しいチャットに移るべきタイミングや節約のコツを助言してほしい」という趣旨の1文を入れておく手がある。Claude 自身が節約のアドバイザー役になり、チャットを切り替える頃合いを教えてくれるようになると @milesdeutscher は言う。

設定面では、Extended Thinking を普段オフにして複雑な推論・数学的タスクのときだけ入れる、ホーム画面の Concise スタイルに切り替えて出力そのものを短くする、Claude Code では Low エフォートを選ぶ、という3つが挙がる。加えて、ニュース検索・リサーチ・要約のような単純タスクは Kimi や DeepSeek といった無料・安価なモデルへ逃がし、Claude の枠は「Claude でしかできないこと」に温存する。繰り返す手順は [[concepts/claude-skills]] として保存すれば、毎回説明し直す代わりに1コマンドで呼べる。

残量が少なくなったら振る舞いを変えるのも明示された運用で、残り20%を切ったら Haiku に切り替える・Extended Thinking を切る・チャットを短く保つ、と意識的にモードを落とす。
