# semantic-generation skill（独自語の乱立・曖昧化対策）

> **TL;DR**: [[tools/openai-codex]] が設計・実装時に対象の定まらない独自語をもっともらしく生成してしまう問題に対し、語（ラベル）を書く前に「出典・目的・具体対象・役割・前後関係」を埋めさせ、そこまで書けた行にだけ最後に候補語を与える7列の対応表を設計前に作らせる skill（@u1）。

```mermaid
flowchart LR
  A["原因箇所は\nまだわからない"] --> B["試験を行う"] --> C["結果から\n原因箇所を切り分ける"] --> D["切り分けた後で\n対策を選ぶ"]
```

著者 @u1 は、Codex 5.5から5.6になっても継続して起きている問題として、言葉の定義を曖昧にしたまま設計・実装を進めてしまう挙動を報告する。具体例として、調査レポートの「圧縮時点」という見出しが「会話履歴が設定量に達したこと」「自動要約を始めるしきい値」「実際に要約が始まる時」の三つの意味を行き来し、開始条件・値・事象という別々の対象を一語が兼ねた結果、調査全体が間違った方向に誘導されたと述べる。同じセッションでは、上図のような「原因箇所不明→試験→結果から切り分け→対策選択」という4段階の作業を、Codexが「観測を一つに集める」という一句に圧縮して要約し、集める対象（試験で得た値・記録）と目的（原因箇所の切り分け）を取り違え、次の作業順序ごと消えてしまう事例も起きたという。

著者はこの失敗を、訂正済みの独自語を記録して次セッションへ持ち越す対策では止められないと結論づける。問題の本質は「以前間違えた語をまた使うこと」ではなく、対象が曖昧なまま語を先に置き、その語で思考を進めてしまうことにあり、訂正リストを作っても次は別の造語が生まれるだけだからだ。そこで著者は、独自語を作る前に候補語一覧を毎セッション先に作らせる方針に切り替えた。対応表は「出典・目的・具体対象・役割・前後関係・候補語・初出定義」の7列で構成し、**候補語を右端に置く**ことで、具体対象と役割を書き切るまで語を確定できない設計にする。役割も1行1つに絞り、開始条件と事象を同じ語で扱いたくなったら行を分けることで、「一語で済ませたい」という圧力より先に対象が2つあるという事実を可視化する。

著者は、生成AIは対象や目的が定まっていなくてももっともらしい語で文章を続けられてしまう点が設計では危険になり得ると述べ、semantic-generation skillは「よい言葉を探す」skillではなく「独自語を使おうとしたときに立ち止まらせ適切な語を選ばせる」skillだと位置づける。

## 問い

- 7列対応表を毎セッション作らせるコストは、[[concepts/loop-engineering]] の4条件テストに照らして見合うか。頻度の低いタスクにまで適用する価値はあるか。
- このwikiのCLAUDE.md・SKILL.mdにも、対象が曖昧なまま先に固定した独自語（「長文フラグ」「粒度判定」等）はないか。referent-before-label ruleで棚卸しできるか。
- [[concepts/agent-reflection-layer]] の対応表（判断を確信度つきでdecisions-logに残す）と、本skillの7列対応表は「書く前に構造化させる」という同じ設計思想か。
