Codex エージェントループ

openai-codex の Codex CLI が採用するエージェントループの内部実装。OpenAI Responses API を使ってユーザー・モデル・ツールの三者間インタラクションを制御する中核ロジック。Michael Bolin（OpenAI MTS）による公式解説シリーズ第1弾（2026-01-23）。

観察ログ（未検証）

  • 2026-05-21: Compactionの圧縮メカニズム — コンテキスト圧縮が劣化しにくい理由は、テキスト形式ではなく潜在空間のベクター表現でバイナリ圧縮しているため（@kenn の観察）。公式ブログでも "preserves the model's latent understanding" と記述。元々膨大なテキストを超圧縮したものがLLMの重みであることと整合する設計。セッションが極めて長くなっても意味的劣化が少ないのはこの仕組みによる
  • 2026-01-23: previous_response_id を意図的に使わない設計判断：ZDR（Zero Data Retention）対応と完全ステートレス性のトレードオフを優先。ステートレス化でプロバイダー側のキャッシュ保持義務が不要になる
  • 2026-01-23: MCP ツールは Codex CLI のサンドボックス外で動作する——MCP サーバー側が自前でガードレールを実装する責任を負う（Codex の shell ツールのみサンドボックス適用）
  • 2026-01-23: コンテキストウィンドウの増大は会話ターン数に対して二次オーダーで成長する。プロンプトキャッシュのヒット率が高ければ実質的に線形コストに抑えられる

検証済み事実

  • 2026-01-23: エージェントループの基本構造 — ユーザー入力 → プロンプト構築 → Responses API 推論 → ツールコール or アシスタントメッセージ の繰り返し。1ターン = 1アシスタントメッセージで終了
  • 2026-01-23: Responses API エンドポイント — 認証方式によりエンドポイントが分岐：ChatGPT ログインは chatgpt.com/backend-api/codex/responses、APIキーは api.openai.com/v1/responses、ローカル（--oss）は localhost:11434/v1/responses
  • 2026-01-23: プロンプトロール優先度 — system > developer > user > assistant の降順。instructions フィールドが system/developer ロール、input フィールドの各アイテムが会話履歴を担う
  • 2026-01-23: input の構成順序（初回ターン）：①サンドボックス権限説明（developer ロール）→ ②developer_instructions（オプション）→ ③ユーザー指示（AGENTS.md 等の集約）→ ④環境コンテキスト（cwd・shell）→ ⑤ユーザーメッセージ
  • 2026-01-23: プロンプトキャッシュ保持の条件 — ツールリストの順序変動・モデル切替・サンドボックス設定変更・カレントディレクトリ変更はキャッシュミスを引き起こす。MCP サーバーのツール順不整合バグ（PR #2611）で発覚した実例あり
  • 2026-01-23: mid-conversation の設定変更対応 — サンドボックスや cwd が変わっても input の既存アイテムを書き換えず、新しいメッセージを末尾に追記することでキャッシュプレフィックスを保護する
  • 2026-01-23: コンテキスト圧縮（Compaction） — auto_compact_limit 超過時に /responses/compact エンドポイントを自動呼び出し。返却される type=compaction アイテム（encrypted_content 付き）が以降の input を代替する。以前は /compact コマンドの手動実行のみだった
  • 2026-01-23: reasoning の扱い — モデルが出力した type=reasoning アイテムは次の推論リクエストの input に含める必要がある。ZDR 環境では encrypted_content がサーバー側で復号される（OpenAI は復号キーのみ保持・データは保持しない）
