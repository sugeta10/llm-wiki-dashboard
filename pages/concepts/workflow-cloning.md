# ワークフロー・クローニング（手順を保存して自分を複製する）

> **TL;DR**: 第二の脳が壊れるのは人間の手入れを前提にしているから——ノート（何を知っているか）でなく手順（どうやるか）を仕様とスキルとして保存し、エージェントに実行させる5工程の設計。

Notion も Obsidian も機能しないわけではない、と @milesdeutscher は前置きする。問題は維持コストのほうにある——ノートを追加するのをやめた瞬間に Obsidian は役に立たなくなり、顧客管理やデータベースを更新するのをやめた瞬間に Notion は役に立たなくなる。忙しい人間が更新の担い手である限り、システムは人間より先に止まる。そこで彼が数週間かけて組んだのは、作業をするそばから自ら育ち、文脈を恒久的に持ち越し、手順についてのノートでなく実際の手順そのものを保持するシステムだと述べる。

```mermaid
flowchart LR
  A["I. ワークフロー監査<br>AIに自分をインタビューさせる"] --> B["II. Clone Score<br>時間×反復性で優先度付け"]
  B --> C["III. 仕様とスキル<br>口頭説明 or 作業録画"]
  C --> D["IV. フォルダと可視化<br>business brain + specs + マインドマップ"]
  D --> E["V. デプロイ<br>エージェント / ループ"]
```

## I. ワークフロー監査——特定していないものは自動化できない

最初にやるのは、自分が実際に何をしているかの棚卸しになる。@milesdeutscher の方法は、AIに自分をインタビューさせて生活と事業の反復タスクを列挙させ、そのうえで自動化する価値の高い順に並べ替えさせるというもの。着手前にまず自分の「プロフィール」を作らせて文脈を渡しておくと精度が上がるとしている。1回のセッションで全タスクは出ないが、それでよく、土台を作って後から足していけばよいと彼は書く。

## II. Clone Score——時間を食い、かつ繰り返すものから

洗い出したタスクは Clone Score で順位づけされる。論理は単純で、時間を食うものほど、そして反復性が高いものほど、先に自動化する価値が上がる。

ここで重要なのは、判定の粒度をワークフローでなく**工程**に置くことだと @milesdeutscher は自身のスポンサー獲得パイプラインを例に説明する。「案件を取る」は表面上ひとつの仕事に見えるが、実際には7つの独立した工程からなり、自動化できるものとできないものが混在している——リサーチと連絡先の収集は完全に自動化できるが、最終交渉とコンテンツの納品はできない。監査の目的は日々のワークフローを見つけることだけでなく、その内側のどの工程が自動化されるべきかを特定することにある、というのが彼の主張の核心になる。

## III. 仕様とスキルを作る2つのルート

自動化する対象が決まったら、エージェントが実際に走らせられる仕様（spec）とスキルに分解する。ルートは2つ。

**話して作る**——工程を口で説明できるならこれが最速だとし、スキル作成機能を開いてワークフローを一通り話す。@milesdeutscher はタイプでなく音声入力（Whispr Flow）を使う。話すほうが自然に説明できるからだという。**作業を録画して作る**——Claude デスクトップの「Record a skill」で自分の作業を記録させ、再利用可能なスキルを自動生成させる。彼が気に入っている点は Claude が声も拾うことで、たとえばツイートの書き方をスキルにしたいなら、実際にツイートを1本書きながら思考過程をそのまま喋ればよい。「従業員に、自分ならこうやるという手順を教えているのに本当に近い」と彼は表現する。この段階のゴールは、満足できるスキルが数本ある状態にすることであって、全部を揃えることではない。

## IV. フォルダと可視化——人間は markdown を読まない

作った仕様には置き場所と、全体を見渡す手段が要る。@milesdeutscher のフォルダは2部構成で、**business brain**（会議・財務など、エージェントに知っていてほしいものを何でも入れる）と **specs**（前段で作った仕様・スキル・手順書を置く）に分かれる。

そのうえで彼が強調するのは、エージェントは markdown の仕様ファイルを問題なく読めるが、自分では読まないという非対称性だ。走らせているスキルとワークフローの数が増えるほど全体の把握が難しくなるため、彼は全ワークフローを視覚的なマインドマップにしている。仕様ファイルやフォルダを Claude Cowork に渡し、マップ生成用のプロンプトを貼るだけで作れる。この可視化は見栄えの話に見えて実務的な強制力を持つ、と彼は言う——AIを実際にどこで使っているのかを直視させ、手順書を段階ごとに書き出させ、必要なら層を足せるようにする。出力したHTMLはローカルに置いてもホスティングに載せてもよい。

## V. デプロイ

最後の工程は最も簡単だと彼は書く。仕様ファイルを Claude のターミナルに渡してエージェントを走らせる、Hermes agent に仕様フォルダを食わせる、Claude Code の `/loop` で自動化ループを回す——どれでもよく、組み合わせても構わない。最終アドバイスは、いきなり数十個を自動化しようとせず、レバレッジの高い日次タスクから数本だけ始めて時間をかけて足していくこと。

## 問い

- このvaultは「ノートを貯める」側に厚く、ingest・weekly・lintは手順化済み。まだ仕様化されていない反復作業（記事の書き起こし・調査の進め方・意思決定の型）のうち Clone Score が高いのはどれか
- 工程単位の自動化可否判定を wiki 運用に当てると、「最終交渉」に相当する自動化してはいけない工程はどこか（カテゴリ判定か、公開判断か）
- 全スキルのマインドマップ可視化は、このvaultではカタログページとスキル一覧で足りているか。それとも「自分がどこでAIを使っているか」は別の図が要るか
