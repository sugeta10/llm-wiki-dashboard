エージェント規模のソース管理（Anthropic Scion）

TL;DR: マージ数が1日2,500件から3万件超へ増えたAnthropicが、gitをやめて「クライアントは常にオンライン・計算はサーバー側」を前提に作り直した社内VCS Scion と、その設計原則・構築で得た教訓。

flowchart LR
  Client["scn client"] -->|socket| Daemon["scion-daemon（ノード単位）"]
  Daemon --> Cache["scion-cache（リージョン単位）"]
  Cache -->|キャッシュミス時のみ| Server["scion-server（正本）"]
  Server --> Spanner["Spanner / クラウドストレージ"]
  Jobs["CIジョブ・社内ツール"] -->|API問い合わせ| Server

コードを書く速さがボトルネックでなくなると、次に詰まるのは人間の規模に合わせて作られた開発基盤（ソース管理・ビルド・CI）だ、とAnthropicのソース管理チーム（執筆は Nick G. ほか）が述べる。gitは各クローンが完全な履歴を持ちオフラインで動く分散設計で、大半のリポジトリには正しい。ところが同社のモノレポは main の履歴だけで約100GB、圧縮した作業コピーで25GB超あり、CIだけで1日約2,500万回チェックアウトする。素朴に取得すれば1日600PB超のgit通信になる計算だとチームは書く。shallow clone・sparse checkout・promisor remote（必要時に取得する遠隔）・社内ミラー数百台・blobストレージ上のスナップショット（seed）で時間は稼げたが、マージ速度が上がるにつれ運用が難しくなった。

チームが気づいたのは、git を「正本が1つの集中型」として使っていながら、クライアントのほぼすべてが定義上オンラインのエージェントとジョブだという食い違いである。そこで「エージェントは常時オンライン」を出発点にソース管理を設計し直し、5か月でモノレポを git から Scion へ完全移行した。設計は Google の Piper と Meta の Sapling という先行例の教訓を踏まえたと明記している。

6つの設計原則（Anthropic の整理）

  1. クライアントは常にオンライン: リポジトリ全体を持たせず、必要になった時点でサーバーから取る
  2. クライアントとサーバーの非対称: 履歴・blame の回答、コミット作成、マージ・リベースはサーバーが担う。クライアントは上限付きのローカルキャッシュ、作業コピーの展開、ファイル変更の監視だけを持つ
  3. 包括的なソース管理サービスが新しい用途を生む: クライアントが使う問い合わせをすべて API で公開し、CI や社内ツールはローカルリポジトリなしで「この行を最後に変えたのは誰か」等を聞ける。自動 bisect・自動 revert のパイプラインはこれがないと大規模では実用にならなかったとチームは書く
  4. すべてを水平スケール可能に: リポジトリ全体を実体化したコピーはサーバーにも存在しない。packfile（git の圧縮オブジェクト束）に当たるものがなく、リポジトリ保守が要らない
  5. コミットは安く・差分比例で・ロックなし: コミット・リベース・マージはすべてサーバー上で起き、push が存在しない。コストはリポジトリ全体でなく変更の大きさに比例させる。全サーバーが合意すべきグローバル状態は将来のスケール問題になるため、main と release 以外の ref（ブランチ・タグ）は使わせない方針
  6. 作業コピーは任意で、sparse が前提: 差分などはサーバーに聞けばよく、多くの書き込みもチェックアウトなしに API で済む。必要なときもクライアントが求めたディレクトリだけの sparse checkout か、読んだファイルだけ実体化する仮想チェックアウトを使う

仕組み

データ構造: 作業の単位は「changeset」で、書き込み先行ログ（write-ahead log）の1エントリである。git のコミットがツリーへのポインタを持つのに対し、changeset は第1親からの変更ファイル一覧と、blob ストレージ上の圧縮内容への内容アドレス（content-addressed）ポインタを持つ。packfile もロックもサーバー間調整も ref の移動もないため高スループットで受け付けられ、ref を動かす操作は Spanner の1行への compare-and-swap として changeset 作成と切り離されている。

派生データ: changeset は差分しか持たないので、blame・パス履歴・コミットグラフのスキップリストなどを「派生データ」として別に作る。どの種類も「親の値から自分の値を計算する」再帰的定義で、1つの汎用機構で計算する。チームが挙げる利点は、新しい種類を足しやすいこと、種類ごとに即時計算か遅延かを選べること、クライアントが内部構造を見ないのでクライアントを変えずに最適化できることの3つ。

取得プロトコルとキャッシュ階層: git の取得はクライアントが「何を持っているか」をサーバーに伝えて差分 packfile を作らせるが、Scion はクライアントが欲しいツリーと blob だけを要求する。ルートツリーから再帰的に不足分を要求し、次に blob を要求する。要求対象はすべて不変オブジェクトなのでどのキャッシュでも答えられ、構成は古典的な多段キャッシュに近くなる。ノード単位の scion-daemon → リージョン単位の scion-cache → 正本の scion-server（Spanner・クラウドストレージを読む）の3段は同一の RPC に応答するため、クライアントはキャッシュの構成を知らなくてよい。理論上はどの段同士も通信できるが、リージョンキャッシュの障害が上流を巻き込まないよう段階を厳格に守らせている。

構築で得た教訓（Anthropic の主張）

  • 小さなチームでの高速開発が普通になる: 7人のチームが Scion とコードレビューツール Antique、関連システム6つほどを作り、5か月で移行した。その間に1日のマージ量は10倍になったとチームは書く
  • エンジニアの価値は減らないが仕事が変わる: 関わった全員が「コードを書くのは Claude の方がうまい」と評価する一方、システム間の構成と設計上のトレードオフの理解は人間が担った。エンジニアの役割は Claude に「no」と言うことが多かったという。例として、main へのマージ時刻をレビューツールに聞かずにコミットログを線形に読んで総当たりする実装が移行中に複数生まれた。敵対的レビュー（adversarial-panel と同系統の手法）は有効だが近視眼的にもなり、別の社内サービスを過剰に疑って不要な検証と複雑さを足させた例を挙げる。人間は今もすべての変更要求をレビューするが、全行を読むのでなく変更の意図を見る
  • 最適化と品質が上がる: 大量のコードを書ける分、非自明なインフラ・ソース管理のやり取りすべての密閉シミュレーション、ファジング、レート制限まで作れた。祖先クエリがインデックスを使えていなかった問題のように、専門家が数日〜数週かける最適化を Claude がついでに見つけたとチームは述べる
  • モノレポの新しいセキュリティ: ディレクトリ単位の権限付与と、承認に意味的な制約（コメントだけの変更と論理変更を区別する等）を表現できるレビューツールで、人間は重大な変更に集中できる
  • 運用の水準が上がる: claude-tag で、1コンポーネントの健全性だけに執着する Claude を Slack チャンネルごとに置いた（チームは「superfan」と呼ぶ）。テレメトリとログを見られ、従来のアラートでは平板に見えるほど微妙で新規の異常を拾うという
  • 前提を考え直す: テスト中に数百〜数千件がマージされる規模では、マージキューにグローバルなロックをかける業界標準を再現できなかった。代わりにマージ後・デプロイ前の自動テストへ投資し、同時変更の衝突は Claude が人間が気づくより速く直すという

チームは Scion を git の一般的な代替とは位置づけない。数万人規模のエンジニアかエージェントの群れが書く巨大モノレポでのみ意味があり、レビュー・コード検索・CI まで専用にする必要があるため公開版は作らないと書く。代わりに、git サーバーをクライアントと同じ作りにしなくてよいこと、フォージ横断で標準化されたサーバー側 RPC、取得交渉プロトコルの見直し、sparse と shallow の機能の組み合わせやすさを提案する。

観察ログ（未検証）

  • 2026-10-14: Anthropic のソース管理チームの自己申告で、Scion 基盤は CPU・メモリで旧 git ミラー基盤の200分の1、各キャッシュ段のヒット率99%超、CI・研究ジョブのチェックアウトが分単位から秒単位（約2桁高速化）、CI だけで CPU 容量25%の節約。社内初期版の Claude Mythos Preview が手書きの git→Scion 取り込みパイプラインを追加指示なしで書き直し、メモリ20分の1・4倍高速にしたとも書く
  • 2026-10-14: 同チームの予測「この種の問題は今後6〜12か月で一般的になる」（答え合わせ対象）

問い

  • 「エージェントは常時オンライン」という前提は、自分の開発環境（ローカルの Claude Code セッション・worktree 運用）でも成り立つか。成り立つならどの git 操作がサーバー API で置き換えられるか
  • 人間のレビュー対象を「全行」から「意図」へ移したとき、意図からずれた実装（コミットログを総当たりする例）を何で検出しているのか。ai-review-bottleneck の流入を絞るやり方とどう組み合わせられるか
  • マージキューのロックをやめマージ後テストへ寄せる判断は、Scion 規模より何桁小さいチームまで有効か
