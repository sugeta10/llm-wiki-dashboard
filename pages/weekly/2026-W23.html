Weekly Insights: 2026-W23（2026-06-01〜06-07）

今週の中心テーマ

今週の隠れた主役は「中間記法」——AIにGUIやバイナリを直接触らせず、LLMが大量に学習したテキスト/Web表現を界面に挟むと、精度とトークン効率が同時に上がる。勝負どころは「どこで働かせるか」ではなく「どの記法で渡すか」に移った。

先週（W22）が「AIエージェントが"働く場所"になった」という 場所 の話だったのに対し、今週は同じ素材を 界面＝AIに渡す記法の設計 という別の次元で切る。

なぜそう見えるか（根拠ページ）

  • intermediate-notation-pattern — 今週の通奏低音。AIにGUIを直接生成させずDSL（中間記法）を操作させ、GUIはそのレンダラに徹する。出力トークンが減り再生成のブレも消える、という原理そのもの
  • hyperframes — その実例。動画編集のXML/バイナリ（人間の視覚操作前提でLLMには外国語）を捨て、HTML+data-*属性という「LLMの母語」に状態を載せ替えてMP4を決定論生成する。ページ自身が「MNPの実例」と明言している
  • claude-skills — 記法を 持続させる 版。職務定義をMarkdownで書き自動ロードさせ、毎回の文脈再構築をなくす。「中間表現をテキストで固定し再利用する」という同じ動きを時間軸でやっている
  • understand-anything — 逆向きの中間表現。コードベースを事前に ナレッジグラフ という中間構造へ変換して俯瞰させる。grepライブ探索（claude-code-large-codebase）との対比が「どの中間表現を選ぶか」の問いを際立たせる

既存wikiとの接続

  • self-refining-skills — wiki地図で被参照16の主要ハブ。中間記法（特にclaude-skills）は「一度書いて使いながら育てる」資産であり、このハブの具体的な実装手段として接続する
  • spec-driven-development — 被参照14のハブ。MNPの「記法で意図を固定し、実装＝レンダリングをAIに委ねる」構図は、specでwhatを固定しhowを委ねる発想の界面設計版として地続き
  • prompt-engineering — 被参照26のハブ。今週の含意は「プロンプトを磨くより、AIに渡す記法そのものを設計し直すほうが効く局面がある」——プロンプト最適化の一段上のレイヤーとして接続する

sugeta-san への問い

あなたの LLM Wiki 自体が、すでに中間記法パターンの実装になっていないか？

→ links という軽量テキスト記法でAIと人間が同じ知識を読み書きし、dashboard がそのレンダラに徹している——これはまさに intermediate-notation-pattern の4要素（DSL／パーサー／シリアライザー／レンダラ）と同型。次の一手は新しいツールを足すことより、この「記法↔レンダラ」の双方向性を意識的に強くする（例: 機械可読なfrontmatterを増やし、生成側がそれを当てにできるようにする）方向が効きそう。

今週の小アクション（5分）

自分のwikiで「中間記法→レンダラ」が効いている実例を1つ確認する: 任意の1ページの被リンク数を dashboard で見て、links（記法）が被参照ランキング（レンダリング結果）に正しく反映されているかを目視する。ズレていれば、それが記法側で直すべき箇所。

いますぐAIと一緒に（コピペ）

以下をそのまま Claude / Claude Code に貼って、今週のテーマを自分のwikiに引き寄せる:

私のLLM Wiki（Obsidian vault）について相談したい。今週の中心テーマは「中間記法パターン（AIにGUIを直接触らせず、LLMの母語＝テキスト記法を界面に挟む）」。

1. このwiki自体を「中間記法パターンの実装」として捉えたとき、DSL/パーサー/シリアライザー/レンダラの4要素は今それぞれ何が担っているか整理して。
2. frontmatter を「もっと機械可読な中間記法」にして生成側（dashboard/gen_*.py）が当てにできるようにするなら、追加すべきフィールドを3つ、理由つきで提案して。
3. 提案のうち最も低コストで効果が高い1つだけを、今日試せる最小ステップに落として。
