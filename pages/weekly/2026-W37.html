Weekly Insights: 2026-W37（2026-09-07〜09-13）

今週のホットトピック

  • gpt-6-astra-skills-prompting OpenAI 側も「積み上げた指示を減らせ」に回った — Codex の開発者体験担当 Eric Provencher が、新世代 gpt-6-astra 前提でスキル・AGENTS.md の各行を「まだ要るか」で再審査せよと述べる。Anthropic 側の同じ主張と独立に並んだ（X bookmark 6,252）。
  • llm-wiki-v2 知識ベースの設計課題が「何を覚えるか」から「何を忘れるか」へ移った — Karpathy の LLM Wiki に確信度スコアの時間減衰・4層メモリ・忘却曲線・矛盾解決を足す青写真。このvault が名指しで当てはまる弱点（全ページを永遠に等しく有効として扱う）から出発している。
  • shikumika-vs-tejunsho 仕組み化とは手順を固定することでなく「直した結果が戻る場所」を決めること — @smark_x が無印良品の店舗マニュアル MUJIGRAM を引き、2,000ページが腐らないのは毎月直される場所があるからだと述べる。減らす側の閾値まで設計されている点が新しい（X bookmark 925）。
  • software-factory-cost-equation 減らすべき対象を金額で名指しした Uber — セッション単価を3項に分解し、「安いモデルへ下げる」でも「機能を削る」でもなく、価値ゼロのトークン消費だけを消す。利用7倍とセッション単価52%減を同時に出したと Uber Engineering が公表（X bookmark 5,958）。

深掘り

gpt-6-astra-skills-prompting OpenAI 側も「積み上げた指示を減らせ」に回った Provencher の主張は「エージェントを1年使ってきた人ほど、モデルを導くために書き足した指示が肥大している」から始まり、スキルは説明文を最短にする・根本文書は薄いルーターにする・手順書化しないの3点へ落ちます。Codex 固有の観察として、スキルを入れすぎると Codex が説明文を黙って切り詰め、モデルが各説明の一部しか見られなくなる挙動を挙げている点が実務的です。sugeta-san にとって重要なのは、同じ週に Anthropic 側の instruction-patch-lifecycle（Boris Cherny の「6か月ごとに全部消す」）と fable-5-1-prompting（公式7本を「全部貼ると精度が落ちる、困っている1〜2本だけ」）が並んだことです。ベンダーが違い、製品が違い、互いを参照した形跡もないのに指針が一致している——これは特定製品のクセではなく、モデルの判断力が上がった局面では指示の在庫が資産から負債へ転じる、という現象そのものが起きている可能性を示します（両者の一致は本 wiki 側の合成で、当人同士が同じ根拠を挙げているわけではありません）。

llm-wiki-v2 設計課題が「何を覚えるか」から「何を忘れるか」へ移った v2 が元パターンの弱点として名指しするのは「3ヶ月前に書かれた事実と昨日確認された事実が同じ重みで扱われる」ことで、対処は削除ではなく非優先化です。事実ごとに確信度スコアを持たせ、final_score = relevance × exp(-λ × days) で時間減衰させ、アクセスや新しいソースによる確認で曲線をリセットする。減衰係数 λ をカテゴリ別に変える設計まで含んでいる点が要で、このvault に当てはめるなら世代交代の速い models/ と長命な concepts/ で λ を分けることになります。同じ週に、個人が会話記憶のために独立に組んだ self-owned-ai-memory（要約→ベクトル化→分類→関連付け→忘却曲線）がほぼ同じ部品構成へ収束していました。ただし 2026-peng-llm-memory-faulty は「経験をコンパクトな教訓に繰り返し書き直すと記憶が劣化する」と示しており、減衰と再合成が劣化を防ぐのか早めるのかは今週の素材では決着していません。

shikumika-vs-tejunsho 「直した結果が戻る場所」を決める @smark_x の診断は「手順書が使われなくなるのは書き方のせいではなく、直した結果の戻り先まで設計されていないから」です。ここまでなら self-refining-skills の LESSONS.md と同じ話ですが、この記事が足しているのは減らす側の閾値です——例外は1回目では手順を更新せず「起きたこと」欄に書くだけにして2回目で初めて昇格させる、見なくなった手順は消して「やめたこと」欄へ理由つきで移す（理由が無いと半年後に誰かが善意で復活させる）、守れない頻度は願望なので即下げ、時間でなく条件で書く。@smark_x 自身が「Claude Code に渡す指示書も同じで、直したことが残る欄の無い指示書は翌日同じ間違いをする」と AI へ接続しています。人間のマニュアル運用の側から、今週の他の素材と同じ結論に到達している例です。

software-factory-cost-equation 減らす対象を金額で名指しする Uber の方程式は Price/Token・Tokens/Request・Requests/Turn の3項で、採用とエンゲージメントを表す項は伸ばし、「エンジニアの依頼の上にエージェントが自分のために行う作業」にあたる中間の項だけを削ります。個人規模へ持ち帰れる具体レバーは2つ挙がっていて、サブエージェントの既定モデルを弱く安いものに固定すること（Uber Engineering が最も効くと述べる）と、MCP ツールを CLI へ投影して事前ロードの50〜70Kトークンを避けることです。さらにセッション分析ダッシュボードが16種のアンチパターン（単純タスクへの上位モデル使用、大きな MCP 応答の文脈残留、10万トークン級の初期化オーバーヘッドなど）を金額影響つきで提示する、という部分が今週のテーマに直結します。「減らせ」は主張としては安いのに実行されにくい。実行されるのは、減らす対象に名前と金額が付いたときだ、という読みです。

今週の中心テーマ

AI運用の蓄積は、増やす機構だけを持つと腐る。今週の素材が揃って足したのは、減らす側の機構——期限つきパッチ・確信度の減衰・「やめたこと」欄——だった。

立場の違う4者が、同じ形の欠落を別々の場所で埋めています。モデルベンダーは指示に期限を設け（gpt-6-astra-skills-prompting、instruction-patch-lifecycle）、知識ベース設計は事実に減衰を設け（llm-wiki-v2、self-owned-ai-memory）、店舗マニュアルの運用は手順に「やめたこと」欄を設け（shikumika-vs-tejunsho）、Uber はトークン消費に金額の名札を付けました（software-factory-cost-equation）。共通するのは、蓄積を止めるのではなく、蓄積したものが自然に沈む経路を先に作っている点です。

先週（2026-W35）の「失敗を扱う語彙」が、起きたことをどう残すかの話だったのに対し、今週はその次に来る工程にあたります。残す設計だけを持つと、残したもの自体が次の失敗の原因になる。sugeta-san のvault で言えば、LESSONS.md も log.jsonl も規約も追記しかしない構造で、これは「育てる」側だけを実装した状態です。

ただし今週の素材には反証も含まれています。grok-bot の運営ボット Jenny は毎朝5時に全ボットと1on1を行い、プレイブックを毎日再注入することで「数週間経っても複雑なワークフローを忘れない」効果を出しており、指示を短く保つ方向とは逆を向いています。区別の線はおそらく「常時ロードされる指示か、発火時だけ読む規約か」で、consulting-pptx-skill が約80項目の規約ファイルを毎回読ませて品質を出しているのも後者だからだと考えられます（この線引きは本 wiki 側の解釈で、各著者が述べていることではありません）。減らすべきは在庫の総量ではなく、常時ロードされる層の在庫だ、という仮説です。

sugeta-san への問い

このvault の指示・スキル・教訓は、いま何行あって、最後に触ったのはいつですか——そして「やめたこと」はどこに残っていますか。

→ 今回の生成中に数えてみました。CLAUDE.md と .claude/skills/*/SKILL.md・LESSONS.md は合計12ファイル・1,865行で、最大の wiki-ingest/SKILL.md（415行）の最終コミットは 2026-07-06、gen-weekly-insights/SKILL.md（269行）は 2026-06-23 です。2〜3か月動いていない指示が在庫の中心を占めています。そして「やめたこと」の記録を全ファイルで探すと、見つかったのは wiki-ingest/SKILL.md の1行だけでした——「『著者帰属は観察ログだけ』という旧運用は廃止」。廃止の記録が本文にインラインで1件だけあり、置き場所は決まっていない状態です。shikumika-vs-tejunsho の言う「理由が無いと半年後に誰かが善意で復活させる」に、そのまま当てはまります。

今週の小アクション（5分）

指示の在庫を行数と最終更新日で並べてください。次のコマンドで棚卸しの候補が上から出ます（動作確認済み）:

for f in CLAUDE.md .claude/skills/*/SKILL.md .claude/skills/*/LESSONS.md; do
  [ -f "$f" ] || continue
  d=$(git log -1 --format=%ad --date=short -- "$f")
  [ -n "$d" ] || d="(未コミット)"
  printf "%5s行  最終更新 %-12s %s\n" "$(wc -l < "$f" | tr -d ' ')" "$d" "$f"
done | sort -rn

上位に来た「行数が多く・長く触っていない」ファイルが、instruction-patch-lifecycle の言う期限切れパッチの最有力候補です。

いますぐAIと一緒に（コピペ）

以下をそのまま Claude Code に貼ると、今週のテーマ「減らす側の機構」でこのリポジトリの指示在庫を棚卸しできます。

このリポジトリの指示在庫を Ablation の観点で棚卸ししてください。実行はせず、提案だけ出してください。

1. CLAUDE.md と .claude/skills/wiki-ingest/SKILL.md の各行を、
   「モデルが自力でできないから書いた（＝まだ要るパッチ）」
   「今のモデルなら指示なしでもできる（＝期限切れの候補）」
   「製品としての体験・出力形式を決めている（＝性能とは別枠で残す）」
   の3分類に振り分ける。判定の根拠を必ず添え、迷った行は「判定できない」に置く
2. 期限切れ候補のうち、外しても壊れないことを検証できるものを3つ選び、
   その検証方法（どの操作で・何を見れば失敗と分かるか）を1つずつ書く
3. 「やめたこと」欄をこのリポジトリのどこに置くべきか、
   既存の LESSONS.md・wiki/log.jsonl・docs/ の役割分担を踏まえて1案だけ提案する

判断基準は wiki/concepts/instruction-patch-lifecycle.md（パッチには期限がある・投機的に追加しない）と
wiki/concepts/shikumika-vs-tejunsho.md（消した理由を残さないと復活する）を参照してください。
