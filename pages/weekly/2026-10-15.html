Weekly Insights: 2026-10-15（2026-10-12〜10-18）

  • agent-scale-source-control git をやめた Anthropic のソース管理 Scion — 1日のマージが約2,500件から3万件超に増えたため、「クライアントは常にオンライン」を前提にソース管理を作り直した記録です（約1.9万ブックマーク）。
  • agent-trust-inverse-pyramid エージェントを信頼するための逆ピラミッド — pstack 作者の @poteto が、信頼の手段をコードベース・静的解析・散文・人間レビューの4層に分け、努力の大半を上の層に置けと述べました（約1.2万ブックマーク）。
  • agent-era-code-review Claude Code チームの多層レビュー — コードの約90%を Claude が書くチームが、レビューを6層の検査とリスク別の人間承認に組み替え、マージ数2倍超・revert 率40%超減を報告しました（Anthropic 一次情報、約3,300ブックマーク）。

深掘り

ai-ambition-four-types 「タスク」でなく「成果」を渡す 読みどころは4型の分類そのものより、Altitude の見分け方です。Rieseberg は「その作業について会議をする予定があるか」で、成果を渡すべき仕事かを判定します。もう一つの要点は、クラッシュゼロを任せる前に、クラッシュレポートの取得・バージョンとコミットの対応・3 OS での再現環境を先に整えたことです。成果を渡す前提として、モデルが自分で確かめられる環境を作っています。Depth の「モデルに自己採点させず外部の審判を使う」も同じ向きです。

agent-scale-source-control 人間が見るのは全行でなく「意図」 Scion の設計原則（サーバー側で計算する、push が無い、ref は main と release だけ）はモノレポ固有の話で、Anthropic のチーム自身も git の一般的な代替ではないと書いています。個人にも効く部分は教訓の節にあります。7人のチームで、「コードを書くのは Claude の方がうまい」という評価と、「エンジニアの役割は Claude に no と言うことが多かった」という報告が並んでいます。数値（CPU・メモリ200分の1など）はチームの自己申告で、外部検証はありません。

agent-trust-inverse-pyramid 訂正するたびに「どの層で直すか」を選ぶ @poteto の分類で見落としやすいのは、スキル・AGENTS.md・ルールが「散文」の層、つまり強制できずエージェントの判断に頼る側に入っている点です。lint や CI と同じ層ではありません。コードベースで問題のカテゴリごと消せば二度と考えなくてよい、というのが上の層を推す理由です。投稿後半の4ステップの指示文は、pstack の /correct（訂正の履歴から誤りの類型を掘り、効く最上位の層で直す）を自分のコードに当てる手順になっています。

agent-era-code-review 同じ指摘は「発生源」で直す 6層の検査の中で、今週の他の素材とつながるのは二つです。一つは、自動レビューが同じ指摘を繰り返したら、スキル・lint ルール・CLAUDE.md という発生源で直すという規則です。もう一つは収束の問題です。ある PR は一晩で50往復を超え、繰り返し指摘された箇所の約59%は初回パスの時点から既にあったコードでした。チームは往復を3回で打ち切り、それ以降は差分だけを再レビューし、指摘をバグの類型単位で出す形に変えました。

今週の中心テーマ

エージェントが人間の読める量を超えて書くようになった週に、素材が揃って動かしていたのは、人間が介入する「高さ」でした。1件の diff や1回の指示を直すのをやめ、同じ誤りが二度起きない層——コード・lint・名前・成果の定義——へ介入点を上げています。

今週の素材を並べると、同じ動きが四つの現場で起きています。@poteto は、訂正のたびに4層のどこで直すかを選び、できるだけ上の決定論的な層に置けと言います（agent-trust-inverse-pyramid）。Claude Code チームは、繰り返す指摘を PR 上で直し続けず、スキル・lint・CLAUDE.md へ戻します（agent-era-code-review）。Scion のチームは、全行を読むのをやめて変更の意図だけを見ます（agent-scale-source-control）。Rieseberg は、個別のクラッシュを直させる頼み方から、「クラッシュゼロに保って」という成果を渡す頼み方へ移りました（ai-ambition-four-types）。デザインの側でも同じことが起きています。@showheyohtaki は「おしゃれに動かして」という形容詞の代わりに、パララックスやオーバーシュートといった演出の名前を共有語彙として用意しました（ai-motion-vocabulary）。毎回の指示を、名前という一段上の層に固定する手です。

なぜ今週これが揃ったのかについて、私の仮説を述べます。人間が全部を読めるうちは、誤りを1件ずつ直しても量が追いつきます。Anthropic のモノレポのように1日3万件が入ると、1件を直す手間に件数を掛けた量が人間の時間を超えます。そこで、1回の介入が将来の多くの変更に効く場所へ、介入点を移すしかなくなります。素材の著者たちは互いを参照していません。ここで四つを一つの動きとして読むのは、並べて読んだ本 wiki 側の推論です。

過去の週との差を整理します。2026-W40 は「AI の判断を何と照合するか」、2026-W42 は「照合できなかったことを記録に残すか」を扱いました。どちらも1回の実行の中の話です。今週は、実行をまたいで同じ誤りを繰り返さないために、直したことをどこへ書き戻すかの話です。

このvaultに当てはめると、逆ピラミッドの形になっていません。ingest の学びを溜める .claude/skills/wiki-ingest/LESSONS.md（ingest スキルの失敗事例集）には箇条が104行あります。これはすべて散文の層です。一方、静的解析の層にあたる scripts/validate_wiki.py（wiki の構造検査スクリプト）が機械的に検査しているのは、frontmatter・孤立ページ・リンク切れ・Mermaid 図の4種類です。LESSONS.md の大半は粒度やカテゴリの判断事例なので、そもそも lint に落とせない判断も多いはずです。それでも、104行のうちどれが機械で検査できるかは、まだ一度も仕分けていません。

反証と、見落としやすい前提を三つ置きます。一つ目は、散文の層の効き目です。claude-md-rules は CLAUDE.md を厚くしてミス率が41%から3%に下がったという実測を載せています。散文が効かないわけではありません。「まず散文で当て、効いた規則を上の層へ移す」という順番の話として読む方が、両方の素材と整合します。二つ目は、上の層へ移すための前提条件です。Anthropic の多層レビューは、インシデントを起こした PR を集めた eval セットで、レビュアーを変えるたびに採点し直しています。複数エージェントの投票で指摘を絞る仕組みも、自社 PR での A/B テストを経て採用しました。このvaultは別モデルに再採点させる独立審判を試し、誤検知の多さで撤去しました。その差は手法の良し悪しより、効き目を測る仕組みがあったかどうかにあると考えます（確信度は中程度です）。三つ目は、層を上げても判断は人間に残ることです。Anthropic は、そもそも作るべきか・課金のような高リスクコード・他の人が真似するパターンを決める設計の三つを人間の判断として残しています。Scion チームの「no と言う」役割も同じです。介入点を上げる目的は人間の判断を減らすことではありません。人間の判断を、そこにしか置けない場所へ集めることです。

sugeta-san への問い

このvaultの LESSONS.md・CLAUDE.md・memory にある規則のうち、validate_wiki.py や hook に移せるものはいくつあり、移したら散文から何行消せますか。

→ LESSONS.md の大半は粒度・カテゴリの判断事例なので、移せるのは形式に関わる一部だと予想します（frontmatter の項目、ファイル名の規則、特定の記法の禁止など）。件数が小さくても、移した規則の分だけ毎回読み込む散文が減ります。逆ピラミッドの形に近づいているかを測る最初の数字にもなります。

今週の小アクション（5分）

LESSONS.md を開いて先頭から10行だけ読み、各行に「機械で検査できる」「判断が要る」のどちらかを付けてください。「機械で検査できる」が1つでもあれば、それが validate_wiki.py に足す最初の候補です。

いますぐAIと一緒に（コピペ）

以下をそのまま Claude Code に貼ると、このvaultの規則を逆ピラミッドの4層に仕分けられます。

このvaultの散文の規則を、@poteto の「逆ピラミッド」4層（コードベース・静的解析・散文・人間レビュー）で仕分けてください。編集はしないでください。

1. .claude/skills/wiki-ingest/LESSONS.md と CLAUDE.md の規則を1件ずつ読み、
   「静的解析の層へ移せる（lint・validate_wiki.py・hook で機械的に検査できる）」「散文に残すべき（判断が要る）」に分けてください
2. 移せるものについて、validate_wiki.py に足すチェックか hook の案を1行ずつ書き、移したあと散文から消せる行をファイル:行番号で示してください
3. 判断が要るものは、類型ごとにまとめて件数を出してください（例: 粒度判定 n 件、カテゴリ判定 n 件）
4. 最後に「散文の行数 → 移行後の行数」を1行で示してください（実装は私が承認してから）
